# ADR-0507: Verify event history at the point of use

Status: `accepted`
Decision date: 2026-10-12

## Context

The SQLite event store re-verified the complete history every time it opened, including read-only opens. Each report transaction did the same, and the context-quality publication path did it once per batch. A complete verification runs SQLite `quick_check` and `foreign_key_check`, decodes every outbox row, and recomputes every event hash and link. Consumers that read history added their own complete check before and after each traversal.

That cost grows with history. A copy of this repository's store holds 20,669 events with 859-byte payloads on average. Opening it takes about 505 ms, of which verification is about 504 ms; the rest of opening takes 1–4 ms. Every terminal hook pays that cost. Synthetic small-payload stores show the same growth: at 10,000 events, opening takes 68 ms and each report write 25 ms; at 30,000 events, 189 ms and 65 ms. Earlier work avoided reopening by reusing handles and keeping in-memory cursors with a 900-second full read. Those changes managed the symptom, not the cause.

The event schema already makes history append-only: the store assigns sequences inside serialized write transactions, and triggers reject updates and deletes. Event hashes are unkeyed, so they detect accidental damage and naive edits but not a deliberate rewrite of the whole chain.

## Decision

The store verifies the rows it returns and the predecessor of each append. Complete-history verification happens only when explicitly requested.

- **Reading.** Every returned event passes the row decoder, which checks the readable schema and recomputes the stored hash. Adjacent sequences in one `list` result must link. Project snapshot traversal (`visitEventSnapshot`, `collectProjectEventsBounded`) requires sequences from 1 without gaps and checks every predecessor link. A traversal may pin the observed head hash and must end exactly at it. A typed read (`list` with `types`, or `collectEventsOfTypesBounded`) verifies each returned row and its forward order but does not read the events between them. A reader whose answer depends only on certain event types uses a typed read; a reader that must prove a complete project snapshot uses a snapshot traversal.
- **Appending.** Before inserting, the store decodes the tail through the same hash check. It also confirms that the tail links to the event before it. A new event therefore extends only a locally consistent chain.
- **Opening and writing.** Opening checks only that the file is this project's store, in the expected format and report layout. Every write transaction repeats this binding check before it does any work.
- **Explicit verification.** `verifyIntegrity()` keeps the complete check: SQLite structure, foreign keys, the report layout, every outbox row and the whole chain from the first event. Diagnostics, inspection, migration and administrative commands keep calling it. Hot paths no longer call it before or after reading.

Consumers that receive events from outside the local store contract keep their own checks. These include Hub synchronization batches, remote projections and diagnostic trace reports.

## Consequences

A modified or corrupted row is rejected whenever it is read, linked or extended, as before. What changes is that damage to rows nobody uses is no longer found at the next open. It is found by the next explicit verification or the next read of that row. Such rows cannot affect any result until they are read. SQLite still reports structural corruption when it reads a damaged page.

Store opening and per-write verification no longer grow with history. On the same repository copy, opening falls from about 505 ms to 1.0–1.7 ms, for both writable and read-only stores. In the synthetic stores, per-write CPU stays at 1.1–1.4 ms from 1,000 to 30,000 events; at 10,000 and 30,000 events it was 21 and 62 ms.

Explicit verification costs the same as before. On the repository copy, alternating runs measured 573–990 ms for the previous algorithm and 597–626 ms for the new one. Reading every event now includes hash checks, so `list` over the full history rises from 117–178 ms to 306–346 ms. A complete traversal therefore costs more per row read, but it verifies the chain once instead of reading history three times. The earlier test that a tampered store fails to open is replaced by tests for each point of use: reading, extending a damaged tail, a valid row with a broken predecessor link, outbox reads and explicit verification.

[ADR-0554](0554-bound-what-a-reader-retains-never-history-length.md) removes history-length bounds: readers bound only what they retain.

## Amendment to the recording storage specification

This decision supersedes the automatic complete-history verification requirements in [Bounded context-quality recording storage reuse](../../../specifications/execution/context-quality/recording-storage-reuse.md). Its older descriptions remain evidence of the preceding implementation, not additional requirements for the point-of-use artifact. Where those descriptions conflict with this decision, the following interpretation governs:

| Specification location                                                          | Superseded requirement                                                                                                                          | Current requirement                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Ownership and bounds; legacy commit queue                                       | “Event identity lookup, complete integrity verification and every append in that batch share one synchronous SQLite transaction.”               | Keep identity lookup and appends in the synchronous transaction. Recheck the live project, format and report-layout binding before writes and verify the append predecessor at its point of use. Do not perform a complete-history scan merely because a batch is published.   |
| Prepared SQL report admission                                                   | “The adapter retains complete integrity verification”                                                                                           | Retain current binding checks, point-of-use event validation, atomic publication, expected report-hash comparison, strong synchronization and both complete report reads. Complete-history verification is explicit.                                                           |
| Current identity and integrity; bootstrap                                       | “including relocation, project binding and complete open-time integrity checks” and “the complete open-time integrity check follows its commit” | Retain relocation, filesystem guards, atomic initialization and project/format/report-layout binding. An ordinary open does not run complete-history verification. Explicit migration and administrative verification keep their full checks.                                  |
| Current identity and integrity; event transactions                              | “Every event transaction runs SQLite, outbox and event-chain integrity checks before append.”                                                   | Every write transaction checks the live store binding. Each append verifies its tail row and that row's predecessor link. Complete SQLite, outbox and chain verification remains available through `verifyIntegrity()`, rather than running automatically before every append. |
| Current identity and integrity; chain receipts                                  | “Chain verification still freshly reads every event row.”                                                                                       | This describes a complete verification or complete snapshot traversal, not ordinary opening, typed reads or every write. Typed reads verify returned rows and forward order without claiming coverage of omitted events.                                                       |
| Candidate SQLite report integration boundary; recording through the report port | Requirements for “full event integrity checks” and “complete event integrity” during publication                                                | Apply the current binding and point-of-use rules above. Report bytes still receive their complete checks; this decision does not replace report verification with partial reads.                                                                                               |
| Opt-in atomic report transaction                                                | “runs the existing complete integrity check inside `BEGIN IMMEDIATE` before callback writes”                                                    | Recheck the current project, format and report-layout binding inside the write transaction before callback writes. Verify append predecessors at use. A report transaction alone does not request a complete-history scan.                                                     |

The same substitution applies to the specification's general descriptions of complete transaction integrity. It does not remove writer activation, fresh filesystem and coordinate observations, report-selection fences, input validation, exact retry checks, transaction poisoning, rollback, strong synchronization or post-commit confirmation. Both complete report reads remain required for every accepted report call. An explicit full verification must still cover SQLite structure, foreign keys, report layout, every outbox row and the complete event chain.

Historical evidence records retain their original algorithms, artifact identities, rejected cohorts and measured outcomes. This amendment does not retroactively change their verification scope. It also does not establish that the current implementation satisfies the amended contract: the supplied assessment context omitted the underlying implementation record, and temporary receipts were not independently inspected.

The [installed qualification record](../../../evidence/quality/context-quality/installed-commit-allowance-qualification.md) reports lifecycle checks for the point-of-use artifact and separately reports loaded-host resource observations that do not qualify performance. Its two unresolved full-suite failures have no supplied comparative baseline establishing that they predate this work. Source verification, complete performance qualification, owner retention, power-loss behavior and other-platform acceptance must retain their separate evidence boundaries.
