# ADR-0502: Bind native assets to runtime distributions

Status: `accepted`
Decision date: 2026-10-10
Updated: 2026-10-11

## Context

The [context-quality implementation](../../evidence/quality/context-quality/context-quality-native-sync-implementation.md) uses optional Darwin synchronization and content-addressed storage (CAS) publication/readback adapters. Copying only JavaScript silently selects ordinary I/O. Native assets introduce architecture, source identity and inventory obligations that the JavaScript metafile cannot prove. Each distribution must bind the complete capability it declares.

## Build and artifact ownership

Filesystem-durability owns the universal synchronization addon; CAS owns the universal publication/readback addon. Each producer binds its C sources, build owner and shared contract/copy owners to a source digest. Binary identity binds the generated bytes. Both manifests use schema 1, API 1, Node-API 8, Darwin and arm64/x64 coordinates. Each binary is bounded to 1 MiB and its manifest to 4 KiB. Compilation stays in the build; ordinary execution and installation never compile or download code. These hashes detect drift, not independent authenticated provenance or hardware persistence.

The shared adapter checks regular non-linked entries, bounded sizes, exact manifest coordinates, source/content digests and actual universal Mach-O slice headers and bounds. Pair-specific readers retain their existing contracts. An aggregate reader accepts the legacy synchronization pair or the complete four-file set: `cas-io-darwin.node`, `cas-io.json`, `file-sync-darwin.node` and `file-sync.json`. Current application writers require both source-bound pairs. They publish captured verified buffers together without reopening admitted sources. A changed receipt digest fails before replacement.

Replacement stages the complete set before moving the previous directory. Publication failure restores the predecessor; failed rollback retains the single fixed recovery stage and stops another attempt. Foreign destination entries are never removed. A pair-specific writer rejects a four-file destination. CAS production and aggregate bundle copying also reject a retained native-transfer stage, even when existing pair source hashes match. This prevents a later build from accepting a partially restored pair set. These are build-output replacement contracts, not live-service transactions or power-loss guarantees.

## Application archives and SBOMs

CLI, Hub and Node bundle builds copy both pairs beside their JavaScript entrypoints. CLI npm archives carry the universal files on every platform, alongside three JavaScript executables, README and package metadata. The original native-only schema-7 archive contains nine files; schemas 5 and 6 retain their original inventories. Current internal-runtime inventory additions are specified below. Software bill of materials (SBOM) generator version 3 binds all four native digests and dependency edges. Schema-6 generation retains version 2, and schema 5 retains version 1. Built and packed consumer verification compares installed native bytes with the source-bound build before executing native probes.

Darwin standalone Hub and Node archives require all four native files. Other target archives omit them and retain ordinary I/O. Under native capability schema 3, Darwin requires the complete regular-file inventory and other platforms reject declared native entries. Readers retain schemas 1 and 2, including the older synchronization capability. The archive sidecar retains schema 1 because its identity contract is unchanged.

Archive verification first checks outer identity and exact extracted inventory, then native manifest/binary identity and each SBOM component and dependency edge. On the matching platform, requested smoke verification executes both adapters in child processes against synthetic temporary files. Synchronization can report its existing ordinary fallback for ineligible filesystems; CAS publication/readback must execute its native contract. Cross-host JavaScript smoke cannot prove target-native execution. Native failure after admission still rejects. No check weakens synchronization, SQLite FULL, fresh identities, complete hashing or event integrity.

Windows archive verification decodes native tar line endings before path checks. POSIX carriage returns remain untrusted path bytes. POSIX extraction compares every permission bit; Windows compares the observable read-only attribute because Node does not expose POSIX execution or owner/group distinctions there. Authenticated archive and manifest bytes retain the original modes. Names, types, sizes, hashes, links and inventory membership match exactly. This does not certify Windows ACLs or replace owner-only runtime configuration checks.

## Complete internal runtime identity

CLI release schema 9 and standalone Node schema 5 add one bounded runtime inventory at `dist/repository-runtime.json`; their readers retain earlier schemas. Runtime-security owns regular-file capture and pure inventory validation, build tooling owns emitted output membership, and application composition owns installation. The manifest requires schema version 1, the `repository-runtime.js` entry and sorted unique file records containing `name`, `size` and `sha256`. Only that entry and private flat `repository-runtime-*.js` or `.cjs` files are allowed; names must also be unique without case distinctions. There are at most 128 code files, the manifest is at most 64 KiB, and the entire set is at most 64 MiB.

The manifest digest binds every code digest. CLI SBOM generator version 5 and Node generation bind this inventory as one runtime component, separate from native assets. Archive validation compares exact expanded membership and canonical manifest bytes; package globs cannot admit additional files. Build metadata must resolve every emitted dependency within the graph or the existing built-in/external package boundary. A loader-only hash cannot establish the shared implementation identity.

Publication uses privately captured buffers, checks existing members before creating missing files and publishes the manifest last. Missing members can be repaired after interruption; conflicting bytes, links and foreign namespace members survive and stop publication. The installed launcher content address includes the inventory digest. This is not an atomic live replacement or a power-loss guarantee. Current CLI and Node builds generate twelve canonical validators alongside the complete 209-schema map and include a private synchronous CJS fallback in both internal runtime inventories. The [actual build-owner selected-validation record](../../roadmap/natural-language-grounding-quality/context-quality-parity.md) establishes this loading boundary; it does not establish adoption of the experimental five-backend cached runtime, performance qualification or production deployment.

No event or repository collection is added. Public names, sizes and digests are the only manifest content. `runtime_module_manifest_invalid`, `runtime_module_inventory_invalid` and `runtime_module_size_limit` reject malformed or out-of-bound artifacts. File, directory, content, digest and publication errors reject redirected, changed or conflicting observations. The CLI maps publication rejection to `node_fleet_executable_invalid`. Existing native identities and failure meanings remain unchanged.

## Same-workflow transfer

Each full Code quality or CLI release matrix run has one macOS `native-runtime` producer. It compiles both addons and creates a schema-2 `lervo_native_runtime_transfer` receipt. Required fields are `schemaVersion`, `kind`, `revision`, `workflow`, `runId`, `runAttempt`, `syncSourceHash`, `casSourceHash` and `artifactDigest`. The combined digest binds the exact four captured files, including manifest representation. Consumers accept only their own revision, workflow and run, and the same or an earlier producer attempt. Both source hashes and the complete digest must match before package output replacement. The existing schema-1 synchronization transfer command remains available for legacy callers; current workflows require the complete schema-2 transfer.

Restore prepares both package outputs from the admitted private buffers. If the second publication fails, it rolls back both outputs. A failed rollback preserves predecessors in their original locations or the fixed CAS `dist/.native-runtime-transfer` stage. An interrupted or failed restore blocks later restore, CAS build and aggregate bundle-copy attempts until recovery is resolved. No per-attempt recovery directory is added. Existing pair-copy recovery stages and foreign entries also block replacement.

Repository LF policy keeps source identity platform-independent. Transfer artifacts expire after three days and contain only four public build files and their bounded receipt. Same-workflow identity is drift detection, not authenticated independent provenance. Each fresh workflow rebuilds its producer; exact manifest checks must reject different toolchain output. Hosted execution and cross-workflow reproducibility remain acceptance requirements, not assumptions.

## Terminal hooks and rollout

Repository-installed hooks materialize the complete set under `.lervo/generated/terminal-hooks/native/`. The runtime integrity manifest uses schema 3 for four assets, schema 2 for the legacy synchronization pair and schema 1 without native capability. The existing `runtime-v2.json` path and provider hook contract remain unchanged; integrity schema and provider contract are separate coordinates. Each asset binding contains its fixed path, byte count and SHA-256 hash. Installation checks both native manifests and content hashes without executing them; the release artifact owner retains Mach-O and source-build qualification.

Plans bind desired assets, previous hashes and the previous outer-manifest hash. A binary-only change therefore changes the exact plan even if JavaScript is unchanged. The durable materialization owner snapshots raw payloads, stages and synchronizes them, and uses its existing hash-bound journal to restore prior bytes before event commitment. Recovery consults canonical application events before choosing rollback or committed cleanup. Downgrading to a plan that omits installed CAS assets returns a `runtime_invalid` blocker rather than retaining undeclared files. Provider settings retain their existing exact-approval boundary.

Startup validates the complete runtime before reading provider input and rejects linked, missing, changed or undeclared native files. Current readers also accept integrity schemas 1 and 2; older readers reject schema 3. Upgrade readers first and retain the complete predecessor artifact for rollback. Installation adds four replace-in-place files, with no per-update history. The public CLI remains the sole product release version. Source, build, copy, inventory, SBOM and transfer changes require reviewed release intent. This decision itself grants no tag, publication, remote installation or writer-activation authority.

## Evidence, privacy and failure meaning

No event schema is added. Manifests, receipts and SBOMs contain public build coordinates and digests, never requests, repository bodies, credentials or provider output. Probes remove their owned synthetic files. Ordinary staging failure cleans its stage; failed rollback or interruption retains one fixed recovery location.

`native_runtime_*` errors reject incomplete inventories, source/content drift, invalid SBOMs, unsafe paths and pending recovery. `native_transfer_*` errors reject receipt/run/source/digest mismatches and distinguish pending recovery or rollback failure. Pair-specific `native_file_sync_*` and `native_cas_*` errors retain their meanings. `release_native_consumer_changed` rejects installed bytes that differ from the verified build. Terminal installation retains `knowledge_source_unsafe`, `knowledge_plan_stale` and durable recovery errors; runtime integrity failure exits 2 before hook input. `terminal.integration.applied` retains its fields: `runtimeAfterHash` describes JavaScript, while `planId` binds the complete transition.

Completion requires adversarial artifact, transfer and archive tests; exact binary execution on supported targets; full installed consumer checks; hosted reproducibility; and the unchanged source and distributed resource gates. [Source verification](../../evidence/quality/context-quality/context-quality-source-verification.md#native-cas-runtime-composition) records the current candidate and limits. A successful build or smoke is not a release or deployment receipt.

[ADR-0539](../execution/providers/hooks/0539-keep-the-terminal-hook-runtime-host-local-behind-a-tracked-launcher.md) materializes native assets in the host-local runtime store instead of `.lervo/generated/terminal-hooks/native/`. The asset bindings and integrity checks are unchanged.
