# ADR-0502: Bind native sync assets to standalone runtime distributions

Status: `accepted`
Decision date: 2026-10-10

## Context

The [context-quality implementation](../../evidence/quality/context-quality/context-quality-native-sync-implementation.md) uses an optional Darwin file synchronization adapter. Copying only the bundled JavaScript silently selects ordinary synchronization, so source performance evidence does not establish distributed behavior. Native files also introduce architecture, source identity and inventory obligations that the JavaScript bundle metafile cannot prove.

## Decision

The filesystem-durability build owns one universal Darwin addon and its bounded manifest. Compilation stays in the build; neither ordinary execution nor installation compiles or downloads code. Source identity binds the C sources, build owner and artifact contract/copy owners. Binary identity binds the exact generated bytes. These digests detect drift, not independent build provenance or hardware persistence certification.

A shared distribution adapter checks the exact two-file set, regular non-linked entries, bounded sizes, manifest/API/Node-API coordinates, source digest and binary digest. It independently inspects the actual arm64/x86_64 Mach-O slice headers and bounds. Unsupported or malformed declared assets cannot masquerade as a complete copy. It stages a verified pair before replacing the owned output directory, restores the prior directory on publication failure and retains the recovery copy if rollback also fails. Foreign destination entries are never removed. This is a build-output replacement contract, not live-service atomic upgrade or power-loss durability.

Hub and Node bundle builds copy the exact assets beside their JavaScript entrypoint. Darwin standalone builders require the source-bound pair and include it in the archive inventory. Other platform archives retain ordinary synchronization and omit the Darwin pair. The new standalone manifest schema is version 2: Darwin requires both regular native files, while partial or unexpected native inventories fail on every platform. Current readers still accept version 1 archives without the capability. The artifact sidecar retains version 1 because its archive identity contract is unchanged.

The SBOM includes each native file and manifest digest as a file component, with explicit dependency edges from the application. Archive verification rechecks native content and SBOM binding after the existing exact archive, inventory and manifest checks. A requested smoke on the matching platform executes the adapter in a child process against owned temporary files; filesystem ineligibility verifies ordinary synchronization fallback. Cross-host JavaScript smoke cannot prove native execution on the target.

The existing runtime fallback remains valid for unsupported hosts and filesystems. Native failure after admission still rejects; no archive check weakens fsync, SQLite FULL, fresh identity observations or event integrity. This decision changes distribution ownership and verification, not CAS format, event schema or production writer authority.

Archive verification decodes native Windows tar line endings before applying the existing path checks. POSIX carriage returns remain untrusted path bytes. After extraction, POSIX hosts compare every permission bit; Windows compares the observable read-only attribute because its Node filesystem API does not expose POSIX execution or owner/group distinctions. The authenticated archive and manifest retain their complete original modes. File names, types, sizes, hashes, link targets and inventory membership still match exactly on every platform. This comparison does not certify Windows ACLs or replace owner-only runtime configuration checks.

## Compatibility and rollout

Version 2 archives require the updated verifier/installer. Upgrade readers first; do not use an old installer rejection as permission to bypass verification. Existing version 1 archives remain readable by the new tools. The current product release version still comes solely from `@lervo/cli`, with reviewed release intent.

CLI npm archives carry the same universal Darwin pair on every platform, alongside the three JavaScript executables, README and package metadata. Release manifest writers use schema 6 with exactly seven archive files; readers retain schema-5 compatibility. The SBOM generator version 2 adds both native file digests and root dependency edges; schema-5 inventory retains generator version 1. Current packed and built consumer verification compares extracted native bytes with the source-bound build before any requested native probe. Installation never compiles the addon.

Each full Code quality or CLI release matrix run has one macOS native producer. A bounded version-1 transfer receipt binds `kind`, source revision, workflow, run ID, producer attempt, source digest and pair digest. Consumers accept only their own revision/workflow/run and the same or an earlier producer attempt, validate all coordinates and content before replacement, and reuse those exact bytes even on macOS. Repository LF checkout policy keeps source identity platform-independent. Transfer artifacts expire after three days; they contain only the two public build assets and receipt. This is same-workflow drift detection, not independent authenticated provenance. Release preparation runs on macOS so the existing generated-file owners can build the addon. Each fresh workflow still rebuilds its producer: exact manifest checks must reject different toolchain output, and cross-workflow reproducibility remains an acceptance requirement rather than an assumption.

Repository-installed terminal hooks also materialize the pair under `.lervo/generated/terminal-hooks/native/`. The runtime integrity manifest uses schema 2 when assets are present: `assets` contains exactly the two fixed relative paths, byte counts and SHA-256 hashes. The native binary is bounded to 1 MiB and its manifest to 4 KiB. Installation checks the native manifest/API/Node-API coordinates and binary digest without executing it; the release artifact owner retains Mach-O and source-build qualification. The outer manifest binds both files, including the native manifest source coordinate.

Generated runtime plans bind desired asset coordinates, observed previous hashes and the previous outer-manifest hash. Binary-only changes therefore change the exact plan even if JavaScript is unchanged. The existing durable materialization owner snapshots binary payloads, stages and synchronizes raw bytes, uses the unchanged hash-bound journal and restores all prior bytes on pre-event failure. It recognizes terminal plan IDs; CLI recovery scans canonical semantic and terminal application events across pages before deciding rollback versus committed cleanup. Provider settings retain their existing exact-approval boundary.

Startup validates the complete runtime before reading provider input, including rejecting linked, missing, changed or undeclared native files. Schema-1 runtimes without native assets remain readable; a legacy plan cannot silently retain an undeclared pair. Old schema-1-only runtime readers reject schema 2, so deploy readers first and retain the complete prior runtime for rollback. Installation adds exactly two replace-in-place generated files and no per-update history. This decision does not authorize a tag, publication, remote installation or service activation.

## Evidence, privacy and failure meaning

No event schema is added. The terminal runtime integrity manifest advances to schema 2 and the existing bounded generated directory gains the two native files. Manifests and SBOMs contain public build coordinates and digests, never requests, repository bodies, credentials or provider output. Temporary native probes use synthetic content and remove their owned files. Build staging is removed on success or successful rollback; failed rollback retains the single recovery directory for inspection.

Transfer `native_transfer_*` failures reject malformed receipts, source/run drift or pair digest mismatch before destination replacement. `release_native_consumer_changed` rejects an installed pair that differs from the verified build. Internal `native_file_sync_*` failures distinguish missing assets, invalid source/binary/inventory/SBOM, unsafe paths, rollback failure and smoke failure. Terminal installation uses existing `knowledge_source_unsafe`, `knowledge_plan_stale` and durable recovery failures; a failed integrity check exits 2 before hook input. `terminal.integration.applied` retains its fields: `runtimeAfterHash` still describes JavaScript only, while `planId` binds the complete transition. Existing distribution command boundaries continue to emit their bounded build/verification failure codes. A failed build or smoke is not a release receipt.

Completion requires adversarial artifact and archive tests, exact binary execution on supported targets, full standalone consumer smokes and the remaining CLI/terminal/CI integration. Local header checks do not prove x86_64 or minimum-Node execution, and source-only resource results do not qualify distributed performance.

Native build/copy staging uses one fixed owned directory per output. Exclusive directory creation prevents a second copy from replacing an active or retained recovery stage. Ordinary failure cleans its owned stage; rollback failure or process interruption retains it and stops later attempts until recovery is resolved. Repeated attempts therefore cannot accumulate recovery directories.
