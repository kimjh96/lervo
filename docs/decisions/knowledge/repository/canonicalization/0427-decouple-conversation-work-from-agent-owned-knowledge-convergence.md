# ADR-0427: Decouple conversation work from agent-owned knowledge convergence

Status: accepted
Decision date: 2026-09-23

## Context

Native conversation repository work currently checks global managed-knowledge currency before provider execution and again before publishing its result. The post-turn check permits `baseline_valid` when unrelated debt predates the turn. Consequently a slow or stale global projection delays a live conversation, while `baseline_valid` can remain indefinitely without an owner or a due reconciliation. A one-time operator refresh does not satisfy autonomous canonicalization and knowledge maintenance.

The provider result, repository checkpoint, canonical-source assessment, structural projection, and visible reply are different outcomes. Treating their checks as one synchronous completion gate delays replies and hides old knowledge debt. Removing the gate without a durable owner would make that debt less visible, not solve it.

## Decision

### Separate truthful outcomes

The live turn retains admission, repository observation, result CAS, exact workstream checkpoint, configured replica readiness, and one canonical repository-work completion before publication. It does not run global knowledge assertion, migration, normalization, or refresh before starting a provider or publishing its verified work result. Changed-source completion records knowledge as `pending_background`, not `current` or `baseline_valid`; its visible result must not claim knowledge convergence while that state is pending. An unchanged repository turn records `not_applicable` without a new source-bound knowledge job. That value means only that the turn changed no repository source, not that global knowledge is current; pre-existing debt remains in the separately owned baseline queue.

The completion event itself is the durable knowledge-job source. A background reconciler reads bounded pages of that canonical chain and idempotently enqueues eligible completions into a local knowledge-job outbox, following the destination-reconciliation boundary of ADR-0194. A completed event cannot be lost between a live event append and a second live-path queue write because there is no second live-path write. If the completion append fails, native work remains effect-uncertain and no success reply is published. Exact source-event identity and result hash deduplicate replay; a replay never reexecutes provider work or creates a second job. The local event chain is canonical and requires no Hub. Outbox, cursor, and search projections are rebuildable from canonical events.

### Source-bound agent work

A job binds the completion event, source conversation event, durable agent, provider-neutral role and assignment, before/after repository revisions, an exact changed-path source-coordinate manifest, workstream snapshot, and result digest. Each coordinate is either a Git tree and relative path, an observed dirty-path digest, or an observed deletion; the worker must recheck it before claiming content currency. A bound after-path whose bytes have changed is `stale`. A pre-turn dirty-path digest whose former bytes are no longer reconstructable is `needs_review`, never `current`; a digest alone cannot establish the semantic change. The manifest is bounded, local, and content-addressed; it contains no request text, provider output, source bytes, or credentials. A path count beyond its bound is a typed failure, never a silently truncated success. A preexisting `baseline_valid` completion becomes an explicit migration debt item without rewriting its historical event or inventing an original path manifest.

The background owner claims one leased job, reads applicable canonical instructions, and reviews the exact source change through a separate agent assignment in an isolated workspace. It classifies whether a durable fact or behavioral obligation needs a canonical target; an implementation-only outcome requires a source-bound rationale. Canonicalization uses the existing typed responsibility and candidate lifecycle. An agent may write an authorized canonical source through the ordinary scoped repository-change and integration contract. A conflict with user-owned content becomes an exact review candidate; the worker never silently overwrites it. A projection refresh alone never closes an unreviewed canonicalization obligation.

For read-only semantic review, the isolated workspace is the existing provider-neutral no-capability process boundary: Codex and Claude run in a fresh private temporary directory with model tools and session persistence disabled. Exact source bytes are passed through stdin only. This is not an ordinary writable Git worktree; the separate narrow write assignment uses the normal workspace and integration lifecycle only after a canonical target is identified.

The first knowledge-job assignment is explicitly read-only: its expected paths bound source access but take no exclusive write-path lease, so a live writer may proceed while semantic review runs. A read-only assignment cannot authorize managed repository writes or activate an ordinary writer workspace. Once the review identifies a canonical target, any proposed edit requires a separate narrow write assignment and the normal workspace/integration contract. A legacy assignment without an access-mode field keeps write-lease semantics; absence never silently becomes read-only. A review workspace must remain isolated and non-writable before background activation.

The no-capability reviewer satisfies that isolation without adding a fake writer state to the durable Git-workspace lifecycle. Its temporary directory contains no repository source bytes, and its provider invocation has no filesystem tool capability.

Before integration, the owner rechecks source hashes, assignment lease, canonical target ownership, and current target revision. Stale evidence reopens or supersedes the item with an explicit state; it cannot be marked current by repetition or provider agreement. After reviewed source integration, migration, refresh, and lint establish the knowledge result. The live conversation does not wait for this sequence. A separate status or follow-up message may report completion only after that message has its own delivery receipt.

### Recovery, capacity, and failure meaning

The worker leases and retries transient failures with bounded backoff and an attempt ceiling. Restart reclaims an expired lease and resumes from the last canonical outcome; it inspects uncertain repository effects before any retry. Exact completed jobs are idempotent. Observed source drift enters `stale`; a permanent authority conflict, source limit, or exhausted attempt enters visible `attention_required` with an owner and reason, not a perpetual pending state. Queue reconciliation has an explicit capacity bound: a full local queue stops projection, leaves the canonical completion discoverable, and reports backpressure without falsely marking the job processed. A cheap admission check prevents unlimited new pending work; it never runs global knowledge compilation. Acknowledged queue entries are purged under bounded retention after their canonical outcome remains inspectable.

The outcome append and queue acknowledgement share one exact-lease event-store transaction. A non-success writer may record `stale` only from observed source drift or `attention_required` from a bounded failure, after checking the separate background-agent assignment. A recovery queue claim after the sixteenth work attempt may record `knowledge_retry_exhausted` without running a seventeenth semantic attempt; the bounded event count remains 16 even if the operational lease count is higher. Neither an expired lease nor an event append failure may consume a job without a durable resolution. The same atomic boundary must apply to the later verified `current` producer.

The new outcome event is `conversation.repository_knowledge.resolved`. Its required fields are completion event ID/hash, source event ID, job ID, agent ID, source-manifest hash or legacy-unavailable marker, terminal state (`current`, `pending_review`, `stale`, or `attention_required`), attempt count, bounded failure code or null, knowledge snapshot hash when current, and occurred-at time. It contains no message body, provider output, source bytes, local absolute path, credential, or raw failure text. `current` means both source-bound canonicalization and knowledge lifecycle passed for the bound source; `pending_review` is not success; `stale` requires fresh source evidence; `attention_required` names a bounded nonretryable or exhausted failure. A retry/lease is operational state, not a claim that knowledge is current.

The worker's read-only source preflight returns `ready_for_review`, `stale`, or `needs_review`; none is a knowledge-success claim. `ready_for_review` means the content-bound artifact matches the completion, current after-path bytes still match their Git-tree or working-tree coordinates, and before-path evidence is reconstructable. `stale` means the after-path changed. `needs_review` means pre-turn dirty bytes, unsafe parent resolution, or an unavailable Git/object observation prevents exact review. Its bounded reasons are `source_bytes_changed`, `before_bytes_unavailable`, `unsafe_path_resolution`, and `source_evidence_unavailable`; they include no path or source body. A missing manifest artifact yields `knowledge_job_source_unavailable`, and a malformed, over-bound, or mismatched artifact yields `knowledge_job_source_invalid`. Neither failure may be promoted to `current` by retry or refresh alone.

Before semantic review, an exact leased source capture reads pinned Git blobs and current dirty after-path bytes into process memory with a combined 16 MiB ceiling. It verifies the dirty digest and source currency again after capture, then rechecks the exact outbox lease. Captured bytes are private inputs, not event fields, CAS artifacts, or workspace files. A changed source remains `stale`; unsupported source kinds become `needs_review` with `review_source_kind_unsupported`; exceeding the combined byte ceiling raises the bounded `review_source_limit_exceeded` failure. None of these outcomes claims semantic review or knowledge currency. The review assignment and physically isolated read-only workspace must still be verified before a provider receives these bytes.

The no-capability semantic review accepts only exact UTF-8 source and content-hash-matched canonical context, with a separate 256 KiB provider-input ceiling and no truncation. It rejects binary text as `review_source_encoding_unsupported`, invalid context as `review_context_invalid`, an untrusted provider boundary as `review_provider_boundary_invalid`, malformed model output as `review_provider_response_invalid`, and missing usage as `review_usage_unavailable`. A canonical instruction document changing before or during the call yields private `needs_review/review_context_stale`; changed source remains `stale`. The outbox and agent assignment leases are rechecked around the call. Its bounded `implementation_only`, `canonical_change_candidate`, or `needs_review` result is a private candidate, not a canonical event, write authorization, human approval, or knowledge-current outcome. Source and context text are omitted from public status and telemetry; a later durable resolution must carry only the specified bounded coordinates.

The context loader discovers the applicable `AGENTS.md` hierarchy and loads it as required instruction evidence. It obtains bounded canonical-document recommendations with the product's default repository ranker, prioritizes recommendations sharing source-path terms within that bounded set, then reads their exact repository bytes and verifies each recommendation hash. This path affinity selects context, never grants authority. A stale concept sidecar does not by itself invalidate current canonical Markdown; the byte check decides whether the selected source is still exact. Recommendation is not loading, injection, or use; only the resulting read-and-hashed documents are loaded, and the provider call is the separate injection boundary. Retrieval is bounded, not exhaustive, so the reviewer must return `needs_review` when missing context prevents a reliable classification. A missing or unreadable required instruction or selected document yields private `needs_review/review_context_unavailable`; more applicable instructions than the eight-document input bound yields `needs_review/review_context_limit_exceeded`; a selected recommendation whose bytes changed yields `needs_review/review_context_stale`. These reason codes carry no source body, query text, path, or credentials and never mean knowledge is current. The owner rechecks both leases and source currency after context loading, before disclosing source bytes to the provider.

The old `current` and `baseline_valid` values retain their historical meaning for readers. New changed-source writers use `pending_background` with a required content-bound manifest; unchanged-source writers use `not_applicable` with zero changed paths and no manifest. Neither state claims knowledge currency. Migration opens explicit debt for old `baseline_valid` events and never retroactively upgrades them. Readers reject unknown writer versions until compatible. `verificationStatus: passed` on a repository-work completion proves the native work/result/checkpoint/replica boundary only; it does not prove background knowledge completion.

## Consequences and acceptance

This changes the synchronous guarantee recorded in ADR-0395 and the installed Discord scope; those documents must identify the new boundary when the writer activates. The async worker must not share a writable checkout or provider session with a live conversation turn. Its CPU/provider concurrency and queue depth are bounded independently of live ingress.

Acceptance requires a real installed conversation journey and common provider-adapter contract tests. Prove that a changed-source turn publishes promptly while knowledge is pending; the worker subsequently writes or reviews the right canonical target, refreshes and lints, and records one current outcome. Prove no lost job between completion and enqueue, restart/idempotency, retry exhaustion, stale source, user-owned conflict, legacy `baseline_valid` migration, path/privacy bounds, queue backpressure, no-Hub operation, and measured live-path latency with the worker busy. A healthy Node, a queued event, or a one-time manual refresh proves none of these alone.
