# Foundation delivery sequence and handoff

## Phase A: freeze meanings, not implementations

Inventory existing IDs, events, commands, ports, projections, and failure codes. Publish the causal work envelope, ownership map, compatibility policy, and telemetry vocabulary. Do not add persistent product entities until G0 and the contract-definition portion of G1 pass.

## Phase B: instrument current vertical paths

Add the resource ledger and stage spans to existing managed runs and direct hooks. Build read-only request-usage and performance projections, capture representative baselines, and freeze reviewed budgets. Improve visibility without adding autonomous effects or monetary hard stops.

## Phase C: prove adverse behavior

Run crash, retry, cancellation, duplicate, concurrency, capacity, security, upgrade, and rollback suites against current paths. Close semantic gaps before a loop can repeat them automatically. G2 through the core of G5 should pass here.

## Phase D: foundation readiness and handoff

Aggregate contract, replay, performance, recovery, security, capacity, packed-CLI, fresh-clone, and local-without-Hub evidence. Review exact limitations and rollback before declaring readiness. Phases A–D correspond to FH0–FH5 in the implementation roadmap.

## Phase E: first enhancement slice

Extend the current assignment DAG with one versioned bounded flow:

```text
trigger -> checkpoint -> attempt -> observe -> verify
        -> complete | bounded retry | block | escalate
```

Reuse existing IDs, events, leases, verification, recovery, and public contracts. Prove a parallel branch, join, approval gate, cancellation, exhausted budget, and crash recovery. Keep the graph rebuildable or declarative; observed state and completion remain canonical elsewhere.

## Phase F: reference products and verified improvement

Build a minimal local operating client over the same public boundary. Add bounded Paperclip-like goals, routines, boards, and budgets, plus Buzz-like threads, mentions, inboxes, and connectors, as product projections and commands. Complete post-promotion effect observation for verified improvement. Presentation membership, message delivery, model confidence, and remembered approval must not grant authority.

## Phase G: advanced and external capabilities

Only after measured need, consider dynamic graphs, unattended autonomy, external graph or semantic services, more provider and harness adapters, and third-party host products. Each must enter through versioned ports, conformance tests, reviewed activation, rollback, supersession, and migration.

## Go and no-go rule

The first durable loop or execution-graph enhancement may proceed only after the bounded foundation roadmap and G0–G5 are accepted. Later product features may use narrower gates once that foundation exists.

Durable loop or graph expansion is prohibited when:

- there is no common causal work root or retry identity;
- there is no public version and historical-reader policy;
- resource data lacks typed distinctions among observed, partial, unavailable, estimated, and billed states;
- a critical path near an external timeout lacks stage visibility;
- an effect can be retried after uncertainty without reconciliation;
- an extension can implicitly add authority, network, filesystem, or unbounded work; or
- crash recovery can produce both a success event and conflicting repository state.

## First recommended implementation scope

The first implementation roadmap contains only:

1. the causal work-envelope contract and event compatibility policy;
2. provider-neutral usage aggregation and stage timing for existing paths;
3. read-only usage, latency, and missing-telemetry inspection;
4. focused hook-latency diagnosis and a safe budget;
5. common failure-injection and historical-replay harnesses; and
6. one aggregate foundation-readiness audit and enhancement handoff.

The governed-loop and assignment-graph vertical slice is the first subsequent enhancement. Cost estimation, budget warnings, reference operating views, and collaboration routes may follow as consumers. Billing reconciliation, hard monetary stops, dynamic graph mutation, and unattended autonomy remain later scopes.

## Completion evidence

Record exact contract and implementation versions, test and evaluation suite hashes, environment profiles, measured percentiles, resource completeness, injected failures, recovery outcomes, historical fixtures, security findings, remaining unsupported states, and rollback evidence. A green repository check alone does not prove a foundation gate.
