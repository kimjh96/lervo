# Lervo strengths and safety boundaries

## Strengths to preserve

### Evidence meaning

Keep context recommendation, loading, injection, output reference, and internal use distinct. Activity convenience must not weaken Lervo's evidence language.

### Repository conflict prevention

Single-assignee issue checkout does not replace repository-path overlap checks. Different tasks may target the same file; assignment paths and lease generations remain authoritative.

### Repository knowledge lifecycle

Keep Markdown, repository state, skills, verification, and execution events canonical. Graphs, lexical indexes, embeddings, dashboards, and task maps remain rebuildable projections. See the [repository knowledge specification](../../specs/repository-knowledge-compilation.md).

### Capability exactness

Preserve immutable package coordinates, exact dependency graphs, provider and platform compatibility, role permissions, and distinct resolved, loaded, activated, invoked, and completed states.

### Local-first authority and recovery

An operating dashboard, routine scheduler, or optional Hub must not replace project policy or canonical repository state. Do not automatically retry uncertain external effects.

## Unsafe direct copies

- Do not make a Paperclip-style company database canonical repository truth.
- Do not replace path-scoped leases with issue checkout.
- Do not equate heartbeat completion, stdout, or an agent's `done` report with managed execution, context evidence, or repository verification.
- Do not mix activity-feed events with semantic evidence or approval records.
- Do not retry uncertain external effects without an idempotent, failure-specific contract.
- Do not adopt opt-out remote telemetry as a local-first default.
- Do not force company, CEO, or board vocabulary into the neutral repository core.
- Do not copy large implementation modules directly; adapt concepts to Lervo's responsibility and dependency boundaries.
