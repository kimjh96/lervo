# Implementation status

The controller and provider-neutral composition are implemented and tested within the [delivery entrypoint](../delivery.md) boundary. Source APIs and fixtures prove neither production activation nor delivery-stage completion.

- [Implemented scope](status/implemented-scope.md): evaluation, storage, authority, recovery, and planning.
- [Dispatch and completion evidence](status/dispatch-and-completion.md): managed and native execution, recovery, acceptance, publication, and startup fixtures, including [exact artifact reviews](../../../../../specifications/execution/outcome-supervision/implementation/managed-execution/artifact-review.md).
- [Readiness and preflight](status/readiness.md): implemented checks and remaining step 2 work.
- [Installed observations and remaining work](status/installed-observations.md): semantic ingress, intake, recovery, equivalence, restart, amendments, activation, and standing supervision.
- [Research and deployment history](status/research-and-deployment-history.md): successor publication, WSL boot repair, mandate authority, reviews, and accepted outcomes.

## Completion boundary

Steps 1–6 contain implemented, tested, and deployed behavior; they are not six unimplemented tasks. The final full suite passed 3,467 tests with zero failures. Approved Discord owner turns executed bounded contract verification covering corrected hiring, amendment, permission, recovery, cancellation, idle, and publication cases.

The common completion gate remains full positive installed supervision acceptance and production activation. Grouped fixture requests cannot replace thirteen separate installed intake journeys. API, fixture, build, command-registration, staged-bundle, or message-delivery success alone cannot establish stage completion.

An operationally ready Node with `supervision: dormant` is not positive supervised-goal acceptance. The [installed canary correction](../../../host-products/discord/multi-party-conversation/installed-scope.md#2026-09-19-dormant-canary-readiness-correction) makes an unrelated current workstream visible without changing this completion gate or clearing its held review approval.

[ADR-0423](../../../../../decisions/execution/orchestration/governed-work/workstream-concurrency/0423-parallel-bound-workstreams.md) defines the same-project, same-agent parallel boundary. Local and WSL tests cover reading and authorizing Elio's bound goal while the independent review is selected, starting and restart-recovering a standing successor without replacing that review or its approval, completing an unselected supervised goal, and retaining the selected replication chain after an unrelated bound event. The [installed canary](../../../host-products/discord/multi-party-conversation/installed-bound-canary.md) now runs that code with Elio's existing bot and durable agent binding while the review approval remains held. The existing Hub protocol still replicates only the selected head; cross-host writing of the unselected branch is not an accepted capability. A fresh human-authored Elio successor turn and the review's exact two-direction evidence gate are still required before claiming this work complete.

Installed evidence now verifies guild `/goal` intake, delivered-result receipts, permission recovery with resumed execution, central/direct intake, a second recipient, restart points, requirement changes on expired and live leases, typed intake refusals, and boot activation. Historical `/goal` evidence does not prove ADR-0410's new semantic ingress.

Preserve existing artifacts, reviews, event history, and usage. Do not count the locally admitted v17 installation as reviewed authority. Use the [current per-scenario evidence](../../../../../evidence/foundation/outcome-supervision-local-and-wsl/deployment-and-upgrades/approved-discord-acceptance.md) to assess remaining acceptance work.
