# Multi-team agent organization

Part of [Paperclip-, Buzz-, loop-, graph-, and host-product outcomes](../host-products.md).

State: `delivery required`.

## Outcome

One human owner operates a Lervo organization with central leadership and multiple repository-backed project teams. Each hired expert agent retains a durable unique name and identity, exact role history, provider-neutral context, one-to-one external speaker identity, explicit channel membership, and scoped authority. Discord speakers may use bot users or webhook sets over a shared Gateway. One named central agent appointed to the CEO responsibility coordinates teams and performs reviewed organization and Discord administration within policy.

## Current foundations

Implemented foundations include:

- Workforce identity, roles, assignments, handoffs, workstreams, and approvals.
- Bounded scheduling and graphs, provider-neutral deliberation, and bot- or webhook-backed Discord deployments.
- Exact agent and role hashes in conversation records, agent-bound managed read-run causality, and bounded agent-specific recent conversation input.
- Repository-local append-only contracts for teams, agent membership, external deployment, channel membership, and deliberation participation.
- Exact-summary-reviewed agent-context promotion, deterministic subject conflict handling, explicit successor handoff, verified-work accumulation, and bounded relevance/freshness/sensitivity-filtered Node injection.
- A read-only multi-repository organization operating report, explicit central/project team-kind revision, distinct agent display identity, conservative built-in CEO role, and fail-closed executive policy evaluator.
- Product-host v7 organization-inspection routes and an installed exact-effect execution boundary with durable replay-safe Discord channel and thread adapters.
- Bounded authoritative reconciliation of uncertain managed deliberations with managed user-visible completion or attention signals.

The CLI can bind current hired agents and Discord deployments. An organization-configured Node fails closed on identity mismatch. These foundations do not complete the outcome.

## Completion criteria

The [outcome supervision roadmap](../execution/outcome-supervision.md) additionally requires goal-to-artifact execution, autonomous owner-defined worker responsibilities, and central escalation without repeated user dispatch or recovery prompts. This remains `delivery required`.

1. Bind one central repository and the Shiflo, Plen, and Arac repository teams. Run the implemented multi-team operating projection against all four without merging authority or context.
2. Enable the appointed CEO to hire internal agents, prepare and bind owner-authorized bot or webhook deployments, create allowlisted channels and public threads, delegate work, and resolve approval effects without exposing credentials or conflating external Discord presentation with hiring.
3. Enable each hired agent to inspect and show requested code, perform authorized managed Codex or Claude repository work, publish verified results, create threads, reply, mention eligible participants, and converse with agents through natural addressed routing.
4. Promote each agent's reviewed identity, work, relationship, and expertise context through real conversation and change turns. Verified work outcomes now accumulate automatically; installed acceptance must additionally verify restart, provider replacement, role transition, expiry, restricted-memory exclusion, retirement, and explicit successor handoff.
5. Compare representative installed read and change journeys against direct Codex CLI and Claude Code baselines. Claim improvement only for measured grounding, correctness, verification, rework, recovery, or continuity outcomes.
6. Install a scenario with a human, a uniquely named central agent appointed to the CEO role, and all three project teams collaborating without crossing authority or context boundaries.
7. Demonstrate two distinct installed agent speakers completing bounded deliberation in one real Discord channel and stopping at its terminal condition.
8. Connect a first-party test surface to the same headless contracts and import the same durable organization, agent context, conversation, work, and evidence projections without a Discord-specific execution dependency.
