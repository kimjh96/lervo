# Installed limits and acceptance

Decision references are linked from the [scope entrypoint](../installed-scope.md).

## Capability boundaries

Webhook replies remain canonical rather than native. Natural product-owner hiring invokes agent-deployment preparation, organization binding, runtime configuration, and post-acknowledgment restart for the durable child speaker. Remaining work extends that governed path to natural central-executive requests across repository teams and broader natural addressed groups.

Cross-Node natural discussion uses ADR-0421's authenticated receiver-owned protocol. Repository-local co-resident formal participants remain a separate policy-seat capability; remote repository-agent formal execution is not claimed without formal-route evidence.

Webhook task results are presentation-only on Discord; the co-resident router carries authenticated results to the coordinator. Remote task delegation over Discord nonce transport is limited to two application-bot speakers until an authenticated receiver-owned webhook control envelope exists. ADR-0425 records the correction for unaddressed webhook observation and its pre-send limits. Acceptance must show the webhook worker's visible result and the coordinator's exact task-ID continuation each occur once, including after restart. Adapter tests and healthy services are insufficient.

Each agent needing native member presence, its own typing indicator, or native mentionability requires a separate installed bot application. Exact Lervo `@DisplayName` addressing remains available to webhook identities.

The request-scoped runtime contract is implemented but unavailable until the target repository's owner-only Node configuration explicitly allowlists `requested_runtime.manage` and binds an exact executable, working directory, readiness observation, and lifetime. Neither a port number nor an old conversation establishes an installed target. Enabling the capability does not prove a particular preview server is open.

## Operational acceptance

The owner already authorized product-owner-to-hired-agent and hired-agent-to-hired-agent operation. The capability stays deployed while technical acceptance is open; earlier authorization is not a missing-consent blocker.

Closing acceptance requires one two-direction evidence run proving exactly one processing and exactly one publication for every request across normal, redelivered, failed, retried, and restarted turns. For each request identifier, correlate durable inbox, participation-decision, outbox, and interlocutor-focus rows with the observed channel result.

The failed-delivery branch must distinguish a nonce-reused earlier Discord message from publication of the requested outbound. A mismatch stays unacknowledged and must not be sent again. Component duplicate-suppression, focus-recovery, and ownership coverage do not replace this run.

The outbox has a bounded `attention_required` state and a Discord-only externally verified reconciliation path under ADR-0424. Uncertain or failed sends are not silently counted as published. Operational approval requires no unresolved attention state for the exact acceptance requests. Recovered historical messages support incident evidence but do not replace the two-direction matrix.
