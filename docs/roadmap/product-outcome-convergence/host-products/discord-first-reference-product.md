# Discord-first reference product

State: `delivery required`

## Outcome

Make Lervo's Paperclip-, Buzz-, Prime-Agent-, and Hermes-derived advantages usable through a real Discord installation before the first-party surface ships. Discord is the current reference surface; Lervo core and versioned application contracts remain authoritative.

The first-party surface must reuse the same commands, queries, subscriptions, durable identities, work, evidence, knowledge, search, and recovery contracts without creating a parallel product backend.

## Delivery sequence

### 1. Goal-to-verified-result spine

- Complete natural goal intent, standing supervision, autonomous staffing, verification, accepted-result publication, and origin-bound Discord delivery.
- Complete real multi-agent role participation in one channel.
- Complete reviewed Mac-offline source handoff, divergence handling, and verified hand-back.
- Show minimal progress, blocker, approval, and terminal-activity projections in the originating thread.

### 2. Observation and control

- Add the bounded, event-derived activity feed and subscription cursor.
- Add live-steering commands through the product-host protocol and Discord adapter.
- Add a unified operating view over existing canonical authorities and projections.
- Show observed tokens; show cost separately as observed or explicitly unavailable. Add warnings, with any hard-stop policy deferred to separate review.
- Integrate formal deliberation as an optional, origin-bound decision thread with structured artifacts, per-role resources, and explicit `converged`, `no_consensus`, and failure meanings. Keep it off default conversation and goal paths.

### 3. Unified discovery and collaboration artifacts

- Add typed unified search across repository knowledge, code, conversations, artifacts, approvals, verification, and work events, using Lexical v2 for repository grounding.
- Add canvas, file, and media artifact lifecycles with privacy, content hash, ownership, retention, and promotion boundaries.
- Project assignment routines and execution graphs as channel-visible workflows without creating a second workflow authority.

### 4. First-party surface parity

- Connect a first-party test surface to the same protocol and conformance suite.
- Import no Discord configuration into application or domain packages.
- Replay the installed vertical slice and shared product scenarios.
- Replace or coexist with Discord without losing or migrating identity, context, work, evidence, or canonical knowledge.

## Cross-cutting gates

- Every slice passes responsibility and dependency review under the code convention.
- Entrypoints remain short. Domain, orchestration, transport, projection, search, rendering, storage, and recovery remain independently testable.
- Every new growing state defines bounds, pagination, retention, compaction, privacy, and failure meaning.
- Every new command, query, subscription, event, and projection has a versioned contract and common host conformance test.
- Existing causal work, document-coverage, resource, stage, token, cache, verification, and delivery observations retain their exact meanings across Discord and future surfaces. Unavailable values remain explicit; host rendering never double-counts them.
- Ordinary discussion and formal deliberation have separate positive and negative installed acceptance. Semantic relevance, mentions, and agent suggestions cannot silently incur deliberation work.
- A Korean natural-language deliberation request produces Korean start, artifact, failure, and substantive terminal content; replies to the exact originating Discord message; and retains relevant prior human design context despite intervening agent chatter.
- Discord renders every writing-gated stakeholder contribution as natural proposal, challenge, revision, or verification prose. Round numbers, artifact and claim counts, and publication-gate status belong in activity and evidence projections, not participant dialogue.
- A transient pre-provider repository snapshot race receives one bounded fresh attempt. Exhaustion creates no deliberation job. Installed acceptance covers a request arriving while replica bytes change.
- Installed acceptance includes a reviewer draft that initially fails `plain_audience_language`: the fresh repair omits internal coordinates, preserves exact provenance in execution evidence, passes the unchanged publication gate, and permits the remaining reviewers and decision owner to finish.
- Installed acceptance includes a reviewer draft that initially fails `direct_result_and_action` by assigning work to another named role: the fresh repair states the reviewer's own result and expresses missing work as an approval condition without delegating to another person or team.
- The installed policy's provider-call ceiling covers its complete maximum-round no-repair path plus both required single-repair acceptance journeys, and the service process timeout preserves terminalization time beyond the policy elapsed ceiling. Static feasibility rejection and an installed provider run both verify this relation.
- Repository grounding uses the current resolved search plan and records exact ranking evidence.
- Knowledge promotion remains explicit, source-bound, reviewed, and rollback-aware.
- Before making version claims, verify current and predecessor release compatibility, migration interruption, rollback, stale-projection rejection, and historical replay.
- Installed Discord acceptance uses real transport, current source, managed providers, restart, and observable result delivery. Fixtures alone do not complete a slice.

## Completion

Completion requires installed evidence for all four slices and a passing first-party host parity suite. A core primitive, source implementation, green test suite, packed protocol, or Discord acknowledgment alone does not constitute completion.
