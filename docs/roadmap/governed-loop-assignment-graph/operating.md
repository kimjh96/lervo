# Operating reports and product host

These completed bounded manual slices share the [roadmap's responsibility boundaries and non-goals](../governed-loop-assignment-graph.md).

## GLA4: Minimal local operating client

`@lervo/operating-client` is a read-only graphical reference client over the exact governed-work report, with no storage, Hub, provider, or mutation dependency. It projects report evidence into a board view model and renders deterministic, self-contained HTML. `lervo loop board` supplies the report; the generated document has no script, form, server, network dependency, or state-changing control.

Acceptance requires focused tests for assignment and dependency projection; attempt, approval, completion, action, and resource visibility; deterministic escaped HTML; explicit evidence limitations; no mutation-port invocation; and invalid-report exit preservation. Quality, type, package-boundary, build, full tests, documentation and knowledge lifecycle, foundation checks, and task-base release completion must pass with reviewed minor release intent.

## GLA5: Current objective and observed token budgets

A storage-free application report exposes the verified current workstream objective. Exact configured token admission limits are related to exact provider and accounting-group observations. `lervo loop objective` reads no managed-work state. `lervo loop budget` performs no mutation and reports partial, unavailable, invalid, or absent evidence as unknown. The local board composes these independent reports, escapes prose, and provides no controls.

The completed follow-up accounts for every causally linked managed run while retaining root and retry as the attempt model. Resource scope is included in group and policy coordinates; missing started child-run observations make accounting incomplete. Unscoped limits remain only as a fail-closed compatibility form. Direct-terminal latency and per-context query-projection budgets remain a separate diagnostic contract and do not make unmanaged provider work governed.

Acceptance requires focused tests for verified objective translation, no managed-work query during objective inspection, exact accounting-group matching, no unknown-to-zero conversion, observed remaining-token projection, board prose escaping, and no mutation-port invocation. Quality, type, package-boundary, build, full tests, documentation and knowledge lifecycle, foundation checks, and task-base release completion must pass with reviewed minor release intent.

## GLA14: Packed product-host protocol

`lervo application capabilities --json` exposes one versioned, effect-free capability report. It inventories existing workforce, operating, and collaboration routes and names their result contracts, output forms, effects, authority, and availability. Product UI, product databases, unattended scheduling, dynamic graph mutation, implicit approval, and unmanaged terminal execution are explicitly unsupported.

The protocol uses the sole public `@lervo/cli` artifact; workspace-private application packages are not prematurely published. The packed external-consumer fixture imports no workspace package. Through CLI commands, it creates one local agent, workstream, and assignment, then reads objective, graph, budget, thread, inbox, and static board without a Hub, provider, or connector effect. Existing domain commands remain the only policy and mutation owners.

Acceptance requires focused tests for deterministic discovery, effect and authority classification, connector adapter requirements, and explicit non-capabilities. The real packed consumer must prove the local product-host journey and absence of private-package installation. Quality, type, package-boundary, build, full tests, documentation and knowledge lifecycle, foundation checks, and task-base release completion must pass with reviewed minor release intent.

## GLA15: Project operating attention

One deterministic read-only projection covers current workstream decisions, approvals and blockers, canonicalization review candidates, and repository-knowledge lifecycle issues. It explicitly reports action owner, user authority, blocking state, source coverage, and unavailable-source meaning. It neither owns nor acknowledges the underlying work.

Direct terminal preparation includes a bounded cache-backed form without another model call or full lifecycle scan. Default product-host protocol v1 stays unchanged; explicit protocol v2 appends `operating_attention.inspect`.

Completed or rejected canonicalization candidates become eligible for the existing exact state-retention policy; unresolved candidates remain protected. A stale candidate permits exact-hash rejection, never defer or promotion.

Acceptance requires focused tests for deterministic ordering and bounds, degraded-source availability, stale-candidate safety, terminal retrieval continuity, and state retention. The real packed consumer must discover both protocol versions and invoke attention without workspace-private imports. Ordinary repository completion gates must pass.

## GLA16: Workstream goal projection

The verified workstream is the one repository root goal; its bound assignments form the execution DAG. A storage-free application report retains exact source coordinates, progress, explicit lifecycle status, completion readiness, and contradictions. It creates no second goal or task authority and never infers completion.

`lervo loop goal` exposes the read-only report. Explicit product-host protocol v2 appends `operating_goal.inspect`; default v1 stays unchanged. Independent nested goals, dynamic topology, provider startup, and unattended scheduling remain unsupported.

Acceptance requires pure tests for coordinate matching, active progress, false authority flags, and inconsistent completion; CLI tests proving no managed execution; packed external-consumer discovery and route invocation; and all ordinary repository completion gates.
