## Reliability scope

The owner reported English-publication policy violations and uncertain document relevance in direct provider terminals on 2026-10-09. Treat this as an end-to-end quality concern. A reference ratio or nonempty hit list cannot establish that the required instructions and evidence reached the agent or affected its output.

The first reproduced defect was independent of ranking: compact preparation read `publication.language` for query metadata but omitted the writing instruction from prepared context. Compact and retrieval preparation now render the configured language separately from ranked documents. Source regression tests cover both providers; actual installed writing compliance remains unverified.

The remaining evaluation must distinguish:

- Required policy delivery: applicable configured obligations remain available with zero hits, failed retrieval, and bounded context. This first correction covers publication language, not every repository instruction.
- Task relevance: label required, supporting, irrelevant, and obsolete sources for real Korean, English, and mixed-language tasks, including ambiguous and no-source requests. Measure required-source recall and irrelevant inclusion at the actual delivery limit, separately from top-10 ranking.
- Delivery integrity: compare ranked candidates with selected paths, loaded hashes, prepared sections, truncation, and observable references. Report unavailable provider acceptance or use as unavailable.
- Outcome compliance: inspect the resulting artifact against the required language and task constraints. An injected or referenced rule can still be violated.

Freeze case labels and corpus coordinates before comparing a retrieval candidate. Keep engine-only queries, projected queries, agent-issued queries, and final delivered context as separate observations. Human review is required before calling the labels production ground truth. Do not raise hit limits, add fixture-specific routing, or activate a new engine solely to improve aggregate counts. A completion claim requires per-case nonregression, useful recall and precision, fresh-source handling, bounded context cost, and installed Codex and Claude outcomes. The current language-delivery correction does not establish general Hit uplift.

## Consumer migration

1. Characterize current terminal, direct query, managed run, and conversation paths before moving code. Bind selected and actually loaded results separately; preserve unavailable states.
2. Extract provider-neutral decisions into their existing domain owners, then compose them through repository-context with explicit ports. Keep compatibility facades and run old/new differential fixtures on identical input.
3. Move terminal and Node callers to the shared operations. Each adapter supplies normalized task, authority and capability coordinates, not copied rules or ranking parameters.
4. Add the native-chat adapter to every new semantic scenario. Add a negotiated product-host capability only when its external-consumer contract and supported schema exist; do not preassign an unsupported protocol version.
5. Remove compatibility code only after the reader window, installed receipts, and rollback boundary permit it. Record any remaining independent concern with an exact owner and verification, not a generic refactoring note.

## Structural acceptance

- Domain code has no imports or semantic branches for Discord, native UI, provider SDKs, filesystem, or database mechanics.
- Entrypoints parse, invoke, render, and translate status. Separate modules own applicability, source observation, stage execution, section decisions, I/O, evidence projection, and artifact verification.
- Shared types live with their contract owner, public exports have real consumers, and no speculative package, directory, plugin system, or generic manager is created.
- Every touched source passes the code-convention responsibility review, package/import boundaries, platform ratchet, and relevant common contracts. Long-module review records cohesion after required splits.
- Retained state has explicit cardinality, byte, concurrency, cancellation, and retirement rules. Cold and warm operation preserve source coverage and authorization.

## Completion labels

`design_ready` means the proposed ADR, contracts, performance/evaluation protocol, and migration plan are reviewable; it means no runtime adoption. `source_verified` means implementation, schema/privacy/common contracts, quality, lifecycle, and task-base release checks pass. `installed_existing_surfaces` requires real supported terminal and Discord evidence. `future_host_conformant` describes external host contract tests; `installed_first_party` is unavailable until a real first-party product passes its own journey. These are roadmap labels, not new event states.

Before each implementation slice completes, record source responsibility review, relevant tests, documentation changes, knowledge lifecycle checks, and `pnpm release:completion:check --base <slice-base>`. CLI and bundled-private behavior require reviewed release intent. Repository-wide knowledge lifecycle changes additionally run migration and lint through the existing exact apply contract. No broad generated-content rewrite is implicit in this feature.
