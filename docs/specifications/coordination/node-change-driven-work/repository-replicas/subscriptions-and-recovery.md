# Subscriptions and recovery

The coordinator subscribes to local source directories and, by default, persistent authenticated SSH peer streams. A constrained bridge may set `peerWatch` to `false`: local watches remain active, and peer changes use finite snapshot commands at the configured recovery interval.

Watches cover tracked and non-ignored source parents, Git HEAD/index/branch coordinates, and the replica readiness request. On macOS and Windows, each repository opens one recursive native watch on the worktree root. It opens another for each Git directory or runtime state directory whose real path lies outside every watched real path, such as a linked worktree's common directory or a symbolic link. Events are classified by their logical repository path, and paths compare case-insensitively. Events outside the watched directory set, such as ignored caches and Git object storage, are dropped in process. A refresh replaces only that set and opens a base that was missing, so directory churn never reopens a handle. This matters on macOS, where libuv leaks memory for every watched path whenever a directory watch opens or closes. Linux keeps one inotify watch per directory and never watches inside ignored caches or Git object storage. Each repository permits at most 4,096 watched directories and a 4 MiB Git path-list response. Unsupported watches and capacity failures trigger recovery without bypassing authoritative snapshot verification.

## Scheduling and recovery

Each repository has one coalesced pending hint. A 250 ms eligibility window groups consecutive changes. Hints received during reconciliation schedule exactly one successor run for that repository. A dynamic keyed pool reconciles at most four independent repositories concurrently; completion immediately frees capacity for an eligible hint without waiting for unrelated runs. Completion records use serialized fresh read-modify-write state updates so parallel cycles cannot discard each other's common snapshot.

Idle healthy subscriptions perform full recovery every 60 seconds. Deliberately disabled peer watches use `pollIntervalMs` as the base recovery interval. Unsupported or disconnected subscriptions also recover at `pollIntervalMs` and retry after 60 seconds.

Each replica keeps its own recovery interval ([ADR-0461](../../../../decisions/operations/services/0461-drive-resident-runtime-service-work-from-changes-not-timers.md), [ADR-0570](../../../../decisions/operations/services/0570-reuse-one-replica-peer-connection-and-back-off-an-unreachable-peer.md)). A cycle ending `current` or `held` schedules that replica's next recovery cycle one interval after it finishes and doubles the interval up to `idleRecoveryCeilingMs`. `held` means the cycle saw an already observed divergence identity or the same structured failure as the previous cycle. The ceiling defaults to 600,000 ms; owner-only configuration accepts 30,000–3,600,000 ms. A hint for a replica, or any other outcome, returns only that replica to its base interval. A recovery cycle never queues while that replica is pending or running. The fallback interval while notifications are unavailable never backs off. Intervals are held in memory, so restart begins at the base. Persistent peer streams' 60-second keepalive hints also count as hints. Health `recoveryIntervalMs` reports the shortest interval of any replica.

A hint starts a `change` cycle; startup or a recovery sweep starts a `recovery` cycle. A `current` cycle reuses its two equal observations as parity proof instead of observing both sides again. A cycle that transferred bytes still recaptures both sides. The local receipt is always written. A `recovery` cycle skips the peer receipt when, apart from `reconciledAt`, it equals the last receipt this coordinator process wrote for the replica. A `change` cycle always writes it. When both sides show the same snapshot and the local supersession result equals that of a peer exchange that changed nothing within the last 15 minutes, the cycle skips the peer half of the supersession exchange. An unchanged current replica therefore costs one peer request per recovery cycle.

## Peer transport

Every finite peer step and peer watch reuses one SSH connection. For an OpenSSH client other than Windows OpenSSH (`ssh.exe`, also through WSL interop), the coordinator adds `ControlMaster=auto`, `ControlPath=<state directory>/replica-ssh/%C`, and `ControlPersist=600`. The control directory beside the coordinator state file is owner-only (`0700`), and a directory that is not owner-only disables reuse. A path beyond the platform socket limit falls back to a hashed name or disables reuse. Coordinator arguments that set any multiplexing option (`ControlMaster`, `ControlPath`, `ControlPersist`, `-M`, `-S`) disable Lervo's own; every other option Lervo adds (`ConnectTimeout=15`, `ServerAliveInterval=15`, `ServerAliveCountMax=3`) yields to a configured value. A disabled reuse mode other than a non-OpenSSH client is logged once at startup.

A transport failure (`repository_replica_transfer_failed` or `repository_replica_transfer_timeout` at stage `transfer`) closes one gate for the whole peer. While it is closed, no cycle starts and no peer watch is resubscribed; hints stay queued. At the retry time one `capture-version` probe runs. The wait starts at the base recovery interval and doubles up to `idleRecoveryCeilingMs`. Cycles that failed during one outage count once. Any answer from the peer, a probe or another replica's cycle, reopens the gate and runs only the replicas it parked once more. A replica whose transport failure recurs after the peer answered anyone is isolated until it completes a cycle again: each of its transport failures runs one immediate `capture-version` probe. A probe answer makes the failure `held` on the replica's own schedule and leaves the gate open; a failed probe closes the gate as a peer outage. A probe result younger than the base interval is reused for confirmation. Health carries `peer: { status: "backing_off", consecutiveFailures, retryAt }` while the gate is closed. One-shot runs are not gated.

A peer remote command that runs through a per-call launcher (`wsl`, `wsl.exe`, `ubuntu*.exe`) boots or wakes WSL for every step. The coordinator reports `repository_replica_peer_per_call_launcher` once on stderr and in health `advisories`. `lervo upgrade` shows the same guidance in its replica service stage: point `peer.destination` at the WSL `sshd` and remove `peer.remoteCommandPrefix`. The configuration is never rewritten.

A peer requiring readiness therefore needs persistent peer watches: readiness-request hints refresh its receipt, while a backed-off sweep exceeds maximum readiness staleness. Timer recovery never queues another full sweep while reconciliation is active or pending, preventing continuous sweeps when a constrained bridge takes longer than its interval. Source-change hints during work still retain one coalesced successor run. SSH streams have a 75-second silence watchdog. Shutdown closes subscriptions and waits only for already-started work.

Each finite SSH snapshot, bundle, apply, and receipt command defaults to a 60-second execution deadline. Owner-only configuration may select 1–300 seconds. Expiry terminates the local transport process, releases its reconciliation slot, writes no parity receipt, and remains a transport failure. Coordinator concurrency accepts one through four, defaulting to four. A serialized Windows-to-WSL bridge uses one to avoid saturating its command-launch boundary.

## Watch hints and evidence boundaries

`lervo-node repository-replica watch --root <root>` emits newline-delimited `{ "schemaVersion": 1, "status": "changed" }` frames. Startup and the 60-second recovery timeout also emit hints; the status does not prove a file changed. The client accepts only the exact versioned frame and limits buffered output to 1,024 characters. Streams carry no filenames, contents, snapshot hashes, credentials, or authorization decisions. Existing configured SSH authentication and peer/root selection control access.

Local subscriptions compare a disposable metadata fingerprint every 60 seconds to recover silent native filesystem notifications. It binds Git status/ref coordinates, dirty-path inode/size/timestamps, the checkout's own HEAD and index, the shared `info/exclude` file, and the exact replica request. A linked worktree's HEAD and index live in its own Git directory, not the common one. It excludes source bodies and ignored caches and grants no snapshot authority. Its status runs with `--no-optional-locks`, so it never rewrites the index; a refresh would itself look like a change to every watcher of the checkout. A changed fingerprint refreshes directory subscriptions and emits only a hint. Focused host tests may select a shorter recovery interval. Closing the watch disposes this timer and prevents pending observations from notifying again.
