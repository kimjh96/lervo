# Terminal preparation and snapshot delegation

## Snapshot delegation

`apps/cli/src/terminal-repository-snapshot.ts` delegates to `capturePersistentRepositorySnapshot` from `@lervo/orchestrator`, passing the repository root, the invocation-local absolute snapshot deadline less a 500 ms persist reserve when present, and the resolved cache path `.lervo/state/cache/terminal-repository-snapshot.json`. Retrieval preparation and terminal repository-change planning use this wrapper.

The shared command has a 15,000 ms budget. Snapshot captures share its 7,500 ms deadline, including nested Stop and knowledge-cache confirmation captures. Main stages share the 10,000 ms deadline; observation recording has the remaining budget. These deadlines do not renew per operation. Deadline races bound awaited operations; the generated executable flushes output and exits to release outstanding handles. A blocked JavaScript event loop remains outside this timer guarantee.

Git ignored-path discovery returns `available` or `unavailable`. Only an explicit non-repository probe permits an empty result without a successful ignored-path listing. Without the previous capture's ignored paths, unavailability rejects before traversal; with them, it rejects before any path that capture did not see is visited and before any file is read. A listing that the deadline cut off rejects as `repository_snapshot_deadline_exceeded`, and a capture that fails waits for the listing, which the same deadline bounds, so Git never outlives it. Git timeouts use the remaining snapshot time. Capture checks limits at each entry and deadlines before traversal, before each stat, link read, directory read, and file read, after each file read, and before completion. It never returns a partial snapshot. File-count rejection already occurred at the first excess entry before ADR-0531.

Capture walks directories concurrently. It runs at most 64 stats, link reads, and directory reads and at most 8 file reads at a time. It records files in the order a depth-first walk in sorted name order would, so the revision does not depend on which stat finished first. Concurrency keeps these guarantees:

- **Entry bound:** a file is counted before it is stat'ed or read, so capture reads at most the entry bound's number of files. Files are counted in the order directories are discovered, not in walk order, so the bound limits how many files are read, not which ones.
- **Deadline:** no stat, link read, directory read, or file read starts after the deadline, including one that was waiting for a slot. A file read already running finishes its identity check and keeps its hash, so a rejection lags the deadline by at most the 8 running reads, well within the 500 ms persist reserve on a disk that serves one 20 ms read at a time.
- **First failure:** the first failure stops the whole walk. No branch starts another operation after it, and capture waits for every branch to settle before it rejects, so no read outlives the capture. A capture that ran out of time persists every hash its branches completed.
- **Byte bound:** up to 8 reads may already be in flight when the byte total first exceeds the bound.

A capture keeps the paths Git ignored, in memory or in the persisted cache, and the next capture walks while Git lists them again instead of waiting for the list. Until the fresh list arrives, a path the previous capture saw (a file it recorded, a directory that holds one, or a path it ignored) is judged by the previous list. Any other path waits for the fresh one and is judged with the directories that hold it, so a new directory Git ignores is never walked. Reading a file always waits for the fresh list, so no file is read before Git has judged it. The fresh list then removes every walked path it ignores, with its cached hash. The capture walks again with the fresh list, reusing the hashes it computed, in two cases: a path the previous list ignored still exists and the fresh list no longer ignores it, or the walk reached the file-count or byte limit, which paths only the fresh list ignores may have counted toward. The result is therefore the one a capture without a previous list returns. When the fresh list equals the previous one, as it usually does, every path was already judged as the fresh list judges it, so the capture skips that removal. On 2026-11-26, under a load average near 12, six alternating runs of 25 warm in-memory captures of this repository put the median at 92–116 ms waiting for the list and 73–100 ms walking meanwhile, with identical revisions; listing ignored paths alone took 30–50 ms.

On 2026-11-25 the concurrent walk cut a warm capture of this repository on the Mac from about 180–250 ms to 115–150 ms, with identical revisions. With the bounds above, on 2026-11-26 under a load average near 12, three alternating runs of 12 warm captures each put the sequential walk's median at 278–545 ms and the concurrent walk's at 181–248 ms, again with identical revisions.

A capture that reaches its deadline still persists the stat-identity hashes it computed, merged over the earlier cache entries it had not reached, and then rejects as before. Those entries carry the same identity (device, inode, size, and modification and change times) a completed capture records, so reusing one is exactly as safe as reusing a completed capture's. Without this, a checkout whose cold capture outlasts one deadline would never warm: on 2026-11-25 a fresh worktree of this repository (8,936 files, 61 MB) took 7.0–11 s to capture cold and 0.48 s warm against the 7,500 ms deadline, so every prompt there degraded with `repository_snapshot_deadline_exceeded` and recorded no turn evidence. The 500 ms reserve lets the write finish before the hook's own timer fires: writing this repository's 2.35 MB cache took 3–7 ms on a loaded Mac. Concurrent writers, such as a workspace-start warm-up and a prompt hook, each rename a unique temporary file, so the last write wins and neither fails. A process remembers the cache it last wrote, with that file's device, inode, size, and modification time, and reuses it while the file keeps that identity; a long-lived process such as the context server then skips reading and checking its own cache on every prompt, and any other writer's file, which has another identity, is read again.

The wrapper adds no alternate capture path. Its comment describes stat-identity hash reuse, but the imported implementation is required to establish cache validation, invalidation, filesystem safety, and behavior after cache corruption. This call site proves neither that every capture avoids rehashing nor a measured latency improvement.
