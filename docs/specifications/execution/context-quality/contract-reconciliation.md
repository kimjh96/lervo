# Context-quality contract reconciliations

Status: `active`

This companion amends three specific descriptions in the context-quality specifications. It preserves their original implementation-stage records while resolving the current interpretation against the supplied canonical evidence. It adds no runtime behavior, activation authority or acceptance result.

## Native distribution: historical prerequisite and later evidence

In [recording storage reuse](recording-storage-reuse.md#native-file-synchronization-source-candidate), the statement that CLI/Hub/Node packaging, release archive contracts, minimum-runtime consumers and a new frozen cohort remain required describes the initial native synchronization source slice. It must not be read as the current status of all subsequent distribution work. The adjacent source-only diagnostic likewise describes its own artifact and stage.

The supplied [source verification record](../../../evidence/quality/context-quality/context-quality-source-verification.md#native-cas-runtime-composition) reports later integration of the complete synchronization and CAS native asset set into CLI, Hub, Node and repository-installed terminal hooks. Its recorded contracts include CLI manifest schema 7 with nine archive files and four native assets, SBOM generator 3, standalone manifest 3 and terminal integrity schema 3, with the stated older-reader compatibility. These are that stage's schema coordinates, not a claim that later manifests retain those versions.

That record reports 285 tests on minimum Node 22.13.0 and Darwin arm64 built, standalone, packed and isolated-registry consumer checks on its rebuilt assets. It also reports native execution of application copies on arm64 and through Rosetta x64. It explicitly does not establish complete x64 packed-consumer acceptance, physical Intel execution or hosted provenance. Its subsequent 380-worker comparison rejects both cold latency groups, all eight CPU groups and three whole-process groups while semantics, integrity, RSS and storage pass. Those observations supersede the initial claim that no later packaging or cohort evidence exists; they do not qualify every later artifact.

The directly linked native-sync implementation document was unavailable to this assessment because its read failed. Its detailed contents and any additional current result remain unverified here. The reconciliation above relies on the supplied source-verification record, not on that missing document or on its filename. No fresh build, packed smoke, benchmark or publication was performed for this reconciliation.

Later aggregate inventory requirements remain separately described by the [CLI build contract](../../../distribution/cli-bundle-construction/build.md). Neither an earlier native asset receipt nor a newer inventory contract substitutes for execution and resource evidence on the exact artifact being accepted.

## Legacy planning diagnostics and runtime-resolved bindings

In [request and plan validation](request-plan-validation.md#current-consumers-and-remaining-acceptance), the paragraph describing unavailable `planningReadiness` and unresolved request-planning coordinates applies to the older `ContextPreparationReport` diagnostic. It does not state that every current runtime preparation lacks task, scope, policy or profile bindings.

The [preparation-observation contract](preparation-observations.md) is explicitly narrower than the request/plan contract. Its unavailable planning diagnostic cannot be used as a substitute for the separate runtime plan, nor can an older report without the field establish planning readiness.

[Shared runtime preparation](runtime-preparation.md#runtime-ownership-and-bindings) supplies local binding owners through `prepareRepositoryQualityContext`. It binds normalized task content, local root identity, manifest content, target paths, policy and exact instruction versions, observed retrieval generation and build, projected queries and a versioned resource profile. Revalidation checks current policy, catalog membership, rules and selected source bytes. The [accepted architecture decision](../../../decisions/execution/grounding/0501-share-context-quality-contracts-across-product-surfaces.md#runtime-implementation-update) also records these connected local-read consumers.

These bindings authorize only current local context preparation. They grant no repository-write, external-effect or provider permission. Corpus completeness and provider token counts remain unobserved in this runtime composition. An ordinary local result may therefore remain incomplete, and compact mode without retrieval does not establish a complete evidence plan. Resolving local bindings does not prove delivery, use, relevance or artifact compliance.

## Tokenizer-based projection bound

In [runtime preparation](runtime-preparation.md#tasklanguage-projection-and-evidence), replace the interpretation of an “existing 32-word primary-task bound” with the search engine's 32-term admission bound for local projector build version 2.

The [source verification record](../../../evidence/quality/context-quality/context-quality-source-verification.md#implemented-boundary) identifies the corrected defect: whitespace-word counting could admit more than 32 search terms when identifiers, apostrophes and paths were present. The projector now counts with the search engine tokenizer, reserves bounded target and alias terms, and admits whole words without cutting identifiers. Query continuation reaches the local projection.

The source's 500-character output ceiling and 16 KiB input ceiling remain applicable. Tokenizer counting does not authorize truncating identifiers or changing retrieval plans. Projector build version 2 is a separate implementation coordinate from local repository preparation build version 2, which distinguishes the instruction-supersession correction. Neither version coordinate is an installed release attestation.

Managed and direct query paths retain their local projection contract. Retrieval-mode terminal search retains its existing validated projector and selected retrieval-plan binding; compact mode still performs no retrieval or provider projection. The correction establishes a bounded query representation, not reviewed relevance improvement or installed provider compliance.

## Resource accounting and acceptance remain separate

The general [performance and acceptance protocol](performance-and-acceptance.md) requires at least five cold pairs; thirty-pair cohorts satisfy that minimum. Sample count alone does not explain the later accounting change.

The supplied [strong-commit supplement](../recovery-and-verification-supplement.md#strong-commit-resource-accounting) records ADR-0506's bounded packaged-protocol amendment. `context-quality-packaged-resource-v2` fixes `durableCommitAllowanceMs` at 5. Candidate samples, including warmups, must show at least one strong commit on a connection enabling `fullfsync`; controls must show none. Missing candidate commits or any control commit invalidate the evidence.

Adjusted added latency subtracts one 5 ms allowance from each paired sample mean. Adjusted whole-process accounting subtracts one allowance per sample from candidate process time before calculating its ratio. Only one required commit per sample receives the allowance; split-batch extra commits remain fully charged. Every group also reports raw latency and process intervals. CPU receives no allowance. CPU, RSS, retained state, semantic parity, integrity, full report reads and current guards retain their requirements.

`context-quality-packaged-resource-v3` retains those accounting rules and increases cold pairs from five to thirty. Its approval followed the known v2 result, including the retained 12 KiB cold CPU upper-bound failure of 1.266. It is a new cohort, not a reinterpretation or deletion of that failure. Earlier protocols retain their original accounting and results. Reusing the allowance on a different platform or storage contract requires fresh commit observations; it is not a universal device-latency or durability guarantee.

Strong synchronization, both complete report reads and fresh authority checks remain required. Ordinary close and checkpoint work cannot be omitted merely to improve measured process cost. The [installed report lifecycle evidence](../../../evidence/quality/context-quality/installed-report-recovery.md) reports bounded Darwin arm64 interruption, retry and quota checks; it leaves owner-retention operations, power loss and other supported-platform qualification open.

Reviewed real-task quality, exact-artifact resource qualification, real installed terminal and Discord journeys, reader-first rollout, recovery and the operational cohort remain independent gates. Release preparation, tag creation and publication retain their separate evidence and authorization boundaries. This documentation reconciliation closes none of those gates.
