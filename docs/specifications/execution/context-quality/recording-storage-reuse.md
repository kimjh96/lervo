# Bounded context-quality recording storage reuse

Status: `implemented_source`
As of: 2026-10-10

The [rejected active-resource cohort](../../../evidence/quality/context-quality/context-quality-priority4-evaluation.md) found repeated project-storage open and chain-validation cost. This repair retains the [outcome/event contract](outcome-and-event-rollout.md), explicit writer activation, per-attempt complete reports, and durable event receipts. It adds no model call, event schema, delivery claim, or production activation.

## Ownership and bounds

`project-storage` owns a bounded pool of overlapping operations. `repository-context` owns one pool for quality recording only; other project-storage callers retain their existing lifetime. The pool admits at most eight repository roots and 16 pending operations per root, including executing operations. A handle rotates before its next operation after 64 uses or one second of age, whichever occurs first. After 50 ms idle, it closes. An active filesystem operation is allowed to finish; the age limit does not abort in-progress I/O. Timers do not keep a terminal process alive, and durable commits complete before success is returned. Explicit pool close stops admission, drains accepted operations, and closes all handles.

Preparation/verification reports are cloned and serialized before admission, with the existing 1 MiB byte ceiling. The serialized report replaces the cloned report body while waiting. Queue entries are transient, bounded by admission, and removed when settled. Pool entries retain a handle, bounded identity coordinates and scheduling metadata, never a conversation or source cache. Operation errors invalidate the lease for new or pending writes; admitted borrowers drain before the handle closes. Age/use rotation also drains admitted borrowers, without invalidating their current observations. Cleanup failure remains a poisoned occupied entry rather than silently admitting another handle; explicit close reports the aggregate failure. Process termination releases operating-system handles without an uncommitted success receipt.

Pooled writers select the adapter's `report_batches` checkpoint policy. An explicitly selected format-4 report writer uses an automatic checkpoint threshold of 1 MiB divided by its actual page size (256 pages at 4 KiB, 512 at 2 KiB); ordinary event writers retain the one-page threshold. Both request `journal_size_limit=0`. The older `checkpointEachCommit: true` option still means one page, and the named `each_commit` policy has the same meaning. Supplying both options or an unknown policy fails with `integrity_failed` before database creation. Independent default openers retain SQLite's default policy. Initialization reads back the selected settings before committing schema/project binding; disagreement rolls back that transaction.

Checkpoint frequency does not change report durability: every report transaction still requires `synchronous=FULL`, `fullfsync=ON` and `checkpoint_fullfsync=ON`, publishes atomically and completes both report reads before receipts. Automatic checkpoints run at the committing transaction that reaches the threshold; their cost remains in that operation. There is no background checkpoint worker, delayed durability receipt or application-side WAL deletion. Closing the last SQLite connection performs ordinary SQLite cleanup. See [SQLite WAL synchronization and checkpoint behavior](https://www.sqlite.org/wal.html#performance_considerations).

The threshold is measured in pages, not a hard byte ceiling. A large transaction can exceed it, and an active external reader can prevent WAL reset. `journal_size_limit=0` controls retained size when SQLite can reset the journal; it cannot evict a reader or bound concurrent external writes. Source tests retain a reader snapshot through growth beyond the threshold, then verify reclamation after release and complete report reads after close/reopen. Report size, batch admission, total report capacity and pool lifetime remain separately bounded. Resource qualification must include actual retained WAL bytes and checkpoint-bearing samples; these settings alone prove no state-growth gate. See the [journal-size contract](https://www.sqlite.org/pragma.html#pragma_journal_size_limit).

The following commit-queue lifecycle applies to the legacy path, including CAS preparation and unscoped SQL recording. The prepared SQL path is described separately below.

Independent CAS preparation can overlap. Before starting CAS work, a quality-owned commit queue admits a preparation callback, with at most 16 admitted operations per storage handle including an in-flight batch. The first settled preparation schedules the next event-loop turn, which freezes the pending membership. Every included preparation must settle before one fresh shared-handle binding observation and a synchronous commit. Later arrivals remain in a separate batch with a separate observation. The existing pool bounds roots and keeps borrowers alive through preparation and commit. Completed authority observations are never cached for later work.

An artifact preparation failure rejects its entire batch without an event transaction. All other included preparations still drain before any rejection is returned, so a caller cannot release the storage handle while an accepted CAS effect is still running. Excess admission rejects before invoking its callback. A slow included artifact can delay otherwise ready peers; cardinality and report sizes are bounded, but this is not a hard filesystem deadline or an abort of in-progress I/O. For CAS recording, the queue retains preparation promises and bounded metadata only; the recording owner retains its already-bounded serialized report until preparation completes.

Event identity lookup, complete integrity verification and every append in that batch share one synchronous SQLite transaction. Exact retries use the stored timestamp and deduplicate, including retries within a batch. Success resolves for each attempt only after the durable commit; any binding, integrity, conflicting-event or commit failure rejects the entire batch and rolls back its appends. Orphaned CAS reports remain subject to existing retention. Drafts are copied when preparation resolves, contain bounded event metadata rather than report bodies, and are released at settlement. The recording owner snapshots request/report input before admission. The queue introduces no durable state, partial-success receipt or provider effect. Reuse never extends a transaction across an asynchronous callback.

A borrow also rechecks its invalidation flag after its asynchronous binding observation. Failure in another borrower while that read is pending cannot produce a current guard from an already invalidated lease.

## Opening during source preparation

The scoped observation API starts a cold storage-opening attempt inside the request, before awaiting its first source preparation. The ordinary awaited preparation API and disabled recording do not start this work. Concurrent callers share an opening already in progress; a retained handle supplies only a capability hint, without a new attempt or recording receipt. A new attempt uses an ordinary bounded pool borrow, including writer activation before backend opening and the initial fresh binding observation. It releases its slot immediately after opening and retains only the existing idle handle. Root, pending, use, age and idle bounds are unchanged. A slow source preparation may outlive idle retirement and require another ordinary open; that work remains inside the request.

The observation owner drains opening before preparation recording or the read continuation, including when source preparation fails. Opening failures map to the existing `writer_not_active` or `unavailable` recording disposition and are preserved for that preparation attempt rather than silently retried. Source failure can coexist with storage initialization, because enabled recording still attempts to report failed preparation. No report or success receipt comes from opening alone. Actual recording borrows again. Prepared SQL groups use that current-binding observation as their final guard immediately before synchronous publication; legacy recording retains its separate final guard. Both paths retain complete reports and both readbacks. Verification recording remains a separate attempt. There is no source cache, outside-request priming, new durable state or telemetry claim.

## Prepared SQL report admission

Opening now returns a transient report-writing capability hint. Concurrent requests share an in-flight opening promise; an already retained handle can supply the same boolean without another authority observation. The hint chooses scheduling only. The scoped observation stores `beforeStorage` in its bounded in-memory membership when the hint indicates a report writer. This field defaults to false, is not emitted in events, and never permits a write. Opening failures retain their existing bounded dispositions.

For that selected path, the recording owner snapshots the complete report, computes its expected hash and constructs and validates the event metadata before queue admission. Invalid inputs fail before occupying the queue. The queue privately copies bytes and draft metadata, with the same 1 MiB report ceiling. One shared budget covers this queue and legacy recording calls: at most eight normalized roots and sixteen reports per root, including queued reports and active legacy or SQL work. The existing pool's separate handle, use, age and idle bounds remain unchanged. Queue entries disappear after settlement and no durable collection is added.

On the next event-loop turn, the queue marks owned reports admitted to their observation scopes, allowing source preparations already completing in that turn to register before membership freezes. Only ready scopes enter a fixed batch. A missing sibling or failed continuation still uses explicit completion or the original fifty-millisecond backstop. Held groups cannot delay an unrelated ready group, and late reports require a later batch and a new observation.

All report preparation and membership selection precede the pool borrow. Its complete current writer, manifest, report-selection and path observation is therefore the batch's final authority check. The publication callback executes synchronously after that guard, with no additional asynchronous preparation or gap before the adapter transaction. It checks each supplied project binding, reports foreign bindings as unavailable and publishes only matching members. An absent selected report writer fails without CAS fallback. The adapter retains complete integrity verification, strong synchronization, expected report-hash comparison, both complete reads and atomic event publication. Exact retries preserve the stored timestamp. Every successful receipt follows the completed transaction and readbacks; borrow or publication failure rejects the frozen group and releases its admission only after the borrow drains.

Ordinary awaited preparation, unscoped recording and CAS-backed scoped observations retain the existing recording and final-guard path. Their calls share the report budget with the prepared SQL queue, so adding the new scheduling path does not double admission capacity. A capability hint that becomes stale cannot override the later fresh borrow, and writer rollback after a hint produces no report or event. No current authority, report body or source result is reused from an older request.

## Current identity and integrity

A pool may capture one required event schema version (1–6) at construction. Quality recording requires version 6. Before every new storage open, including after idle, age or use retirement, the pool freshly inspects the writer and rejects inactivity before opening either backend. For an existing handle, the initial borrow checks that requirement within its existing fresh writer and path observation. The recorder no longer performs a separate preliminary inspection. No retained-handle hint or previously observed writer grants admission. Pool closure, admission bounds and poisoned cleanup are evaluated before writer inspection; simultaneous failures retain those pool meanings.

A new lease establishes its baseline from the first admitted binding observation instead of a separate preliminary observation. Its transient `binding` promise holds that first exact identity result, and `bindingConfirmed` becomes true only after a borrower validates it. Concurrent first borrowers compare their own fresh observations with that same first result; a later observation cannot replace an unfinished baseline. An invalidated lease rejects even if the pending observation otherwise succeeds. Failure drains accepted borrowers and closes the handle; failed cleanup keeps the entry poisoned. These fields remain in process memory, contain no report bodies, and produce no new event or telemetry.

Before the first confirmation, an observation first checks that the live writer matches the opened handle, then checks the required activation version. This preserves the difference between a handle opened under an inactive writer and writer drift after opening. Later admissions independently observe the current writer and paths; the stored baseline is a comparison value, never permission to reuse an old authority observation. Fixed groups can share only observations started after their members were admitted. Every final commit guard still observes the binding again. These filesystem observations remain non-atomic and do not promise protection from a change after an observation returns.

The callback’s final current-binding guard still performs a fresh observation without the initial admission requirement. A writer rollback after admission therefore remains a binding failure and recording returns `unavailable`, including after CAS preparation. An initially inactive writer returns `writer_not_active`. Current writer checks are observations, not an atomic cross-process writer lease.

Project manifest decoding may reuse a validated representation only after the existing loader freshly reads and checks the entire current file. The private project parser retains at most eight exact content strings of at most 64 KiB each, with a fixed one-second lifetime and unreferenced retirement timers. Hits do not extend retention. Every returned manifest is isolated from the retained value; changed content, expiration or eviction requires decoding again. Invalid input is never retained and larger accepted manifests keep the existing uncached path. This is transient decoding reuse, not a filesystem observation or authority cache; project layout, activation transactions, writer coordinates and storage bindings are still checked freshly. Generic YAML consumers do not use this parser.

Bootstrap remains the existing verified project-storage opener, including relocation, project binding and complete open-time integrity checks. Event database opening now commits schema migration, supplemental indexes and project metadata binding in one `BEGIN IMMEDIATE` transaction. Each nested step uses its own savepoint; failure rolls back both steps before the connection closes. Standalone migration calls retain their independent immediate transaction. General configuration pragmas and directory creation precede this transaction; checkpoint policy is selected after format resolution inside it, and the complete open-time integrity check follows its commit, so a failed open does not promise that no filesystem bytes changed. This changes no event format, schema version, writer authority or report retention policy. Each borrowed operation freshly observes the project ID, writer coordinate bytes, and real directory/file identities of the repository, `.lervo`, durable/rebuildable roots, CAS roots and event database. Replacement, symlinks, writer changes or invalid activation transactions reject reuse. The recording callback repeats that observation after asynchronous CAS preparation and immediately before its synchronous event transaction.

The project adapter exposes `inspectProjectStorageCoordinates` for consumers that need both writer and report-format selection. Every call freshly loads and validates one project manifest, checks both independent pending-activation fences and the report data-directory guard, then reads and validates both complete current coordinate files against that project ID. It retains no observation between calls and accepts no caller-supplied manifest or authority hint. Standalone writer and report inspection APIs retain their existing contracts. The shared private writer-file reader preserves the original bounded read, parsing, validation, default and error behavior.

The storage opener still loads its initial manifest before layout validation and legacy migration. After those effects it obtains a new joint observation and rejects a different project ID before opening either backend. Read-only opening also checks that boundary. Pool admission and final binding observations use the joint API while retaining all managed-path identity reads and comparisons against the opened manifest, writer and report-coordinate hashes. Sharing a current manifest within one observation does not make the filesystem observation atomic or permit a later call to reuse it.

Every event transaction runs SQLite, outbox and event-chain integrity checks before append. Live metadata and schema-version checks reject rebinding through a retained connection. A retained connection is never an authorization receipt. Existing filesystem observation races are not promoted to an atomic cross-process writer lease: this local pool neither grants repository authority nor replaces the coordination handoff contract.

Streaming SQLite readers retain their prepared statement until exhaustion, failure or early return. Each adapter's row boundary owns that reference and clears it when the cursor closes. This preserves lazy row validation on the supported Node 22.13 runtime, whose original iterator can lose its statement during garbage collection. Event/outbox inspection, conversation queues and Hub graph rebuilding use the same lifetime rule through their local adapter owners. No statement cache, new persistent state, event schema or weaker integrity check is introduced.

Chain verification still freshly reads every event row. An unchanged page reuses its exact-byte receipt. When only the tail page grows, its old prefix can reuse validation only if freshly read raw columns hash to the previous full-page digest and its incoming predecessor matches. New suffix rows undergo the original schema, sequence, predecessor and hash checks. Modified prefixes, truncation, predecessor rewrites and failed checks invalidate the corresponding receipt; no source rows are retained in receipts. This avoids repeating decode/schema/hash work for unchanged historical events without assuming append-only storage cannot be tampered with.

The shared event-envelope schema validates common identifiers, hashes, timestamps, actor fields, required/closed properties and predecessor/provider conditions once at the envelope root. Its six mutually exclusive branches retain each version's exact event-type allowlist. Versions 1 and 2 retain their standalone schemas. This factors declarative constraints rather than skipping validation or caching event values. Accepted values and failure codes remain unchanged; JSON Schema error coordinates follow the factored schema. Differential tests use the exact pre-repair schema snapshot independently of current shared definitions, including every version/type pair, missing fields, invalid values and conditional invariants. Trace and sync consumers continue to reference the same schema ID. Resource qualification requires a separate exact-build cohort.

Generated schema validation indexes static primitive enum lists at the existing loop threshold. Each index belongs to one compiled schema array, and no request value is retained. Short lists, structured enum values and `$data` retain the original compiler path. The public validation facade deep-copies error parameters so a caller cannot mutate the enum definitions used by later requests. Verdicts, complete error contents and ordering retain their existing contract; [ADR-0503](../../../decisions/execution/verification/0503-compile-schema-validators-at-build-time.md) defines the build and retention boundary.

## Project path calculation

Project path calculation reuses native-separator suffixes only for the finite built-in relative-path catalog. The project adapter builds that private map once at module initialization; it contains no repository root, file content, observed identity or authority. Each call freshly resolves its root against the current working directory and returns an independent path object. Absolute, empty, drive-relative, backslash, dot-segment or otherwise uncatalogued values use the original native resolver. The suffix map does not grow with requests or roots, and every filesystem observation and storage guard remains unchanged. Whole-process performance measurement includes initialization; pure path-API equivalence is not installed filesystem acceptance.

## Fresh small metadata reads

Project manifests and writer-coordinate files use a dedicated bounded read adapter for regular files at most 64 KiB. It performs the same complete fresh read and no-follow descriptor recheck without repeated thread-pool round trips. Open uses nonblocking mode to reject a substituted FIFO before it can block at open. A read allocates at most the observed size plus one byte, checks the complete byte count, size, modification/change times and file identity, then reopens and verifies the current path before decoding strict UTF-8. Growth, replacement and symlinks fail closed. Returned content is not cached.

The 64 KiB threshold selects an I/O strategy, not a source-coverage limit. Larger allowed project manifests retain the existing asynchronous reader and original 4 MiB ceiling; writer coordinates retain their existing 64 KiB ceiling. Other project-file reads stay on their current path. Filesystem calls can still stall on a slow or unavailable filesystem; byte bounds are not an unconditional event-loop latency guarantee. This strategy requires its own exact-build resource cohort, including concurrent consumers, and does not relax durability or final current-binding checks.

YAML decoding/schema validation remains a separate project-owned module behind existing configuration exports. No schema, language policy, source parser limit or validation result is cached or weakened.

## Failure and privacy

The pool adds internal `ProjectStorageError` codes `storage_busy` (closed, retiring, or admission bound reached) and `storage_binding_changed` (current project/writer/path identity differs). The optional required-writer admission adds `storage_writer_not_active` when the fresh selected writer differs from the captured requirement. Existing `storage_layout_invalid` and `cleanup_failed` retain their meanings. Required fields remain `code`, a bounded generic message, and an optional cause; no new event or durable state is introduced. Quality recording maps only `storage_writer_not_active` to its existing `writer_not_active` result; other thrown failures map to `unavailable`, never `recorded`. Cleanup failure takes precedence when discarding an inactive handle also fails. Orphaned CAS bytes after a failed final recheck follow the existing CAS retention policy and are not a durable success receipt.

Pool metadata stays process-local. No new report includes raw tasks, conversations, source content, credentials, or provider output. Performance reports retain only hashes, bounded IDs, numeric samples and safe system coordinates.

## In-flight identical artifact writes

The CAS adapter may share one unfinished raw-file write among at most sixteen concurrent `put` calls on the same handle, for individual inputs of at most 64 KiB. Each eligible call snapshots its exact input before awaiting; SHA-256 selects an entry and full byte equality confirms it. Sharing retains at most 1 MiB of eligible input snapshots, in addition to existing I/O buffers. Larger bodies and calls beyond the sharing bound follow ordinary independent streaming writes; they are not rejected or delayed for batching.

The original writer still streams a temporary file, synchronizes it, publishes an immutable hard link, and verifies the actual target. Followers wait for that complete operation, then freshly reject a linked or non-directory hash prefix, read and hash the target and compare it with their own snapshot before returning `created: false`. Each quality recording separately performs its existing artifact verification, fresh repository binding, and durable event transaction. A completed or failed write is removed from the lookup immediately; later calls perform another ordinary durable write. Failed writes give no successful follower receipt. No completed-byte cache, format change, new event, writer authority, timer or cross-handle sharing is introduced. The transient map holds body bytes only during accepted calls and never emits them in diagnostics.

Existing raw readers, streamed inputs, owner-only permissions and per-object deletion retain their storage format. Validation includes concurrent writes, failure retirement and retry, mutation after the original writer's verification, input snapshots, sharing limits, separate handles and read-only handles. The [CAS sharing evaluation](../../../evidence/quality/context-quality/context-quality-cas-sharing-repair.md) retains unsuccessful grouped-container experiments and the exact-build resource cohort; source implementation does not establish resource or installed qualification.

## Observation and recording lifetime

`withRepositoryQualityObservation` starts preparation recording only after the ordinary source preparation has finished. An observation continuation receives an isolated copy of that prepared result and can perform read-only artifact evaluation and owner-managed quality recording while the initial report is being stored. The ordinary `prepareRepositoryQualityContext` operation keeps its awaited receipt contract. Both operations snapshot recording coordinates before asynchronous preparation; neither returns a promise disguised as a durable receipt.

The observation operation drains both its continuation and preparation recording before returning. A read failure still waits for recording; a recording failure still waits for the admitted read. If both reject, an `AggregateError` retains both causes in read/record order. Ordinary recording statuses such as `unavailable` and `writer_not_active` remain statuses, not successful receipts. No background completion, new durable state, event schema, admission queue or body cache is added. The operation retains one additional isolated prepared view for the bounded call lifetime; existing source/report limits and storage admission remain in force. It supplies no hard deadline for an uncooperative caller continuation.

Callers must keep consequential effects outside the observation continuation. The CLI artifact query overlaps verification and its existing observation recording, then waits before emitting output. The common post-turn host overlaps only its first artifact read and policy resolution, then drains before correction proposals, authorized writes or completion decisions. Later artifacts keep their existing sequential lifecycle. Per-artifact policy failure remains attached to that artifact and does not suppress later observations. Existing authority owners and required-completion checks remain unchanged; this API grants no provider, repository-write or publication authority.

The host reader uses two transient internal results. `observed` requires `required`, `contract` and `observation`; it means an observation was obtained, including failed or unavailable verdicts, not that task quality passed. `unavailable` requires `required` and `error` when resolution or reading throws. The parent preserves the requirement flag and maps this to a missing artifact observation. Causes stay within the call and are not serialized into events or retained as a cache.

The [v10 protocol](../../../../benchmarks/context-quality/recording-repair-v10.json) measures the actual observation operation in both arms. The timed interval includes all source work, the continuation, both recording receipts and failure drains. The control disables recording; the candidate retains the original raw CAS and full event-store checks. It changes consumer await ordering explicitly rather than moving durability outside measurement. Historical harness comparisons remain descriptive, and all original gates still apply.

## Candidate SQLite report integration boundary

Status: `recording_source_integrated`; bounded scoped recording is integrated; final resource qualification remains pending. [ADR-0505](../../../decisions/operations/storage/0505-stage-reader-first-sqlite-report-storage.md) defines explicit format selection and reader compatibility.

The current SQLite prototype reduces some recording costs but still fails cold performance. Further implementation must preserve the existing artifact contract instead of copying prototype SQL access into application code. The following boundaries define the next feasibility slice; they do not approve a storage migration or establish resource acceptance.

- The storage contract owns a synchronous report transaction operation that publishes complete bytes with an event. The SQLite adapter owns encoding, bounded chunk reads, hash verification and durable commit. Repository-context owns report meaning and recording outcomes; it must not access a database handle or private event repository.
- `ArtifactStore.get` and `has` must resolve the same content-addressed URI for both existing raw CAS reports and new SQLite reports. An absent SQLite record may fall back to CAS. A present but malformed, incomplete or hash-mismatched record must fail instead of hiding corruption with a second copy. Ordinary artifact writes and streamed inputs retain their existing behavior.
- The adapter snapshots and encodes report bytes inside the synchronous transaction. A separate opaque prepared-report capability remains a possible later optimization, not a current public contract. The encoded report is transient and contains an exact private byte snapshot, content hash, byte count and codec identity. It grants no writer authority and is not a durable receipt. Its bytes and diagnostic causes stay private; public errors contain bounded codes and coordinates. Preparation failure produces no event or successful receipt.
- `report_published` describes only the existing successful recording outcome after a strong atomic report/event commit and both full report verifications. It is not a new public event or an early promise. Fresh repository binding, writer activation and full event integrity checks remain required. Failure of any admitted operation drains its owned work before the caller receives failure.
- The report layout changes persistent meaning and therefore requires a versioned migration and compatible readers; it cannot be added as an unversioned supplemental index. Existing version-3 history and CAS bytes remain readable. Reader-first rollout, predecessor compatibility and rollback evidence remain separate requirements before production activation.
- Capacity must bound decoded report size, encoded size, chunk count, admitted operations and total retained report bytes. Reaching capacity must reject a new report before partial publication. It must never delete immutable events, discard report fields, silently prune referenced bodies or claim a durable receipt. Exact limits and owner-authorized retention behavior must be fixed and tested before adopting the format.
- Verification covers existing CAS reads, mixed history, malformed chunks, bounded decompression, hash conflicts, identical and conflicting retries, project/writer drift, transaction rollback, restart and interrupted commit, read-only handles, capacity exhaustion and exact installed consumers. The complete frozen resource cohort remains required on the rebuilt distribution, with no omitted initialization or report work.

The generic project-storage opener still owns required filesystem validation and legacy migration. This proposal does not waive that work, turn read-only verification into persistence, or move initialization outside the measured operation. ADR-0505 now selects the explicit reader-first format transition, with reviewed patch intent. Retention and actual-artifact qualification remain pending requirements; the bounded observation scope is described below.

### Private adapter implementation status

The first source slice implements an internal report codec and SQLite repository in `event-store-sqlite`. The codec and repository stay private. A provider-neutral report reader now connects the event-store connection to project-storage artifact reads. An explicit version-6 opening with `reportStorage: "sqlite_v1"` creates format 4 inside atomic initialization; default opening preserves format 3. Writable, read-only and offline inspection paths support both formats. The existing-format recording integration is described below; persistent activation is defined below and production rollout remains pending.

The codec snapshots 1–1,048,576 input bytes, rejects shared-memory inputs, and uses `deflate_raw_v1` with compression level 1. Encoded content is limited to 1,049,600 bytes in ordered chunks of at most 800 bytes. Reads require exact ordinals, chunk lengths and counts, a supported codec, complete compressed-stream consumption, exact decoded length and the original SHA-256. Decompression is capped at the declared decoded length. Trailing compressed data, concatenated streams and decompression errors fail closed without exposing native error prose or report bytes. Every successful read returns independently owned bytes.

The repository accepts its connection and lifetime/transaction guards from the event-store owner. It bounds reads at the SQL boundary with row limits and substring reads before allocating complete chunk arrays, so an oversized malformed BLOB cannot force an unbounded read. An absent header with orphan chunks is corruption, not an absent artifact. Insertion validates and privately copies input bytes, then computes their SHA-256 before looking up existing content. A complete verified existing body returns duplicate metadata without recompression; only new content is encoded from the private snapshot. A corrupt existing object still fails and is never silently replaced by a retry. Both complete per-call reads, transaction poisoning and post-commit confirmation remain required. Insertions participate in the caller's transaction, and a failed chunk or owner operation must roll back the report and its associated event together.

Candidate retention limits are 16,384 reports and 64 MiB each of total decoded and encoded content. Quota inspection reads at most 16,385 metadata rows. Capacity rejection precedes a new header or chunk insertion; existing reports remain readable and valid duplicate requests remain idempotent. This bounds retained report cardinality without automatic deletion. Reader restart, versioned migration and mixed CAS reads now have source tests. Owner retention operations and product rollout still need implementation and verification. The [installed report recovery checks](../../../evidence/quality/context-quality/installed-report-recovery.md) cover before/after-COMMIT and after-receipt termination, exact retry and ordinary reopen in CLI/Node format-4 fixtures on Darwin arm64. Twelve further installed cases independently reach all three quotas on both Node versions, preserve atomic rollback and duplicate retries, and leave existing referenced bodies readable. Ordinary and scoped quality operations retain usable plans with unavailable recording at capacity. Owner-retention operations, power loss and other supported-platform qualification remain open.

The new internal failures are `invalid_report` for rejected input bytes or hashes, `report_corrupt` for invalid stored metadata/content, and `report_capacity_exceeded` for a rejected new object. Each carries a stable code and bounded message, with no raw report, SQL row or decompressor error. They do not add public events or authorize recording. Production recording will map a failed storage operation to its existing unavailable outcome after the required drain.

### Reader-first format and privacy behavior

`OutboxStore.reports` is an optional read capability. The SQLite implementation returns complete verified report bytes or null for absence, and rejects reads after connection closure or a live storage-format change. Project storage composes it into artifact `get` and `has`; ordinary and streamed writes retain their existing CAS adapter. An absent report may fall back to CAS. A corrupt header, chunk, stream or hash must not fall back, even if a valid CAS copy exists. Returned bytes have independent ownership and retain the existing Buffer representation.

Format-4 opening verifies its report tables and metadata. Default opening never upgrades a format-3 database solely because a newer reader exists. Explicit activation requires a version-6 opening coordinate and joins schema creation, `user_version` and project metadata in the owning initialization transaction. A failed project check or table conflict leaves the prior schema intact. Existing format-3 binaries remain incompatible with format 4, so rollout and rollback must follow ADR-0505.

Database and SQLite auxiliary files containing reports use the CAS owner-only privacy boundary. Writable format-4 opening secures checked regular-file descriptors; read-only opening rejects unsafe Unix permission bits and redirected files. Permission changes occur before the schema transaction. Windows follows the existing platform permission model; Unix mode tests do not prove ACL behavior. Layout and permission failures use `integrity_failed` with bounded messages; causes remain local error context and are not added to events or receipts.

### Opt-in atomic report transaction

An explicitly selected writable opening exposes `OutboxStore.reportWriter` when format 4 is present. Its synchronous `transact` callback receives `append` and `putReport` through the provider-neutral `ReportTransaction` contract. Report meaning and event payload construction remain application responsibilities. Read-only handles and ordinary openings without a report selection do not expose this writer, including ordinary version-6 openings of an existing format-4 store. The pooled project opener now requests existing-format support only under writer version 6.

Before starting a report transaction, the adapter requires `synchronous=FULL`, `fullfsync=ON` and `checkpoint_fullfsync=ON` and verifies those values on its connection. It retains those stronger settings afterward. The connection owner excludes nested ordinary and report transactions and runs the existing complete integrity check inside `BEGIN IMMEDIATE` before callback writes. SQLite provides the atomic commit; the adapter does not hold a transaction over an asynchronous continuation.

Each `putReport` snapshots its input and performs the private repository's complete verified read before returning in-transaction metadata. A transaction admits at most sixteen report calls, including duplicates. Every accepted call gets another independent complete read after commit, and the outer operation returns only after all those reads pass. Returned in-transaction metadata is not a durable receipt. No completed body is cached or exposed in diagnostics.

A failed report or append operation poisons the transaction even if the callback catches the error. Callback failure, a thenable return or commit failure causes rollback through the connection owner. Transaction methods expire as soon as the callback exits, so escaped methods and delayed asynchronous work cannot append later. A post-commit read failure throws without a success receipt; the commit may already exist, and an exact retry can verify and deduplicate it. This distinguishes failed confirmation from a claim that committed records were undone. Existing error codes retain their meanings: `report_capacity_exceeded` also covers the sixteen-call bound, and `invalid_report` rejects an expired report transaction.

Source tests verify publication/readback ordering, exact retries, explicit capability selection, strong connection settings, callback and commit rollback, caught partial-insertion and event-conflict failures, closed/nested/asynchronous use, batch bounds, corrupt existing content, current metadata and post-commit read failure. Forced process termination checks cover before-commit rollback and after-commit recovery, including interruption before readback and after return. These checks do not prove power-loss behavior, platform-wide durability, owner retention or the original performance gates.

### Recording through the report port

The pooled SQLite opener passes `reportStorage: "existing_sqlite_v1"` only when its current project writer coordinate selects version 6. The adapter offers a report writer only for an already migrated format-4 database. Format 3, including a newly created store, retains CAS and does not gain report tables. Custom backends and ordinary artifact puts keep their existing contracts. Merely selecting writer version 6 does not authorize a format transition.

The recorder serializes its complete snapshot as before. With a report capability it computes the raw SHA-256 and validates the event payload without publishing a CAS object. Otherwise it performs the existing CAS write and verification. The same queue admits at most sixteen operations, snapshots each optional private report at admission and clones each prepared draft. This adds at most sixteen 1 MiB report snapshots per handle; they are released when the batch settles and are never a completed report cache. Shared-memory or out-of-bound snapshots are rejected before admission.

All preparations in a fixed batch settle before the fresh final binding observation. SQL publication then uses the report port, compares each returned content hash with its draft's expected hash and appends with the stored timestamp on exact retries. The adapter owns complete event integrity, atomic commit, strong synchronization and both full report reads. The queue resolves no receipt until the outer transaction returns. Failed preparation still drains every admitted preparation. A failed binding, hash comparison, conflicting event or adapter operation produces no fallback CAS write and no successful recording outcome.

Source tests cover byte snapshot isolation, delayed and failed final guards, mismatched hashes, failed preparation drains, existing-format selection without migration, actual SQL recording, exact retry, conflicting retry rollback, corrupt-body refusal, concurrent receipts and writer rollback. Built CLI and Node fixtures must additionally prove that their actual shared modules record preparation and verification reports through this path. These functional checks do not establish human-reviewed quality or the frozen resource gates.

The existing-format-only stage could not initialize a cold database. The persistent selection below resolves that source gap. Final measurement must still begin without event schema or project metadata and include their initialization; a precreated database or a writer-6-only authority claim remains invalid.

### Persistent selection and cold initialization

`@lervo/project` owns version-1 report selection through `planReportStorageActivation`, `applyReportStorageActivation`, `inspectReportStorageCoordinate` and `recoverReportStorageActivation`. The coordinate is stored at `.lervo/data/report-storage.json`; `.report-storage-pending` fences an interrupted publication. No database is opened or created by these operations. Default absence means no permission to create the new format.

The coordinate requires `schemaVersion`, `format: "sqlite_v1"`, `activationId` and `evidence`. Evidence requires its own schema version, project ID, ISO observation time, exact writer-coordinate hash, a strictly sorted list of one to sixty-four readers, and a rollback artifact. Each reader supplies its ID, peer identity hash or null, artifact hash and exact `[3, 4]` readable-storage formats. Rollback supplies its artifact hash and the same formats. Hashes and IDs are bounded, unknown fields are rejected, and the complete file is limited to 64 KiB. The activation ID binds canonical evidence. No report body, task, credential or provider output belongs in this state.

Planning requires the current writer-6 coordinate and exact reader/peer membership from its validated activation inventory. Evidence must be no older than five minutes or more than thirty seconds in the future. Applying reconstructs the plan, checks its approval ID and revalidates current evidence; a newer observation timestamp is permitted when every other coordinate is unchanged. Activation callers verify the declared binary capabilities and rollback evidence before submitting a plan. These APIs validate evidence bindings, not remote software or operational rollback. The immutable selection persists through writer rollback and does not claim its historical inventory is still a current observation.

Publication uses an exclusive owner-only pending file, file and directory synchronization, and a non-overwriting hard link. Only after the final content is verified is the pending file removed and the directory synchronized again. Recovery finishes a valid already-approved publication without replacing owner bytes; incomplete or conflicting data remains a visible failure. The two fixed paths bound metadata cardinality. There is no automatic selection replacement, database down-migration or report deletion.

The new failures are `report_storage_invalid` for invalid evidence or unsafe/unverifiable files, `report_storage_stale` for invalid approval, changed inputs or stale observations, and `report_storage_recovery_required` for a pending or conflicting publication. Required error fields are a stable code and bounded message; optional causes stay private. Underlying publication I/O failures also return no receipt and may leave a pending record. No new event type is introduced.

Project storage reads the selection during opening and captures its content hash on the handle. Under writer version 6 it requests explicit SQL initialization; a backend that ignores the selection is rejected before artifact opening. The pool independently reads the selection on its binding observations and compares it with the opened handle and later baseline. Removal, replacement or pending publication rejects reuse. Ordinary format-3/CAS behavior remains unchanged without selection, and read-only opening does not create a database. Cold recording now performs the real format-4 schema and project binding initialization inside its normal operation; the resource protocol must retain that work.

### Bounded observation commit scope

`withRepositoryQualityObservation` registers a private scope after ordinary source preparation and before starting its initial recording. The recorder owns this registry alongside its existing storage pool and commit queue. Keys use the normalized root and generated request ID. At most eight roots and sixteen scopes per root are retained; excess or duplicate registration uses ordinary recording. Scopes retain admission flags and group membership only; groups retain a ready promise, member map and timer. Neither retains report bytes, a storage handle or an authority observation.

Only SQL report queue entries use the scope. Registrations for one root join a group until its first successful queue admission, explicit member completion or eighth registration freezes membership. Admission is announced only after the queue has reserved its existing bounded slot and snapshotted the report. Eight observation pairs fit the sixteen report slots; later registrations enter a separate group and cannot extend the first group's membership or deadline.

Each member finishes after both distinct preparation and verification kinds are admitted, or when its observation continuation completes in `finally`. Repeated admission of one kind cannot stand in for the other. The group releases only after all its members finish, or after a referenced fifty-millisecond deadline measured from its first registration. Later members never extend that deadline. Release is idempotent, clears the timer, removes all registry entries and resolves the shared ready promise. A stale member's later cleanup cannot remove a replacement registration. Disabled recording creates no scope; the ordinary awaited preparation API retains its existing receipt contract.

The commit queue freezes only entries whose scopes have released, plus ordinary unscoped entries. Held scopes cannot delay an unrelated ready report. Once selected, every preparation in that fixed batch still settles before the fresh final binding check and the original synchronous transaction. All admitted reports in a released group can share one durable commit, with two independent full reads per report and both receipts retained. Timeout, late arrival or lease rotation can split them across commits; this is a bounded scheduling fallback, not a successful performance result or permission to omit a record. Timer waits and every resulting commit remain in the measured operation.

An observation failure still releases and drains its accepted preparation recording. A failed preparation still drains its admitted sibling before rejecting the batch. Registry release does not release a pool borrow, resolve a durable receipt or bypass a writer check. All three complete source preparations, the read-only outcome verifier, event/report validation and final authority observations remain unchanged. No new persistent state, public event or telemetry claim is added.

### Lazy optional CAS capabilities

`FileSystemCas.open` and `openReadOnly` retain all directory creation and real-path checks. They no longer construct native synchronization or CAS batches merely because a handle exists. A small ordinary put initializes its synchronization capability at first use; an actual object read or native publication initializes its CAS capability at first use. Each handle remembers that capability or its observed absence. Read-only handles never initialize a write synchronizer, and large/streamed writes preserve their existing ordinary synchronization path.

A SQL-backed report read or write that never reaches CAS therefore does not load unused native code. This is not input priming, an artifact-result cache or a removal of CAS path guards. Asset validation still occurs when the capability is first used. Initialization errors fail that operation without a success receipt or silent error fallback. Missing optional capabilities retain ordinary complete I/O and hashing. First-use cost belongs to the actual operation and the unchanged resource accounting.

### Physical pages for new report databases

An explicit `sqlite_v1` opening selects 2 KiB physical SQLite pages only when the database has zero pages, before WAL configuration and schema initialization. Setting readback must match or opening fails with `integrity_failed`. Existing databases keep their actual page size, including a format-3 database later migrated to format 4. No `VACUUM`, index removal, schema-version change or report truncation occurs. The report codec and both full readbacks remain unchanged. SQLite readers already interpret page size from the database header; [the page-size contract](https://www.sqlite.org/pragma.html#pragma_page_size) governs this physical layout.

The report checkpoint policy derives its page count from the same 1 MiB target, preserving the prior 256-page behavior for existing 4 KiB databases. That target excludes WAL frame headers and remains a scheduling threshold, not a hard storage bound. Smaller initial pages address measured cold schema/WAL overhead; only exact-artifact resource measurement can establish the retained-state gate. All initialization work remains inside the ordinary recording operation.
