# Bounded context-quality recording storage reuse

Status: `implemented_source`
As of: 2026-10-10

The [rejected active-resource cohort](../../../evidence/quality/context-quality/context-quality-priority4-evaluation.md) found repeated project-storage open and chain-validation cost. This repair retains the [outcome/event contract](outcome-and-event-rollout.md), explicit writer activation, per-attempt CAS reports, and durable event receipts. It adds no model call, event schema, delivery claim, or production activation.

## Ownership and bounds

`project-storage` owns a bounded pool of overlapping operations. `repository-context` owns one pool for quality recording only; other project-storage callers retain their existing lifetime. The pool admits at most eight repository roots and 16 pending operations per root, including executing operations. A handle rotates before its next operation after 64 uses or one second of age, whichever occurs first. After 50 ms idle, it closes. An active filesystem operation is allowed to finish; the age limit does not abort in-progress I/O. Timers do not keep a terminal process alive, and durable commits complete before success is returned. Explicit pool close stops admission, drains accepted operations, and closes all handles.

Preparation/verification reports are cloned and serialized before admission, with the existing 1 MiB byte ceiling. The serialized report replaces the cloned report body while waiting. Queue entries are transient, bounded by admission, and removed when settled. Pool entries retain a handle, bounded identity coordinates and scheduling metadata, never a conversation or source cache. Operation errors invalidate the lease for new or pending writes; admitted borrowers drain before the handle closes. Age/use rotation also drains admitted borrowers, without invalidating their current observations. Cleanup failure remains a poisoned occupied entry rather than silently admitting another handle; explicit close reports the aggregate failure. Process termination releases operating-system handles without an uncommitted success receipt.

Pooled writers request SQLite auto-checkpointing after each committing transaction and minimum retained journal size. `synchronous=FULL` remains unchanged; independent default storage openers keep their existing checkpoint policy. This reclaims transient WAL space without deleting canonical records. Active external readers may delay checkpoint progress, so this is not an unconditional byte ceiling. See the [SQLite checkpoint and journal-size contract](https://www.sqlite.org/pragma.html#pragma_journal_size_limit).

Independent CAS preparation can overlap. Before starting CAS work, a quality-owned commit queue admits a preparation callback, with at most 16 admitted operations per storage handle including an in-flight batch. The first settled preparation schedules the next event-loop turn, which freezes the pending membership. Every included preparation must settle before one fresh shared-handle binding observation and a synchronous commit. Later arrivals remain in a separate batch with a separate observation. The existing pool bounds roots and keeps borrowers alive through preparation and commit. Completed authority observations are never cached for later work.

An artifact preparation failure rejects its entire batch without an event transaction. All other included preparations still drain before any rejection is returned, so a caller cannot release the storage handle while an accepted CAS effect is still running. Excess admission rejects before invoking its callback. A slow included artifact can delay otherwise ready peers; cardinality and report sizes are bounded, but this is not a hard filesystem deadline or an abort of in-progress I/O. The queue retains preparation promises and bounded metadata only; the recording owner retains its already-bounded serialized report until preparation completes.

Event identity lookup, complete integrity verification and every append in that batch share one synchronous SQLite transaction. Exact retries use the stored timestamp and deduplicate, including retries within a batch. Success resolves for each attempt only after the durable commit; any binding, integrity, conflicting-event or commit failure rejects the entire batch and rolls back its appends. Orphaned CAS reports remain subject to existing retention. Drafts are copied when preparation resolves, contain bounded event metadata rather than report bodies, and are released at settlement. The recording owner snapshots request/report input before admission. The queue introduces no durable state, partial-success receipt or provider effect. Reuse never extends a transaction across an asynchronous callback.

A borrow also rechecks its invalidation flag after its asynchronous binding observation. Failure in another borrower while that read is pending cannot produce a current guard from an already invalidated lease.

## Current identity and integrity

A pool may capture one required event schema version (1–6) at construction. Quality recording requires version 6. Before every new storage open, including after idle, age or use retirement, the pool freshly inspects the writer and rejects inactivity before opening either backend. For an existing handle, the initial borrow checks that requirement within its existing fresh writer and path observation. The recorder no longer performs a separate preliminary inspection. No retained-handle hint or previously observed writer grants admission. Pool closure, admission bounds and poisoned cleanup are evaluated before writer inspection; simultaneous failures retain those pool meanings.

The callback’s final current-binding guard still performs a fresh observation without the initial admission requirement. A writer rollback after admission therefore remains a binding failure and recording returns `unavailable`, including after CAS preparation. An initially inactive writer returns `writer_not_active`. Current writer checks are observations, not an atomic cross-process writer lease.

Project manifest decoding may reuse a validated representation only after the existing loader freshly reads and checks the entire current file. The private project parser retains at most eight exact content strings of at most 64 KiB each, with a fixed one-second lifetime and unreferenced retirement timers. Hits do not extend retention. Every returned manifest is isolated from the retained value; changed content, expiration or eviction requires decoding again. Invalid input is never retained and larger accepted manifests keep the existing uncached path. This is transient decoding reuse, not a filesystem observation or authority cache; project layout, activation transactions, writer coordinates and storage bindings are still checked freshly. Generic YAML consumers do not use this parser.

Bootstrap remains the existing verified project-storage opener, including relocation, project binding and complete open-time integrity checks. Each borrowed operation freshly observes the project ID, writer coordinate bytes, and real directory/file identities of the repository, `.lervo`, durable/rebuildable roots, CAS roots and event database. Replacement, symlinks, writer changes or invalid activation transactions reject reuse. The recording callback repeats that observation after asynchronous CAS preparation and immediately before its synchronous event transaction.

Every event transaction runs SQLite, outbox and event-chain integrity checks before append. Live metadata and schema-version checks reject rebinding through a retained connection. A retained connection is never an authorization receipt. Existing filesystem observation races are not promoted to an atomic cross-process writer lease: this local pool neither grants repository authority nor replaces the coordination handoff contract.

Streaming SQLite readers retain their prepared statement until exhaustion, failure or early return. Each adapter's row boundary owns that reference and clears it when the cursor closes. This preserves lazy row validation on the supported Node 22.13 runtime, whose original iterator can lose its statement during garbage collection. Event/outbox inspection, conversation queues and Hub graph rebuilding use the same lifetime rule through their local adapter owners. No statement cache, new persistent state, event schema or weaker integrity check is introduced.

Chain verification still freshly reads every event row. An unchanged page reuses its exact-byte receipt. When only the tail page grows, its old prefix can reuse validation only if freshly read raw columns hash to the previous full-page digest and its incoming predecessor matches. New suffix rows undergo the original schema, sequence, predecessor and hash checks. Modified prefixes, truncation, predecessor rewrites and failed checks invalidate the corresponding receipt; no source rows are retained in receipts. This avoids repeating decode/schema/hash work for unchanged historical events without assuming append-only storage cannot be tampered with.

The shared event-envelope schema validates common identifiers, hashes, timestamps, actor fields, required/closed properties and predecessor/provider conditions once at the envelope root. Its six mutually exclusive branches retain each version's exact event-type allowlist. Versions 1 and 2 retain their standalone schemas. This factors declarative constraints rather than skipping validation or caching event values. Accepted values and failure codes remain unchanged; JSON Schema error coordinates follow the factored schema. Differential tests use the exact pre-repair schema snapshot independently of current shared definitions, including every version/type pair, missing fields, invalid values and conditional invariants. Trace and sync consumers continue to reference the same schema ID. Resource qualification requires a separate exact-build cohort.

## Project path calculation

Project path calculation reuses native-separator suffixes only for the finite built-in relative-path catalog. The project adapter builds that private map once at module initialization; it contains no repository root, file content, observed identity or authority. Each call freshly resolves its root against the current working directory and returns an independent path object. Absolute, empty, drive-relative, backslash, dot-segment or otherwise uncatalogued values use the original native resolver. The suffix map does not grow with requests or roots, and every filesystem observation and storage guard remains unchanged. Whole-process performance measurement includes initialization; pure path-API equivalence is not installed filesystem acceptance.

## Fresh small metadata reads

Project manifests and writer-coordinate files use a dedicated bounded read adapter for regular files at most 64 KiB. It performs the same complete fresh read and no-follow descriptor recheck without repeated thread-pool round trips. Open uses nonblocking mode to reject a substituted FIFO before it can block at open. A read allocates at most the observed size plus one byte, checks the complete byte count, size, modification/change times and file identity, then reopens and verifies the current path before decoding strict UTF-8. Growth, replacement and symlinks fail closed. Returned content is not cached.

The 64 KiB threshold selects an I/O strategy, not a source-coverage limit. Larger allowed project manifests retain the existing asynchronous reader and original 4 MiB ceiling; writer coordinates retain their existing 64 KiB ceiling. Other project-file reads stay on their current path. Filesystem calls can still stall on a slow or unavailable filesystem; byte bounds are not an unconditional event-loop latency guarantee. This strategy requires its own exact-build resource cohort, including concurrent consumers, and does not relax durability or final current-binding checks.

YAML decoding/schema validation remains a separate project-owned module behind existing configuration exports. No schema, language policy, source parser limit or validation result is cached or weakened.

## Failure and privacy

The pool adds internal `ProjectStorageError` codes `storage_busy` (closed, retiring, or admission bound reached) and `storage_binding_changed` (current project/writer/path identity differs). The optional required-writer admission adds `storage_writer_not_active` when the fresh selected writer differs from the captured requirement. Existing `storage_layout_invalid` and `cleanup_failed` retain their meanings. Required fields remain `code`, a bounded generic message, and an optional cause; no new event or durable state is introduced. Quality recording maps only `storage_writer_not_active` to its existing `writer_not_active` result; other thrown failures map to `unavailable`, never `recorded`. Cleanup failure takes precedence when discarding an inactive handle also fails. Orphaned CAS bytes after a failed final recheck follow the existing CAS retention policy and are not a durable success receipt.

Pool metadata stays process-local. No new report includes raw tasks, conversations, source content, credentials, or provider output. Performance reports retain only hashes, bounded IDs, numeric samples and safe system coordinates.

## Verification and acceptance

Tests cover idle/use/age retirement, bounded roots and queues, drain/close, operation and cleanup failure, project/database/CAS replacement, post-CAS writer rollback, corrupt chains and metadata/schema rebinding, concurrent attempts and exact retry deduplication. Tail-page fixtures compare against independent full verification and reject modified prefixes, broken predecessors, deletion and rollback.

The repair uses a new exact-build protocol and retains the rejected original cohort. Profiles, samples, workload composition, latency/CPU/process/RSS/storage gates, failed-sample retention and provider-call ceiling remain unchanged. Resource improvement cannot establish the missing real-family quality population, provider outcomes, or installed acceptance.

## In-flight identical artifact writes

The CAS adapter may share one unfinished raw-file write among at most sixteen concurrent `put` calls on the same handle, for individual inputs of at most 64 KiB. Each eligible call snapshots its exact input before awaiting; SHA-256 selects an entry and full byte equality confirms it. Sharing retains at most 1 MiB of eligible input snapshots, in addition to existing I/O buffers. Larger bodies and calls beyond the sharing bound follow ordinary independent streaming writes; they are not rejected or delayed for batching.

The original writer still streams a temporary file, synchronizes it, publishes an immutable hard link, and verifies the actual target. Followers wait for that complete operation, then freshly reject a linked or non-directory hash prefix, read and hash the target and compare it with their own snapshot before returning `created: false`. Each quality recording separately performs its existing artifact verification, fresh repository binding, and durable event transaction. A completed or failed write is removed from the lookup immediately; later calls perform another ordinary durable write. Failed writes give no successful follower receipt. No completed-byte cache, format change, new event, writer authority, timer or cross-handle sharing is introduced. The transient map holds body bytes only during accepted calls and never emits them in diagnostics.

Existing raw readers, streamed inputs, owner-only permissions and per-object deletion retain their storage format. Validation includes concurrent writes, failure retirement and retry, mutation after the original writer's verification, input snapshots, sharing limits, separate handles and read-only handles. The [CAS sharing evaluation](../../../evidence/quality/context-quality/context-quality-cas-sharing-repair.md) retains unsuccessful grouped-container experiments and the exact-build resource cohort; source implementation does not establish resource or installed qualification.

## Observation and recording lifetime

`withRepositoryQualityObservation` starts preparation recording only after the ordinary source preparation has finished. An observation continuation receives an isolated copy of that prepared result and can perform read-only artifact evaluation and owner-managed quality recording while the initial report is being stored. The ordinary `prepareRepositoryQualityContext` operation keeps its awaited receipt contract. Both operations snapshot recording coordinates before asynchronous preparation; neither returns a promise disguised as a durable receipt.

The observation operation drains both its continuation and preparation recording before returning. A read failure still waits for recording; a recording failure still waits for the admitted read. If both reject, an `AggregateError` retains both causes in read/record order. Ordinary recording statuses such as `unavailable` and `writer_not_active` remain statuses, not successful receipts. No background completion, new durable state, event schema, admission queue or body cache is added. The operation retains one additional isolated prepared view for the bounded call lifetime; existing source/report limits and storage admission remain in force. It supplies no hard deadline for an uncooperative caller continuation.

Callers must keep consequential effects outside the observation continuation. The CLI artifact query overlaps verification and its existing observation recording, then waits before emitting output. The common post-turn host overlaps only its first artifact read and policy resolution, then drains before correction proposals, authorized writes or completion decisions. Later artifacts keep their existing sequential lifecycle. Per-artifact policy failure remains attached to that artifact and does not suppress later observations. Existing authority owners and required-completion checks remain unchanged; this API grants no provider, repository-write or publication authority.

The host reader uses two transient internal results. `observed` requires `required`, `contract` and `observation`; it means an observation was obtained, including failed or unavailable verdicts, not that task quality passed. `unavailable` requires `required` and `error` when resolution or reading throws. The parent preserves the requirement flag and maps this to a missing artifact observation. Causes stay within the call and are not serialized into events or retained as a cache.

The [v10 protocol](../../../../benchmarks/context-quality/recording-repair-v10.json) measures the actual observation operation in both arms. The timed interval includes all source work, the continuation, both recording receipts and failure drains. The control disables recording; the candidate retains the original raw CAS and full event-store checks. It changes consumer await ordering explicitly rather than moving durability outside measurement. Historical harness comparisons remain descriptive, and all original gates still apply.

## Native file synchronization source candidate

The [native synchronization implementation](../../../evidence/quality/context-quality/context-quality-native-sync-implementation.md) adds a filesystem-durability adapter and per-store queue for known-size CAS puts of at most 64 KiB. Up to sixteen preparations drain before one fixed group synchronizes. Fresh descriptor eligibility rejects non-local, non-APFS or mixed-device/filesystem groups before synchronization and selects ordinary per-file fallback. Native failures reject after drain; no target is published before synchronization succeeds. Streams, larger bodies and unavailable native capabilities retain ordinary file synchronization. Raw storage, digest verification, writer bindings and event commits are unchanged.

The adapter owns duplicated descriptors and asynchronous teardown, validates finite integer inputs, and uses the pinned same-device fsync/F_FULLFSYNC contract. Build metadata binds source and binary identity, and performance artifact hashes include native bytes and their manifest. This is source implementation only: CLI/Hub/Node packaging, release archive contracts, minimum-runtime consumers and a new frozen cohort remain required. Existing v12 resource, reviewed-quality and installed acceptance statuses are unchanged.

The [native source-only diagnostic](../../../evidence/quality/context-quality/context-quality-native-sync-implementation.md#source-only-resource-result) passes six latency groups and all process/RSS/storage/correctness checks, but both cold latency and every CPU gate remain open. It binds native artifact bytes and preserves all 380 workers. Packaged-consumer qualification still requires explicit native asset distribution and supported-platform checks.
