# Conversation knowledge-job assignment provenance

A background conversation-knowledge assignment is ordinary workforce state with an exclusive `knowledgeJob` provenance. Its version-1 record requires a deterministic job ID, exact completion-event ID and hash, source conversation-event ID, nullable content-bound source-manifest hash, and the durable agent ID. The nullable manifest hash means only that a historical `baseline_valid` completion lacks a version-3 source manifest; it never establishes content currency. A workstream ID, current role version and contract hash, scoped expected paths, acceptance criteria, and verification suite remain mandatory. Routine and topology provenance cannot be combined with this provenance.

The assignment ID is deterministic for project and completion event. Exact replay returns the same record; any changed provenance, role, path scope, or acceptance contract under that ID is a conflict. A claim requires the named active agent, current role and capability binding, scoped paths, and an unexpired exclusive lease. A different agent cannot take the job merely by sharing its role or provider.

The `assignment.created` event retains `knowledgeJobContractVersion`, `knowledgeJobId`, `knowledgeCompletionEventId`, `knowledgeCompletionEventHash`, `knowledgeSourceConversationEventId`, `knowledgeSourceManifestHash`, and `knowledgeAgentId` together. Missing or malformed coordinates fail event validation and roll back creation. It never includes message text, source paths or bytes, provider output, absolute paths, credentials, or raw errors. Creation proves only deterministic assignment provenance, not queue claim, agent execution, semantic review, integration, or knowledge currency. Those require their distinct lease, workspace, and knowledge-outcome evidence. A stale source, failed claim, or changed replay is not success.
