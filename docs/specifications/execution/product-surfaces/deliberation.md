# Deliberation product integration

## Responsibility and applicability

Formal deliberation is a bounded decision workflow, not a synonym for multi-agent conversation.

| Situation                                                                                | Default path                           |
| ---------------------------------------------------------------------------------------- | -------------------------------------- |
| Ordinary question, progress update, or role-relevant discussion                          | Multi-party conversation               |
| Routine code or document verification                                                    | Owning work and verification contracts |
| Independent implementation acceptance                                                    | Outcome supervision or assigned review |
| Explicit independent challenge, competing designs, consensus, or high-assurance decision | Formal deliberation                    |
| Ambiguous language or agent suggestion to debate                                         | Recommend or clarify; do not start     |

The application composes existing deliberation control, queue, runtime, artifact, verification, and event contracts. It owns origin correlation and product queries but cannot decide convergence, weaken policy, or promote a decision.

## Origin and participant binding

Before queue execution, the application binds:

- Project, conversation, thread, and source conversation-event coordinates.
- Requester participant and authorized principal.
- Policy ID, policy hash, and requested topic digest.
- Deliberation ID and start idempotency coordinate.
- The exact participant, hired agent, role revision, provider policy, and surface identity resolved for each policy role, or an explicit policy-only role disposition.

Origin is a rebuildable join between the deliberation queue's durable source event and the immutable conversation-event target. Every new start job stores a `ConversationDeliberationOriginBinding` containing the required conversation ID, nullable thread ID, requester-participant ID, and binding digest; the digest also binds the project and source event. Legacy all-null origin columns remain readable but cannot satisfy the product projection. Partial or malformed bindings are queue-integrity failures. These are opaque Lervo coordinates: principal identity remains hashed, and native platform IDs, credentials, and request content are excluded from the queue.

`ConversationApplication.inspectDeliberationOrigin` is the read-only application boundary for this join. Given project and deliberation IDs, it returns the queue-validated source event and origin binding, or `null` when deliberation is unconfigured, missing, or legacy. It never infers coordinates from notification configuration. Decode or digest failure propagates as an integrity failure instead of becoming `null`.

Participant identity uses existing organization deliberation-participant bindings; no second origin, chat, or identity store is added. The projection contains Lervo coordinates, not native Discord channel or message IDs. Transport adapters recover current platform delivery coordinates through existing mappings. Missing or contradictory origin or participant evidence fails before provider execution.

A product policy names the people or stakeholder perspectives required for the decision, not generic workflow stages. The decision owner represents the product outcome. Independent reviewers cover affected installed-user, core and knowledge, compatibility, operations, security, and observability concerns. The verifier remains separate. A policy-only role is labeled honestly and never presented as a hired agent. A recurring policy's installed acceptance requires reviewed bindings to the intended hired agents; a convenient provider assignment or a role named only `proposer` or `reviewer` is not a stakeholder binding.

## Surface behavior

Discord uses one bound decision thread for a start acknowledgment, writing-gated artifact updates, and one terminal result. The main channel may receive coalesced start and terminal notices. Replies, restart recovery, and terminal delivery remain attached to the original Lervo origin. Using the validated application query, the terminal coordinator targets exactly one conversation and thread, replies to the original source event, and mentions the requesting participant. A legacy `null` origin may fan out to configured conversations only as an operational notice; it has no reply coordinate and never fills `originDeliveryCoordinate`.

Every reply-bound outbound record carries its immediate source event and the immutable event it must answer. Synthetic deliberation signals retain their own event identity for replay, while `replyToEventId` resolves the original native Discord message. Platform mapping must prefer the explicit reply coordinate and may fall back to the source event only for predecessor records. A signal-generated product reply delivered as a standalone Discord message does not satisfy origin-bound acceptance.

Natural-language acknowledgments, stakeholder contributions, and terminal replies are product presentation, not queue or operator diagnostics. Unless a human explicitly requests diagnostics, they omit deliberation IDs, artifact and claim counts, writing-gate status, retry instructions, checkpoint terminology, canonical-history repair guidance, and raw failure codes. A start acknowledgment says stakeholder review began and its result will return to the same conversation; it never reports zero artifacts as progress. Each proposal, objection, revision, verification explanation, and decision appears as the writing-gated participant contribution as soon as its canonical event is available, without waiting for the whole worker process to exit. The thread therefore reads as a progressing discussion rather than a delayed event dump. Operational details remain available through activity, trace, doctor, and exact diagnostic commands.

Every acknowledgment, artifact update, failure notice, and terminal result is an observation-only publication for other agents. Outbound and normalized inbound contracts carry `audienceParticipation: observe_only`; interaction records `publication_observation_only` without semantic relevance, typing, or provider execution. Discord preserves this classification in versioned transport metadata, not visible text, and history recovery restores it after restart. Missing or unsupported transport encoding fails before ambiguous publication. The field contains no content or platform identifier and grants no authority. A human reply to the visible result is a distinct eligible event that may continue the conversation or explicitly address an agent.

The originating human message selects the response language. A Korean request uses the versioned Korean conversation writing contract for proposals, reviews, verification explanations, revisions, the final decision, deterministic acknowledgments, failures, terminal presentation, and policy-owned participant labels when present. Repository documentation remains English by default. Surface language neither changes canonical evidence coordinates nor relaxes writing verification.

Every stakeholder prompt states before drafting that the publication will appear verbatim in the originating conversation. It requires the conclusion and user-visible impact first, followed by either the concrete next action the speaker owns or an explicit statement that no action is required. Unmet dependencies are approval conditions or missing evidence, never work delegated to another participant. Proposal, revision, and decision turns are bounded to 450 English words or Korean space-delimited words and eight paragraphs; review and verification turns use smaller bounds. These are generation bounds in addition to, not replacements for, the unchanged independent writing gate.

Publication repair receives the exact failed semantic check IDs and permits at most one fresh, language-matched retry. A `direct_result_and_action` repair states the review's result and user impact; it never assigns the next action to another person, named role, owner, reviewer, verifier, user, or team. Dependencies are objective approval conditions or missing evidence. A plain-language repair treats topic and shared-artifact wording as evidence, not reusable prose. It removes avoidable internal names and every path, file or command name, abbreviation, state label, hash, and machine identifier. Product, protocol, stage, and version labels become observable behavior unless the name is material and explained inline. The replacement is limited to eight paragraphs and 450 English words or Korean space-delimited words; it does not restate the complete design. Exact evidence remains attached through managed events and context receipts. A failed or invalid semantic-evaluator invocation is infrastructure evidence, not a writer-repairable defect: publication terminates without spending the bounded rewrite. Repeating an undirected rewrite after the same failed check is invalid recovery.

Deictic requests such as "review this design" bind the exact current human message and bounded prior human anchors into the topic. Recent agent and system chatter remains available to ordinary conversation but cannot evict the most recent human design context from deliberation scope. The queue stores only the bounded topic and its existing digest; native platform identifiers and credentials remain excluded.

Natural-language effect resolution may encounter a transient repository snapshot failure while replica bytes change. Because this occurs before provider start, the interaction retries only within the configured response-attempt bound and takes a fresh exact snapshot. Exhaustion fails closed with the normal language-matched context-unavailable reply, creates no deliberation job, and never treats a partial snapshot as evidence.

Publishable deliberation prose includes exact repository paths only when location is necessary to understand the conclusion. If the separate writing evaluator rejects audience language, the single allowed fresh-turn repair forbids paths, file and command names, backticked names, abbreviations, repository state labels, hashes, and machine identifiers. It restates checked behavior and significance in plain language. Canonical execution events, loaded-context receipts, and artifact evidence retain exact provenance. The repair receives neither evaluator prose nor the quarantined draft, cannot weaken the writing gate, and creates no deliberation artifact unless the complete gate passes.

For `converged`, the terminal reply contains the writing-gated final decision body recovered from its canonical decision-artifact coordinate. For `no_consensus`, it states that no disputed conclusion was accepted and includes the last writing-gated review. For `failed` or inconclusive reconciliation, it states plainly that no partial result was accepted. Before publication, the coordinator verifies project, deliberation, terminal status, artifact coordinate, content hash, and bounded bytes. A missing or contradictory final artifact leaves notification retryable; it never falls back to status plus artifact count.

Each new `deliberation.artifact.recorded` repository event is read through the structured-artifact validator used by the host-neutral product projection. The Discord projector emits one `signal.raised` with `signalCode: deliberation.artifact.recorded`, the original conversation and thread, the original source event as reply target, and the artifact event time. It reads the writing-gated Markdown body from the repository artifact store, verifies recorded byte count and content hash, and copies it into the conversation artifact store under the policy-bound human-facing participant name. The visible message is the labeled participant proposal, objection, revision, verification explanation, or decision. It does not synthesize round numbers, role IDs, claim counts, or gate status. Those coordinates remain in canonical events for activity, trace, search, and future first-party views without becoming chat prose. Prompts, private reasoning, unverified provider payloads, credentials, and native Discord identifiers remain excluded.

The canonical contribution remains complete even when a channel has a smaller presentation limit. Discord deterministically presents an observation-only excerpt within its 2,000-character bound and states that the complete contribution remains available through Lervo records and unified search. Human-directed replies are never silently shortened. The delivery receipt therefore proves the bounded Discord projection, while the original artifact hash and conversation outbound retain the complete writing-gated content.

The rebuildable `deliberation-artifact-cursor.json` stores schema version, exact cursor kind, project ID, integration ID, last inspected repository-event sequence, and update time. Missing state checkpoints the current head to avoid surprise historical replay. For a bound origin, advancement follows exactly one durable interaction outbound; a crash before advancement is deduplicated by deterministic source-event identity. Platform delivery remains the responsibility of the interaction outbox and adapter receipt. A legacy event without origin is skipped and cannot satisfy product acceptance. Invalid structured evidence, unavailable interaction ownership, or zero or multiple responding policies fails the worker before advancement. Startup validates the required proactive signal subscription.

Settlement and reconciliation atomically create a durable notification obligation. `pending` is host-ready, `leased` is held by one bounded worker, and `accepted` means the normalized event and exactly one writing-gated outbound were committed to the interaction lifecycle. Project ID, deliberation ID, terminal summary, and settlement time are required and immutable. A lease adds worker, attempt, and expiry fields; acceptance adds a Lervo conversation-event ID and time. The obligation stores no topic, message body, principal, native Discord identifier, credential, provider payload, or delivery receipt. An expired lease is reclaimed with its original settlement time, preserving stable event identity. Missing origin uses only the explicit legacy fallback. Missing fallback, missing interaction runtime, zero responding participation policies, or multiple responding policies leaves the obligation unaccepted and exposes a retryable configuration failure. Adapter rejection and uncertain send retain existing interaction and platform replay meanings.

`accepted` does not claim delivery. `originDeliveryCoordinate` stays `null` until the accepted event joins an outbound with valid writing evidence and a durably stored adapter receipt. A crash after interaction acceptance is recovered by existing inbox, outbox, and platform replay contracts without regenerating the deliberation or terminal obligation.

The application enumerates bounded uncertain start and resume jobs with immutable uncertainty times for restart recovery. The coordinator invokes only the authoritative reconciliation source, never original provider execution. A confirmed result settles the owning queue and atomically creates its notification. After bounded inconclusive inspections, owner attention uses the uncertainty time in a stable event identity and checks the append-only interaction inbox for the same logical source key before publication. This suppresses duplicates across runtime restarts and the earlier timestamp-derived event identity. Incomplete or inconsistent history remains uncertain and produces no terminal claim.

The installed process adapter prepends the running Node executable's directory to child `PATH` before invoking the configured Lervo CLI. This preserves the explicit runtime dependency of `/usr/bin/env node` script entrypoints, including systemd services whose inherited `PATH` omits the private runtime installation. Child stdout and stderr remain bounded; user-facing replies never include child stderr. Operator diagnostics retain typed launch, exit, output, source, or artifact failure meaning instead of relabeling all process failures as repository-history explanations.

The future first-party decision room renders the same proposals, objections, revisions, verification, adopted claims, unresolved objections, terminal status, resources, and source links. Neither surface exposes private reasoning or provider conversations.

Exact commands remain available for policy selection, status, resume, and diagnostics. Natural start requires an explicit human request and a configured default policy. Product recommendations are read-only and cannot invoke `deliberation.start`.

## Bounds and resource meaning

Existing policy rounds, required verification suites, provider selection, writing gates, queue leases, deadlines, output limits, and uncertain-effect reconciliation remain authoritative. Each policy additionally binds `maximumProviderCalls`, `maximumObservedTokens`, `maximumElapsedMs`, and `unobservedTokenDisposition: block`. Provider calls include stakeholder production, semantic evaluation, bounded repair, verification, and decision turns. Exact normalized `resource.usage.recorded` totals accumulate across those child scopes. Reaching the call limit blocks admission; reaching the inclusive observed-token limit after a call blocks publication and every later call; unavailable exact usage blocks with `deliberation_budget_observation_unavailable`. The elapsed deadline supplies the managed abort signal and remains bound through the approved checkpoint on resume. Before admitting each provider call, the runner subtracts a fixed finalization reserve from the remaining workflow time. The Node worker also passes a managed elapsed ceiling that ends before its child-process timeout. This leaves bounded time for stream drain, provider stop, post-run snapshot, failed-outcome recording, storage close, and terminal summary serialization. Budget values and consumed counters contain no prompts, prose, credentials, native payloads, or platform identifiers.

Execution-plan construction rejects a provider-call ceiling that cannot complete the configured maximum rounds, every reviewer, revision between rounds, every required verification suite, the decision-owner turn, and each required semantic evaluation even when no repair is needed. The installed architecture policy requires 20 calls for that baseline and permits 24 so two bounded writer repairs and their evaluations can occur. This feasibility check prevents a policy from beginning provider work with a structurally impossible call ceiling; ordinary runtime exhaustion remains the correct meaning when actual repair or usage consumes the declared finite allowance.

All managed role and semantic-evaluator runs in one deliberation share one integrity-preserving repository snapshot capture. Capture still revalidates directory entries and rereads changed files; unchanged files reuse identity-bound hashes instead of forcing every child run to rescan their bytes before the same deadline. Product configuration must be no looser than the selected policy's elapsed ceiling. A mismatch blocks start instead of weakening policy.

Managed deliberation resolves repository knowledge once before the first provider starts. It selects a bounded set of current topic-ranked publications, rereads each source under the repository file boundary, verifies the query-returned content hash, and materializes an immutable workspace copy plus a manifest that binds query, source snapshot, impact report, source path, concept, and exact source hash. No current result, a changed source, an oversized source, an invalid bundle, or a failed copy records `deliberation_evidence_unavailable` and a terminal failed deliberation with zero provider calls. Every stakeholder and verifier turn receives the same manifest and exact copies through the managed context rules; writing evaluators receive only their evaluation request and writing policy. Resume restores the exact generated evidence bytes from the checkpoint rather than rerunning retrieval. Selected, loaded, injected, and referenced evidence remain separately observable and are never inferred from the bundle alone.

Managed deliberation provider turns consume only that exact-hash evidence bundle and prior writing-gated publications injected by Lervo. The application disables provider tools where the native adapter supports that boundary and independently configures every deliberation child run with zero allowed tool calls and zero allowed command executions. The first observed tool or command event is retained as normal provider telemetry, aborts the active provider session, and records `run.failed` with `provider_tool_limit_exceeded` or `provider_command_limit_exceeded`. Those existing failure events require the normal run, session, phase, code, retryability, and causal coordinates; they add no prompt, command body, output, document body, credential, or native provider payload. Neither failure is retryable within the deliberation because retrying the same unconstrained behavior would spend the bound again.

An internally exhausted elapsed budget records a canonical failed outcome and the assigned CLI returns a terminal `failed` summary with exit status 2. The queue settles that summary normally and publishes the language-matched failure consequence; it does not classify the known failure as uncertain. Only an outer worker expiry, process loss, or other boundary failure that prevents a verified terminal summary remains uncertain exactly once and never reruns provider work. Authoritative inspection continues on the background schedule; a transient inspection, interaction-store, or delivery failure does not terminate the deliberation background loop or discard the pending attention obligation.

Semantic publication evaluation is fail-closed and separately bounded. When its read-only managed child run fails at a retry-safe snapshot or provider boundary, the runner retries the same content-addressed artifact once in a fresh session and records attempt ordinal two under `publication_evaluation` causality. It does not regenerate the producer artifact. Invalid evaluator contracts, negative check results, capability failures, telemetry failures, and exhausted infrastructure attempts remain publication failures.

Each managed role run retains its resource descriptor and `deliberation` causal relationship. Provider input, cached input, output, reasoning output, and total tokens remain grouped by provider, role, run, session, accounting mode, and descriptor hash. Publication evaluation and verification remain separate child scopes. Unlike cache observations are never combined.

Observed tokens are a hard admission and acceptance bound only because current Codex and Claude adapters provide exact normalized resource observations. They do not prove billing or monetary cost. A monetary stop still requires a separately versioned accounting contract.

## Result, search, and canonicalization

Application results distinguish `converged`, `no_consensus`, `failed`, `interrupted`, `unknown`, publication state, and origin-delivery state. `no_consensus` is a valid bounded outcome, not a transport or provider failure.

Unified search exposes authorized deliberation artifacts and outcomes as a distinct corpus class with stable artifact, claim, objection, verification, decision, and source coordinates. Search never changes outcome state or grants artifact access.

A converged decision may produce a reviewed work, documentation, or knowledge candidate. It becomes canonical only when the owning lifecycle accepts exact source-bound bytes. `no_consensus`, `failed`, and uncertain outcomes promote nothing.

## Evolution

Version-1 deliberation artifacts, outcomes, events, and queue records remain readable without reinterpretation. New artifact events retain original summary fields and add the complete validated structured artifact as an optional, source-free projection source. They may include the policy-bound participant name used for presentation. Predecessors without it remain readable and use honest role labeling, never an invented agent identity. Every duplicate coordinate must match. Legacy events without the structured artifact remain valid but cannot independently reconstruct complete claim, objection, verification, and decision semantics. Product routes and `ProductDeliberationViewV1` are additive. Future budget dimensions, principal kinds, artifact kinds, or terminal meanings require explicit new versions, current-and-predecessor fixtures, restart and rollback coverage, and historical replay.

Product-host protocol v11 exposes the host-neutral projector, reader-first sources, and installed read-only composition. The composition validates and joins queue origin, the exact embedded or hash-matching predecessor policy, structured artifact events, verification evidence, terminal outcome, participant bindings, resource work coordinate, writing permit, and receipt-backed origin delivery. Missing legacy evidence produces an explicit partial or unavailable result; it cannot be filled from notification configuration, topic text, native Discord identifiers, or empty default arrays. This query alone does not satisfy Discord-visible artifact updates or installed round-trip acceptance.
