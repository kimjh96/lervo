# Lervo ADE sessions

Status: `proposed`
As of: 2026-11-23

This specification defines the sessions of the Lervo ADE that [ADR-0613](../../../decisions/execution/applications/0613-host-provider-clis-in-a-first-party-development-environment.md) proposes: session kinds, launch options, conversation modes, hosted observations, and the commands, events, and failure meanings they use.

## Session kinds

| Kind    | Process                                              | Login                          | Evidence                    |
| ------- | ---------------------------------------------------- | ------------------------------ | --------------------------- |
| Shell   | A login shell in a PTY                               | None                           | None                        |
| Hosted  | The user's installed provider CLI, launched by Lervo | The user's own provider login  | Hosted observations (below) |
| Managed | An ADR-0010 adapter session                          | An API key the user configures | E0–E4, unchanged            |

A hosted session is the default agent session. Lervo prepares its launch, and the session host executes it. For Claude Code, the launch uses these documented [CLI options](https://code.claude.com/docs/en/cli-reference):

- `--session-id` with a Lervo UUID, so hook events bind to the session that Lervo started;
- `--settings` with a session-scoped file that adds Lervo's hook handlers, leaving the user's settings files unchanged (invariant 5);
- `--mcp-config` with Lervo's MCP server;
- `--append-system-prompt-file` with the role's instructions.

### Lervo's session hooks

An adapter that declares `hooks` receives Lervo's hook handler with the launch intent: the path of a session-scoped settings file and a hook command. It returns the file's content with the launch, and passes the file to the provider. Lervo writes the file before the launch returns, so the session host never receives it.

- **The file.** It is `<user state directory>/hosted-settings/<session ID>.json`, with mode 0600. It holds Lervo's `SessionStart` and `SessionEnd` handlers, each with a 10-second timeout, because Claude Code otherwise gives `SessionEnd` 1.5 seconds. Claude Code merges it with the user's settings, so the user's files and hooks stay unchanged and keep running. It names no `disableAllHooks`. Lervo removes a session's file when no kept launch record names the session.
- **Lervo sessions everywhere (ADR-0632, S2a).** Every hosted session gets Lervo's context, Stop check, capture, and evidence hooks, whatever the repository commits.
  - Project settings carry Lervo's terminal hooks in most repositories: `.claude/settings.json` runs the committed launcher `.lervo/generated/terminal-hooks/runtime-v2.mjs` for `SessionStart`, `UserPromptSubmit`, and `Stop`.
  - While the workstream starts, the start hashes the new worktree once into its terminal repository snapshot cache ([terminal preparation and snapshots](../stage-observation-and-performance/terminal-preparation-and-snapshots.md)). Without it, a large repository's first prompts cannot snapshot within the hook's deadline and record no turn evidence. A failure only leaves the hooks to warm the cache themselves.
  - Once the worktree exists, the launch reads every settings file the provider merges into the session: for Claude Code, managed policy, the user's settings (`$CLAUDE_CONFIG_DIR` or `~/.claude`), and the worktree's `.claude/settings.json` and `.claude/settings.local.json`. It reads them as Lervo's installer does, comments and trailing commas allowed, and follows links. A file that is missing, unreadable, over 1 MiB, or does not parse counts as absent, as Claude Code ignores a settings file it cannot parse.
  - A hook counts for an event when it runs Lervo's terminal hook for this provider: the repository's launcher while it is present, or `lervo terminal hook`. A `SessionStart` hook limited by a matcher covers only the sources the matcher selects (`startup`, `resume`, `clear`, `compact`), testing it as a regular expression against each, as the provider does; the added handler takes a matcher for the rest. A matcher that is no valid expression counts as covering every source, so Lervo never runs twice.
  - For each event no merged settings file covers, the file adds `node '<terminal hook store>/launcher.mjs' --provider claude --contract 2` with a 30-second timeout, as the project's own hooks allow. The path is single-quoted, so nothing in it expands, and written with forward slashes on Windows, where Claude Code runs hooks in Git Bash. A worktree whose project hooks every event gets none, so no event runs Lervo twice.
  - The host launcher is the same launcher a repository commits, kept beside the runtime store that the installed CLI publishes (`~/.lervo/terminal-hooks`, or `%LOCALAPPDATA%\Lervo\terminal-hooks` on Windows). It verifies and runs the store's current runtime and needs nothing in the worktree, so terminal and hosted sessions take one path from launcher to runtime. Whenever the installed CLI checks its runtime, it replaces the launcher atomically with an owner-only copy of its own when the file is missing, is a link or no regular file, or differs from it, so a release that changes only the launcher still reaches it.
  - A launch runs the host launcher only when it is a regular file, not a link, that holds exactly the installed CLI's launcher and, where the platform has owners, belongs to the user and is writable by no one else. Otherwise, as on a host whose install predates the launcher, the file runs `lervo terminal hook --provider claude --contract 2` instead.
  - The launch record's `terminalHooks` holds the events whose handlers in the written settings file run the chosen command, and `via`: `launcher` or `cli`. A launch whose settings file runs none of them records none.
  - **Failure meaning.** The added hooks fail as a repository's own terminal hooks do.
    - The launcher exits 2 when the runtime fails its integrity check; for `UserPromptSubmit`, Claude Code then blocks the prompt and shows the error, exactly as in a terminal session of a repository with project hooks.
    - On the CLI fallback, a host without `lervo` on the session's `PATH` makes the hook exit 127. That is a non-blocking hook error, and the session goes on without Lervo's context.
    - The adapter contract refuses terminal hooks with an empty or multi-line command, no events, duplicate or unknown events, or a matcher on any event but `SessionStart`. Its common checks require an adapter to write a handler, with its matcher, for every listed event, or none.
  - `lervo workspace open` reads the worktree the same way for the launch it prepares. An adapter without hooks, such as Codex today, gets none.
- **The command.** It is `lervo workspace hook --provider <provider>`, found on the `PATH` that the session host passes on, so it survives an upgrade of the CLI. It reads the hook input from stdin, at most 64 KiB, and uses only `session_id`, `hook_event_name`, and, for `SessionEnd`, `reason`.
  - It never prints to stdout, because Claude Code adds a `SessionStart` handler's output to the model's context.
  - It always exits 0, so a hook never stops the session.
  - It ignores a session that no launch record names.
- **When the hooks run.** On 2026-11-23, Claude Code in print mode with stream-json input ran `SessionStart` with `source: startup` at launch. It ran `SessionEnd` with `reason: other` both when its input closed and on SIGTERM. Both hooks received the UUID passed with `--session-id`.

The provider adapter owns these options. The session host receives an opaque launch descriptor, which holds the executable, arguments, added environment, working directory, and initial input. The session host never branches on the provider (invariant 2).

Each adapter implements the hosted-session contract of `@lervo/adapter-contract`. It declares `nativeConversation`, `sessionIdBinding`, `hooks`, `mcp`, `systemPromptFile`, and `resume`, and every adapter's tests run the common hosted-session checks against its launches. A capability stays false until the launch actually provides it. In S1.4a, Claude Code declares the native conversation, session ID binding, and resume. S1.4c adds `hooks`. Its native conversation uses `--permission-mode auto`, because print mode cannot ask the user for permissions; the CLI conversation keeps the user's own permission settings. The Codex CLI declares only the CLI conversation: Codex chooses its own session ID, and its native conversation waits until its decoder is proven against a real Codex session.

The ADE supports Claude Code and the Codex CLI first. The Codex adapter maps the same launch intent to Codex's own options and declares the capabilities it lacks instead of emulating them. Gemini, Grok, and later providers arrive as new adapters from the registry of admitted adapters ([ADR-0536](../../../decisions/execution/providers/admission/0536-admit-provider-clis-by-contract.md)), without changes to the UI, the session host, or other adapters.

A managed session is available when the user configures an API key. It follows ADR-0010 without change.

## Conversation modes

A hosted session reaches the user in one of two modes. Since [ADR-0617](../../../decisions/execution/applications/0617-offer-only-claudes-native-conversation-in-the-ade-for-now.md), the ADE shows the native conversation only and offers only providers that support it. The core still prepares CLI launches for `lervo workspace` commands, so the CLI conversation below describes those launches.

| Mode                | How the CLI runs                                                                                 | What the user sees                                         | What Lervo observes                               |
| ------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- | ------------------------------------------------- |
| Native conversation | Print mode with structured streams (`-p --input-format stream-json --output-format stream-json`) | The ADE renders messages, tool activity, and questions     | Every streamed message and tool event, plus hooks |
| CLI conversation    | The interactive CLI in a PTY                                                                     | The provider's own terminal interface inside the workspace | Hooks only                                        |

The native conversation is the target experience. The CLI conversation is the fallback that every installation can always use.

Both modes run the unmodified provider CLI under the user's own sign-in, so the native conversation is the default for every sign-in. The user can switch a workspace to the CLI conversation at any time.

The start screen does not ask for a mode. When `workspace.start` names no mode, the core uses the provider's preferred conversation: the native conversation when its adapter declares `nativeConversation`, otherwise the CLI conversation. The workspace header switches between the two.

A managed session always renders as a native conversation.

## Provider terms

The ADE runs each provider CLI under that provider's terms. For Claude Code, Anthropic's [legal and compliance terms](https://code.claude.com/docs/en/legal-and-compliance) allow a product to run the binary under each user's own sign-in, with these conditions:

- Lervo runs the Claude Code binary as Anthropic publishes it, and never removes or restricts its authentication methods.
- Each user signs in through Claude Code's own flow, with their own subscription or API key. Lervo never collects, stores, or forwards Claude credentials or session tokens.
- Lervo never pays for, resells, or intermediates Claude usage on a user's behalf.
- The ADE may state in plain text that it runs Claude Code. It never uses the Claude Code or Anthropic names or logos in its own name or logo.
- The publisher of a distributed build accepts Anthropic's Commercial Terms of Service.
- Managed sessions use the Agent SDK and therefore use API keys only.

The Codex CLI ships in a distributed build only after OpenAI's terms are checked against the same conditions. A provider adapter that cannot meet its provider's terms is not admitted (ADR-0536).

## Provider memory

Hosted Claude sessions run with Claude Code's auto memory off: the Claude adapter adds `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` to every hosted launch's environment.

- **Why.** In the ADE 0.5.0 canary on 2026-11-25, an ADE agent given an owner rule wrote it into Claude Code's auto memory as well as `AGENTS.md`. Claude Code shares one memory directory across every worktree of a repository, so that note would reach the owner's terminal sessions outside Lervo. Owner rules and corrections belong to Lervo, which captures them from the conversation (AGENTS.md); provider-private memory must not hold them. Turning auto memory off enforces that rule for the sessions Lervo launches.
- **Scope.** Only hosted processes get the variable. The launch writes no user or project settings, so the owner's terminal sessions keep whatever they set. The setting lives in one place, `CLAUDE_HOSTED_ENVIRONMENT` in the Claude adapter.
- **Exit.** It stays off until S2d's Lervo memory tools reach hosted sessions. Then hosted agents remember through Lervo, and this section records whether provider memory returns.

## Permission mode

Native hosted Claude sessions run with `--permission-mode bypassPermissions`, as the owner's terminal sessions run. The CLI conversation passes no permission flag and keeps the owner's own settings, because the owner answers its prompts in the terminal.

- **Why.** Claude Code holds a cross-session message from a session in another permission mode until someone approves it, and a hosted session has no one to approve it. While hosted sessions ran in `auto`, a message from the owner's bypass sessions never reached them: on 2026-11-26 a hosted session listed by `ListAgents` stayed silent, while a bypass session answered the same message at once. The owner chose bypass that day.
- **Scope.** Only native hosted launches pass the flag. The setting lives in one place, `CLAUDE_HOSTED_PERMISSION_MODE` in the Claude adapter, and the launch writes no user or project settings.
- **Next.** The ADE's settings will let the owner choose the mode; until then every hosted session uses bypass.

## Hosted observations

Hosted sessions record their own observations. They are never E1–E4 and never satisfy a managed context or write gate (invariant 3). Hosting removes one of ADR-0197's four reasons, because Lervo starts the provider. The other three reasons still hold.

- `launched`: the provider's `SessionStart` hook reported a session ID that Lervo prepared, for a launch descriptor that Lervo recorded. Every other hosted observation requires it.
- `prepared` and `referenced`: unchanged from ADR-0197, bound to the launched session.
- `tool_observed`: a `PreToolUse`, `PostToolUse`, or `PostToolUseFailure` hook, or a streamed tool event in the native conversation, reported a tool call. A tool call that nothing reported is not proven absent. A Bash command can also change files that no hook names.
- `instructions_loaded`: an `InstructionsLoaded` hook reported a repository instruction file by path. This is provider-side loading. It is not Lervo's E2, and it proves neither injection nor use.

A session whose `SessionStart` never matches a prepared ID stays `launch_unconfirmed`. Its observations fall back to the ADR-0197 unmanaged ladder.

Each adapter that declares `nativeConversation` provides a stream decoder, and the common hosted-session checks hold the two together. The decoder runs in the resident Lervo process behind the [core link](ade-core-link.md). Claude Code's decoder reads `stream-json` with partial messages. A text block becomes a streamed agent message. A tool call becomes one tool-activity item, succeeded or failed, when its result arrives, with a bounded [tool detail](ade-session-host-protocol.md#tool-detail): what the call acted on, its counts, and a preview of its output or change. The decoder reads the call's input, its `tool_result`, and Claude Code's structured result, and shows paths relative to the working directory that the `system` `init` line names. The transcript reader builds the same detail, so a rebuilt conversation shows what the live one showed. Native sessions also run with `--replay-user-messages`: the replay of the person's own message repeats what the decoder showed at sending and is dropped, and a message another session sent (`origin.kind` `peer`, with the sender's name and body) becomes a `peer_message` item. The transcript keeps such a message as a meta line with the same origin, and the transcript reader shows it the same way. A `compact_boundary` line adds the `context_compacted` notice, which the interface shows as a thin divider; the transcript reader also skips the summary Claude Code writes for the model after a compaction (`isCompactSummary`, `isVisibleInTranscriptOnly`), which earlier showed as a long message from the user. `result` ends the turn and adds the `provider_turn_failed` notice when the turn did not succeed. Subagent messages, thinking, hooks, and other system lines stay out of the conversation. A tool that is still running shows only as the session's working status until its result arrives.

The native conversation's structured stream carries the same kinds of events that ADR-0010 reads. It still records hosted observations only. A native hosted session can claim an E3 receipt only after the provider adapter's common contract tests prove the same controlled-input coordinates that ADR-0010 requires.

## Live status and notifications

- The workspace list shows a workspace's status from `sessions.watch`. Only `working` and `needs_user` show: a working workspace's title sweeps, and one that needs the user has the amber dot, as the visual language defines. Each has a text equivalent.
- A desktop notification appears when a session turns to `needs_user`, or from `working` to `idle`, which means the agent finished its turn. Nothing notifies for the workspace the user is looking at in a focused window, or for a status the interface saw first after connecting.
- A notification holds the workspace title and a catalog message, never conversation text.
- The shell shows the notification. On macOS it goes through the User Notifications framework, which asks for the system's permission at the first notification. The notification daemon serves only an app whose code signature names its bundle identifier, so the bundle step signs the app ad hoc as `dev.lervo.ade`; the linker's own signature names a hash, and the daemon refused it. Before this, the notification plugin reported permission as granted without asking the system, and its notifications reached Notification Center without a banner. Each notification's identifier holds the launch's time and a count, because Notification Center only updates a notification whose identifier it still holds, such as one an earlier launch delivered, without a banner. While Lervo is the active app, macOS adds a notification to Notification Center without a banner, and the workspace list shows the same change. A banner then would need a notification-center delegate, which the shell's ban on unsafe code rules out.

## The conversation in the interface

- The interface keeps a window of at most 600 items for the open conversation and loads pages of 100 with `conversation.range`. Scrolling near the top loads the previous page, and the window trims the side away from what the user reads.
- Only items near the viewport mount: the list is virtualized, and rows measure their own height.
- Streamed text applies at most once per frame. A new item, or a repeat of a streaming item, flushes the pending text first, so the order never changes.
- When the workspace's session does not run, the interface opens it with `session.open`, which resumes the provider's session through the core, and attaches again.
- Each item kind has one renderer in a registry. Lervo notices render from the catalog by code. In S1.5c, messages render as plain text; S1.6 chooses Markdown and code rendering by measurement against the conversation budgets.
- Slash commands, skills included, work in a native session: the reply goes to Claude Code as typed, and the conversation shows it as sent. A conversation read back from Claude Code's transcript shows the same: the command's line reads as the command and its arguments, while the skill text it loaded and a built-in command's local output, which the live conversation never shows, stay out.

## Stopping a turn

The owner stops the agent's running turn without ending the session, as Escape does in Claude Code's terminal.

- **In the interface.** While the agent works and the reply card is empty, the card's button is Stop, and Escape in the card does the same. Typed text turns the button back into send, so a reply can still go. The working line says "Stopping" until the turn ends, and the turn's notice confirms it. Stop shows only when the session host is at least as new as the interface and the core advertises `decoder.interrupt`.
- **Through the session host and the core.** `session.interrupt` asks the session's decoder for the bytes that stop the turn through `decoder.interrupt`, and the session host writes them to the provider's standard input. With no turn running, nothing is written. The session host answers with `session.interrupted` once the bytes reached the provider, or with `request.failed` and `interrupt_unsupported` in the CLI conversation, for a provider that cannot, or when the core did not advertise it.
- **Claude Code.** The decoder writes a stream-json `control_request` with subtype `interrupt`. Claude Code answers with a `control_response`, stops the turn, and ends it with a `result` whose `terminal_reason` is `aborted_streaming` or `aborted_tools`; a stop while text streams reports `error_during_execution`. The session stays, and the next message continues it. Observed with Claude Code 2.1 on 2026-11-25.
- **What the conversation shows.** A stopped turn ends with the `turn_stopped` notice instead of `provider_turn_failed`. A turn whose result says `completed` finished before the request arrived and shows no notice. A Claude Code without `terminal_reason` is taken at the request.
- **Core records.** Claude Code runs no `Stop` hook for a stopped turn, in the terminal or the ADE, and the next prompt replaces the turn's open-turn marker. At event schema 12 the next prompt or session start of the same session settles the stopped turn instead: a detached worker records its `terminal.turn.observed` with `ending` and `completionResult: not_checked`, its repository change, and its skill assessment ([turn evidence](../events-and-privacy/terminal-observations/context-reference-and-turn-evidence.md#turns-that-end-without-a-stop-hook-schema-12)). Settling at `SessionEnd`, and from the decoder's own `provider_interrupt` signal, remain follow-ups.

## Questions

An agent that needs the owner to decide asks with choices the owner picks in the conversation, as Claude Code's terminal shows them, instead of in prose the owner answers by typing.

- **Claude Code.** A native session the session host launches runs with `--permission-prompt-tool stdio`, so Claude Code sends each `AskUserQuestion` call as a stream-json `control_request` (`can_use_tool`) and waits for its answer. Its decoder shows the call as a `question` item with `choices`: the request's ID and at most four questions, each with its text, a short header, whether it allows several answers, and at most eight options with a label and a description. It answers every other tool Claude Code asks about with "allow", as a session that bypasses permissions would, and refuses any other control request, so Claude Code never waits on what the interface cannot ask. Observed with Claude Code 2.1 on 2026-11-27.
- **Asking for it.** The session host adds `questions: true` to `workspace.start` only while the core advertises `decoder.questions`, since only such a core answers Claude Code's requests through `decoder.output`'s `input`. The core passes the intent only to a provider whose adapter declares `questions` and only in the native conversation, and records `questions` in the hosted launch record, so the conversation's reopened session and every agent that joins it ask the same way. A terminal conversation asks in its terminal.
- **In the interface.** Each question shows as the agent's text with its options on one raised card under it, on a needs-you edge. One question with one answer sends as soon as an option is chosen; otherwise each question takes its choice, several where it allows them, and "Send answers" sends them together. Arrow keys move between a question's options. A question is open while it is the last item of its session; once the owner answers, the options close their space and the edge settles to a faint line.
- **Answering.** `session.answer` names the session, the question's `choices.requestId`, and the answers, each by its question's text, several labels joined by ", ". The session host asks the decoder for the bytes through `decoder.answer` and writes them; the conversation then shows the answers, in the order asked, as the owner's message, and the turn goes on, so its status returns to working and no turn ends at the question. A question that no longer waits fails with `question_not_open`, and the card says so.
- **Answering in prose.** A reply sent while a question waits answers it in the owner's own words: the decoder first tells Claude Code that the owner replied instead of choosing, then sends the reply.
- **What the conversation keeps.** The question with its choices and the owner's answer are ordinary items of the index. The `AskUserQuestion` tool call adds no tool line, since the question and the answer already show it. A conversation rebuilt from Claude Code's transcript shows the question as the agent's question, without its choices, and the owner's choices as their message, from the result's structured `answers`.

## Idle sessions

A provider process holds about 150 MB. Without a limit, every conversation opened since the session host started kept one: four visited conversations held five Claude Code processes and 746 MB (measured 2026-11-27).

- **When a session rests.** No client shows it, no turn runs, no question waits for the person, and no delivered turn waits. A session that rests for 10 minutes has its provider asked to end, as `session.stop` does. Its conversation and index stay.
- **Coming back.** The stopped session does not linger. The interface shows the conversation from its index and opens the workspace again ([Reopening a conversation](#reopening-a-conversation)). The core then resumes the provider's session, and the conversation continues where it was. A mention of an agent whose session stopped joins it again the same way (Lervo ADE rooms).
- **What never stops.** A conversation on screen, a running turn, and a question that waits for the person.

## The turn summary

A finished turn ends with one quiet line of what the core recorded about it (approved mockup 3, "The Lervo turn summary"): how long the turn took, then only what it did beyond the usual, such as _48s · 2 documents found · 3 files changed · Workstream updated_. An ordinary turn reads as its time alone. The line opens to a card of the rows that have something to say, in four parts: what Lervo gave the agent (documents it selected, the workstream revision), what the agent used (documents its Lervo searches found, documents its answer cited), the outcome (files changed, the workstream revision it ended at, a completion check that blocked or did not run), and the provider-reported usage with a list-price cost.

- The interface asks the core with `turn.summary` once a turn is over and its line comes into view, and keeps the answer for the conversation. Only a core that advertises the command is asked.
- A hosted turn has no provider turn ID, so the core takes the session's first prepared prompt context from 5 seconds before the turn's message to 5 seconds before the next one. The rest follows from that context: its selections, the `terminal.turn.observed` that cites it, a `repository.change.completed` from that observation, and the session's `resource.usage.recorded` in the window.
- It calls no model and reads only the repository's store: about 10 to 35 ms and 300 bytes a turn on 2026-11-25, in stores of 90 and 57,000 events.
- What the core does not record does not show (invariant 3). From event schema 15, the turn's `terminal.context.prepared` may carry one object, `appliedInstructions`, with `status` (`complete`, `incomplete`, or `unavailable`), `preparedCount`, and `omittedCount`, which is null when the status is `unavailable` ([turn evidence](../events-and-privacy/terminal-observations/context-reference-and-turn-evidence.md#owner-rules-prepared-for-a-turn-schema-15)). The card may then say how many owner rules Lervo prepared, such as "2 owner rules prepared". It never says they were applied or delivered, because the provider's injection and use of the rules stay unobserved. A turn without the object, including every turn until a writer records it, shows no owner-rule row.

## Owner rules in the conversation

The terminal shows the owner rules Lervo applies as "Lervo applied owner rule" blocks, because Claude Code prints its hooks' output there. The native conversation does not repeat them.

- **Why not.** The blocks are context written for the agent, often several screens per turn, and Lervo cannot observe whether the provider used them (invariant 3). Repeating them would add noise and claim more than Lervo knows.
- **What shows instead.** A turn's summary names how many owner rules Lervo prepared for the turn, such as "2 owner rules prepared", next to the documents Lervo gave. It never says applied or followed. A rule set Lervo cut for space says so: "2 of 14 owner rules prepared".
- **Where it comes from.** From event schema 15, `terminal.context.prepared` carries `appliedInstructions`: `status` (`complete`, `incomplete`, or `unavailable` when the rule catalog could not be read), `preparedCount`, and `omittedCount` (null when unavailable). Readers accept it before any writer emits it, as for the room events. `turn.summary` reports it in `given`; a turn recorded before then, or an unavailable catalog, shows no rule count.
- **Learned rules.** A rule Lervo captures from the conversation is reported where Lervo reports what it learned, never as a block in the conversation.

## Replies while the agent works

Claude Code reads a reply sent during a turn between the turn's steps, in the same turn, and its stream has no line for the moment it does (checked on 2026-11-26). A reply the person sends while the agent works says _Queued · the agent reads it at its next step_ under its bubble until the agent's next item arrives, then fades. The prompt hook still runs for such a reply, so the core records it as a new prompt and settles the one before it as ended by the next prompt; the conversation shows the same split, with that earlier part's summary line.

## Images in a message

The owner pastes images and screenshots into the reply card of a native conversation and into the instruction of new work, and sees them in the conversation as images, never as "Image 1" text (image mockup, design "A").

- **Pasting.** A pasted image shows at once as a 56-pixel thumbnail above the card's field, faint with the waiting sweep while it is prepared. Its remove button shows on hover and keyboard focus, and the thumbnail opens the image at full size. A message carries at most three images and may be images alone. A card offers images only when the session host is as current as the interface and the core advertises `decoder.images`; otherwise a paste says the session cannot take images yet, and nothing is added. Pending images belong to their card and conversation; the draft keeps text only, and a failed start or send puts its images back.
- **Size.** The interface scales a pasted image so its longest side is at most 1,568 pixels, the size Claude reads images at, and sends it as PNG when that fits 240,000 Base64 characters, otherwise as JPEG at 85% quality, in smaller steps down to 384 pixels. Three images and the longest text then fit one protocol frame. An image the system cannot read, or one still too large at the smallest step, is refused with its own line under the card.
- **Path.** `session.send` carries a reply's images. For new work, `workspace.start`'s `images` argument carries them: the session host takes them out, so the core receives the text alone, and sends them with the first message. Either way, the session host keeps each image beside the conversation index as `img-<identity>.<extension>`, where the identity is the SHA-256 of its bytes, and passes the images to the core's decoder with `decoder.send`. Claude's decoder writes them as image blocks after the text in one stream-json user line. Images sent alone carry Claude Code's own placeholders as their text, such as `[Image #1]`, as its terminal does, so prompt hooks and Lervo's retrieval read a prompt.
- **In the conversation.** The user message keeps a mark per image: its format, size, and identity, never its bytes. The bubble shows the images above its text, a lone image in its own shape within 280 by 200 pixels and several as 112-pixel square tiles; a message of images alone wraps them in 4 pixels. The interface draws an image from its cache, where a sent image goes before it is sent, or reads it with `image.read`. An image opens at full size over the dimmed window, where Escape or a click outside closes it and the arrow keys move between the message's images.
- **Kept images.** The images stay with the conversation index: the cap on all indexes counts them, and a rebuild of the index from the provider's transcript keeps them. A transcript read back names each image by the same identity, so its kept image still shows. An image the session host does not keep, such as one from a session it never sent, shows as a quiet tile with its size, in the same place.

## Files in a message

Before this, pasting a file other than an image into a card inserted only its name, so the agent searched the repository for that name and found nothing or the wrong file. The owner now pastes or drops any file or folder into the reply card and into the instruction of new work, and it goes to the agent by its path (file mockup, design "A").

- **Attaching.** A file copied in Finder and pasted, or dragged onto the window and dropped anywhere on it, waits as a chip beside the card's image thumbnails, as tall as they are: a type badge with its extension or a folder, its name, and the folder it is in with its size. Its remove button shows on hover and keyboard focus, and the chip shows the file in Finder. While files are over the window, the card that takes them shows it with its accent border, a faint accent tint, and _Drop to attach_ in place of what waits; when several cards are mounted, the one mounted last takes them. A message carries at most ten files; an eleventh, or a path that is not absolute on one line, is not added.
- **Images among them.** A pasted or dropped file with an image extension the webview draws (PNG, JPEG, GIF, WebP, HEIC, HEIF, BMP, TIFF) goes as an image, as in "Images in a message", when the session takes images, and as a path when it does not. A pasted image that has no file, such as a screenshot, still needs a session that takes images.
- **The shell reads paths.** The webview never learns a file's path. On a paste whose clipboard carries files, the interface asks the shell, which reads the paths of the clipboard's file URLs (`pasted_files`); Finder writes file reference URLs, which the shell resolves. A drop comes from the window with its paths. The shell describes each path (`describe_files`: name, size, whether it is a folder, whether it still exists), reads a dropped image's bytes up to 64 MiB (`read_image_file`), and shows a file in Finder (`reveal_file`). A paste that carries files never inserts their names as text.
- **Path to the agent.** Files go as text the agent reads: the message's text, a blank line, `Attached files:`, and one `- <path>` line per file. The agent opens each path with its own tools; hosted sessions run with permissions bypassed, so a file outside the repository needs no approval. Nothing is copied, so a large file attaches at once and the agent reads what it needs. No protocol message, decoder, or core changes; the session host and the transcript carry the text as they carry any text. A message may be files alone, and new work started with files alone takes its title from that text.
- **In the conversation.** The bubble reads the list back from the end of the text and shows a chip per file, under any images and above the text. The shell describes the paths once per interface launch; a file moved or deleted since shows faint with _Moved or deleted_ and does not open.
- **Limits.** A path names a file on this Mac, where the session runs. A file moved after sending can no longer be read by the agent; its chip says so.

## The CLI conversation in the interface

The ADE no longer shows the CLI conversation ([ADR-0617](../../../decisions/execution/applications/0617-offer-only-claudes-native-conversation-in-the-ade-for-now.md)). This section records how it worked, for when it returns.

- The interface shows the CLI conversation in xterm.js with the generated terminal theme for the current color scheme. It uses the WebGL renderer and falls back to the DOM renderer.
- It opens the session with `session.open` in the CLI conversation, attaches from the last sequence it wrote, and skips frames it already wrote, so reconnecting never repeats output.
- Keystrokes go out as terminal frames on the session's channel. Size changes go out as `session.resize`, once per change.
- The header switches a workspace between the two modes through `session.open` with the other mode. The session host stops the running provider process and waits up to 10 seconds for it to end before the core prepares the other mode, so one provider process serves each workspace. If the process does not end in time, the switch fails with `session_stop_timeout` and the session keeps running in its current mode.
- The session host ends a native session's provider with SIGTERM, so Claude Code runs its own shutdown and its `SessionEnd` hook. It kills the provider 8 seconds later if it still runs, which stays below the 10 seconds a mode switch waits. When the process has ended, the session host reports its exit code, or none after a signal, with `session.exited` to a core that advertises it ([core link](ade-core-link.md)).
- The terminal and its renderer load on first use, so the start screen does not pay for them.
- When the session host cannot be reached, the interface's reconnection makes the shell start it again (session-host protocol, "Transport").

## Reopening a conversation

A conversation whose session does not run shows the newest page its index holds while the session opens, so it shows before the core and the provider are ready.

- **Stored pages.** The session host answers `conversation.range` for a session it does not hold from the index that session left. It reads the index without creating or repairing anything and marks the page `stored`. A session that left no index, or whose index is damaged or being rebuilt, answers `session_not_found`, as before.
- **Opening.** The interface opens the session at once when the session host reported no running session as the conversation opened, and asks the index for its newest page meanwhile. Otherwise it attaches first, and a `stored` page tells it that the session does not run. The live page replaces the stored one once the session attaches, so a stored page never streams.
- **Joined agents.** A joined agent's lane takes a `stored` page as a session that does not run and joins it again ([Lervo ADE rooms](ade-rooms.md)).
- **First paint.** On the 100,000-item conversation, first paint measured 84–100 ms in four of five runs at a load average near 8.5 (2026-11-27). It was 113–136 ms when the page waited for the session to open.

## Conversation index

- The session host keeps one conversation index per session: segment files of 256 encoded items each, written as length-prefixed records.
- The index is a rebuildable projection of the provider's transcript (invariant 4). Appends skip `fsync`. When the index opens, it truncates a torn final record; a missing or damaged sealed segment reports `conversation_index_corrupt`, and the host rebuilds the index from the transcript.
- Both conversation modes run the same provider session, so the transcript holds the turns of either mode. When a native session opens from `session.open` and the core marked its launch `transcript`, the session host reads the transcript through `transcript.read` before the provider starts. It applies the items as the live transcript would, so long text splits the same way. When their number differs from the index's, it replaces the index with them; turns from the CLI conversation then appear in the native conversation. An empty transcript never replaces an index, and a transcript beyond 100,000 items or 64 MiB of text, or one that cannot be read, leaves the index as it is.
- Rebuilding replaces items that only the live stream produced, such as the `provider_turn_failed` notice, because the transcript does not record them.
- An item's identifier encodes its position, so the host finds any item without a lookup table that grows with the conversation.
- Sealed segments are cached in a byte-bounded cache. The open segment is read from its file.
- One item streams at a time and stays in memory until it completes; then the index stores it at the position it received when it started. Text beyond 256 KiB continues in a new item of the same kind, and one delta carries at most 64 KiB.
- An item that the provider adapter produced outside the protocol's limits is stored as the Lervo notice `conversation_item_invalid`, with no parameters, so every position stays filled.
- Each session keeps at most 1 MiB of sealed segments in memory.
- Retention: an index is removed with its workspace. All indexes on a host share a cap of 1 GiB. Each index directory holds an `opened` marker that the session host touches when the index opens; at that moment, the least recently opened indexes are removed until the rest fit. The index opening and the indexes of sessions the host still holds are never removed.

## State, events, privacy, and failure meaning

- **`lervo workspace start`.** The command reads the instruction from stdin. It takes `--repository` with a project ID from the host's repository registry, and optionally `--provider` (default `claude`), `--mode` (`native`, the default, or `cli`), and `--model`. It runs on the host where the repository lives; the session host there invokes it.
  - Before any change, it resolves the provider's hosted-session adapter and the provider CLI on `PATH`, and the adapter checks the launch intent. A refused intent changes nothing, not even a fetch.
  - **The workspace's base.** New work starts from the default branch's upstream tip, not from the owner's checkout, which may trail its upstream because Lervo's knowledge commits land there and nothing pulls it.
    - The default branch is the default a remote advertises (`origin` first), even when only the remote has it, as after `git clone -b <other>`, else a local `main` or `master`. Lervo never guesses: a repository that names none this way starts from the checked-out commit with the notice `base_unresolved`, as does any failure to choose a base. The fallback commit and the retire rule resolve the default branch the same way.
    - The upstream comes from `branch.<default>.remote` and `.merge`; a branch that follows a local branch (`remote = .`) has none. Lervo fetches the explicit refspec `+refs/heads/<branch>:refs/remotes/<remote>/<branch>` with `--no-write-fetch-head` and automatic maintenance off. That moves only that remote-tracking ref, whatever `remote.<name>.fetch` says, and the owner's branch never moves.
    - Git never waits for a person: `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, and ssh in batch mode unless `GIT_SSH_COMMAND` is set. Git runs in its own process group, so the 20-second deadline ends its remote helpers too. The fetch needs Git 2.29 or later, for `--no-write-fetch-head`; an older Git falls back with `fetch_failed`.
    - It carries along the knowledge commits on the default branch that the resident has not published, counted as the resident counts them ([ADR-0603](../../../decisions/knowledge/maintenance/0603-derive-knowledge-publication-from-repository-policy-and-judge-it-by-content.md)): non-merge commits that `Lervo Knowledge` both authored and committed, whose patch the upstream lacks, and that no merged publication carried, no replay conflict superseded, and no person declined. It reads only local state: the publication state, the supersession ledger, and this host's part of the history cache. Every such commit is replayed in order, so a later commit that undoes part of an earlier one, such as the resident's repair, still undoes it. Developer commits, and commits on another checked-out branch, stay in the owner's checkout.
    - Without an upstream, or when the fetch or any later step fails or takes too long, the workspace starts from the local tip with the notice `no_upstream` or `fetch_failed`. When the publication state exists but cannot be read, or shows earlier publications while this host's part of the history cache is missing, it starts from the upstream tip, carries nothing, and notes `knowledge_state_unreadable`. Without them, nothing says which commits a person declined or a squash published. The start goes on in every case.
    - Carried commits reach the workspace's pull request beside its work, outside the resident's publication scope check, and they can conflict with a later resident publication that changes the same file, such as the terminal hook launcher. Whichever merges second carries the same patch, which Git drops as already applied.
  - The **workspace** stage creates the branch `lervo/<words>-<6 hex>` at the base and replays the carried commits on it, committed by `Lervo Knowledge` like the originals, so the resident still recognizes them. The owner's hooks and signing never run. The replay is all or none, because a later commit may undo part of an earlier one and the resident never publishes a partial set either. A commit whose change the branch already holds counts as carried. When any pick conflicts, a pick runs past its 20 seconds, or the whole replay passes 45 seconds, the branch returns to its base, every commit counts as skipped, and the notice becomes `replay_incomplete`; the workspace still starts. With the fetch, the budget keeps a start inside the ADE's 120-second command deadline. When the branch cannot return to its base, the start fails and rolls back. The words come from the ASCII words of the title, or `work` when there are none. The stage puts the worktree at `~/.lervo/workspaces/<repository name>/<branch leaf>`, beside Lervo's other per-user state and apart from the owner's projects, so starting work never adds a folder beside or inside a repository. The place is the same on every host; on WSL, `~/lervo` is a checkout, so a visible `~/lervo` could not hold it. `LERVO_WORKSPACES_HOME` moves that root; when set, it must be a safe absolute path (not empty, no NUL, CR, or LF), as `LERVO_USER_STATE_DIRECTORY` must, or the start is refused with `workspace_home_invalid`.
    - Before anything changes, the start checks the repository's folder under the root, `<root>/<repository name>`. Inside a Git work tree, a `.git` folder, or a bare repository, it refuses with `workspace_home_invalid`, because workspaces there would fill that repository with untracked folders and nested worktrees. The check ignores inherited `GIT_DIR` and `GIT_WORK_TREE`. When Git cannot answer, the start goes on, and a missing Git fails the workspace stage anyway.
    - Repositories with the same name share `<root>/<name>/`. That is harmless: the branch leaf's six hex digits keep their workspaces apart, and open and retire find a workspace by its branch. It records the Git host's ownership marker in the worktree's Git directory. Workspaces started before Lervo 0.47.9 stay at `<repository>-wt/<branch leaf>`; Lervo finds every workspace by its branch, so they keep opening and retiring. The workspace ID is `wsp_` followed by 24 hex characters.
  - The **workstream** stage starts the workstream as `lervo workstream start --apply-now` would run in the new worktree: its events and the workspace branch's binding go to the registered repository, and the worktree keeps its own current projection ([ADR-0633](../../../decisions/execution/providers/hooks/0633-record-a-linked-worktree-in-its-registered-repository.md)). Every hook and Lervo command the session runs there records into the registered repository the same way, so its turn evidence, owner-rule captures, skills, plan items, and workstream survive retire. The title is the instruction's first line with text, its spaces collapsed, shortened to 80 characters at a word. The interface shows the same title while the core creates the workspace, from the one rule in `@lervo/session-host-contract`, so the header keeps its title when the workspace arrives. The objective is the instruction, within the workstream's 8,192-character limit.
  - The **launch** stage prepares the hosted launch and writes its launch descriptor record.
  - The JSON result holds `workspaceId`, `workstreamId`, `projectId`, `branch`, `sessionId`, `provider`, `launch`, and `base`. `base` is `{source, upstream, notice, replayed, skipped, carried}` with counts, never commits. The contract keeps `notice` an open lowercase name, so a notice a later CLI adds never fails an older ADE's start; the interface tells the user after the fact when a workspace started from the local tip or without its knowledge commits. The core link passes it on with the `workspace.start` result. The ADE shows a non-null notice as a Lervo notice under the first message of the started workspace's conversation, in words for each known notice and with the code for an unknown one, while the view continues the start. The `launch` field holds the absolute program path, the arguments, the added environment, the working directory, the conversation mode, and `initialInput`, which is the text the session host sends through the stream decoder.
  - If a stage fails, the command removes the worktree and deletes the branch, which it deletes only while the branch still points at the commit the workspace stage left it on. It then reports the failed stage. Removing the worktree removes its current projection; the workstream's events already recorded in the repository stay as history.
- **`lervo workspace open`.** It takes `--workspace` and optionally `--mode`, and prepares the launch that continues the workspace's hosted session. It resumes the recorded session where the adapter declares `resume`, and otherwise starts a new session in the same worktree. It finds the worktree from the record's project and branch, and records the new launch.
- **`lervo workspace retire`.** It takes `--workspace` and removes a hosted workspace its user is done with; the core-link command `workspace.retire` does the same for the ADE. It never discards work:
  - It finds the workspace's newest launch record and its registered repository, and the worktree that has the workspace's branch checked out.
  - It refuses with `workspace_in_use` while any other process has its working directory inside the worktree, such as the provider of a running session. Linux, including WSL, reads `/proc`. macOS asks `lsof`. When it cannot list the directories, it refuses with `workspace_use_unverifiable`.
  - It refuses with `workspace_has_changes` while the worktree holds changes to tracked files or untracked files Git does not ignore. It then removes the worktree with `git worktree remove`, which itself refuses a worktree that changed in between. Ignored files, such as the workspace's own `.lervo/state`, leave with it.
  - It deletes the branch only when it has the form `lervo/<words>-<6 hex>` and nothing on it is missing elsewhere: its tip is in the default branch or its upstream, or every commit beyond the upstream copies a patch the default branch or the upstream holds, as the commits a workspace replayed at its start do. A merge counts as work, and so does any commit made in the workspace, even one Lervo made. Otherwise it keeps the branch, so the work stays one `git worktree add` away.
  - It removes the session settings files of every session the kept launch records name for the workspace. It leaves the records; `workspace.list` no longer lists a workspace whose worktree is gone, and the records leave with the bound of 256.
  - It records no event. The result is `{workspaceId, worktree, branch}`: `worktree` is `removed` or `absent`, and `branch` is `deleted`, `kept`, or `absent`. Retiring a workspace that is already gone finishes what remains.
  - In the ADE, the selected workspace's header holds a quiet trash button when the core advertises `workspace.retire`. It asks "Remove this workspace?" in place, with Cancel focused and Escape cancelling. On Remove, the interface stops a running session with `session.stop`, waits up to 15 seconds for its `ended` status, and then sends `workspace.retire`. It shows a refusal in the header and otherwise returns to the start screen.
- **Hosted session events.** The four events below need event schema 10 ([event envelope compatibility](../events-and-privacy/event-envelope-compatibility.md)). Lervo records them in the registered repository's store, not in a workspace's worktree, which selects no writer of its own. A writer below schema 10 records none of them, and the launch goes on. The results of `lervo workspace start` and `lervo workspace open` report `hostedEvents`: `recorded`, `inactive` below schema 10, or `unavailable` when the store could not take them. A session appears in them only as `providerSessionDigest`, the SHA-256 digest of the provider name and the session UUID, which terminal turn events also use. The UUID stays in the host's launch descriptor record. The envelope's `occurredAt` dates each event, and its `policyVersion` binds it to the policy in force.
- **`application.workspace.started`.** The required fields are `workspaceId`, `workstreamId`, `branch`, `providerSessionDigest`, `instructionDigest`, and `startedAt`. The branch must have the form `lervo/<words>-<6 hex>` that `lervo workspace start` gives it. The instruction text stays in the provider conversation; the event holds only its digest.
- **Hosted usage records (ADR-0632, S2b).** The session host's decoder records each provider result's usage, one record per model, as `resource.usage.recorded` with hosted attribution. This needs event schema 11. The [payload contract](../events-and-privacy/event-envelope-compatibility/payload-contracts/resource-usage-recorded.md#hosted-sessions-schema-11) defines the fields. Claude's per-result `model_usage_since_last_result` deltas give the counts, so a session's records sum to the provider's totals.
  - Hosted usage shares the managed usage event because both are AI usage the core records. One ledger keeps one token vocabulary, so a future total-usage reader selects records by attribution instead of merging two event types. Managed accounting, supervision spend, and work reports read only managed records, so the owner's own ADE turns never count as agent spend under a mandate.
  - The record holds counts, a list-price cost or null, and digests only. No field carries prompt, reply, or tool text. A result that reported no usage records nothing, never a zero.
  - **Writer.** The resident process records the usage. A decoder opened with the launch's `sessionId` hands each finished turn's usage, with the adapter's accounting descriptor, to the resident's bounded queue ([core link](ade-core-link.md)). The queue records into the repository of the session's newest launch record.
    - Before the first record that cites the descriptor, the writer stores the descriptor's canonical bytes in the repository's artifacts and reads them back to check the hash.
    - The coordinate of a record is the digest of the session digest, the provider's result ID, and the model key. It names the event, `resourceObservationId`, and `sourceCoordinateDigest`, so a replayed decode records each result once.
    - `usage.inputTokens` is the uncached input plus both cache kinds. `cachedInputTokens` is the cache reads, and `cacheCreationInputTokens` sits beside the usage.
    - A result whose provider reported no reasoning count records 0 with status `partial` and reason `reasoning_unreported`. A model name the hosted pattern refuses, or a cloud ARN without a resource path, records the identity's unavailable form with reason `model_name_invalid`.
    - From an older Claude Code without per-result model usage, a result's own `usage` gives one record under the turn's last model, with a null cost and `costBasis: unreported`.
  - **Failure meaning:**
    - Below writer schema 11, no usage is recorded and the launch goes on, as with `hosted_events_inactive`.
    - When the accounting descriptor cannot be stored, the session records no usage that would name it, and the conversation goes on.
    - A payload the event screen refuses, such as cache counts above the input, is dropped and counted, never recorded partially.
    - A session that no launch record names records nothing. Neither does a decoder opened without a `sessionId`, as with a resident process from before `decoder.session`.
- **Launch descriptor record.** Before each launch, Lervo writes `{schemaVersion: 1, workspaceId, sessionId, provider, projectId, branch, conversationMode, argumentDigest, settingsDigest, mcpConfigDigest, preparedAt, base}` to `hosted-launches.json` in the user state directory, beside the repository registry, with mode 0600. It holds no instruction text, environment values, credentials, or paths. The branch name derives from the title's ASCII words, which Git already shows. `argumentDigest` covers the program and arguments, because the arguments of a CLI conversation carry the first instruction. `base` records where a started workspace began: `{commit, source, upstream, replayed, skipped, carried, notice}`. `source` is `upstream` or `local`, and `upstream` is the ref such as `origin/main` or null. `replayed`, `skipped`, and `carried` list knowledge commits. `notice` is `base_unresolved`, `no_upstream`, `fetch_failed`, `knowledge_state_unreadable`, `replay_incomplete`, or null. Records written before Lervo 0.47.7 have no `base`. Lervo retains the newest 256 records.
- **`terminal.session.launch_prepared`.** The required fields are `providerSessionDigest`, `provider`, `workspaceId`, `conversationMode`, and `descriptorDigest`, the digest of the launch descriptor record. Lervo records it after the record, before `lervo workspace start` or `lervo workspace open` returns; start records `application.workspace.started` with it. If preparation fails, the launch stage fails and rolls back, as `workspace_start_failed` describes. The ADE offers no CLI conversation to fall back to ([ADR-0617](../../../decisions/execution/applications/0617-offer-only-claudes-native-conversation-in-the-ade-for-now.md)).
- **`terminal.session.launched`.** Lervo's `SessionStart` handler records it when the session ID is one that Lervo prepared, for every `source`. The required fields are `providerSessionDigest`, `provider`, and `descriptorDigest`. A missing event means `launch_unconfirmed`.
- **`terminal.tool.observed`.** It arrives with S2 under a later event schema version. The required fields are `providerSessionDigest`, a digest of the tool use ID, the tool name, the phase (`pre`, `post`, or `failed`), the source (`hook` or `stream`), and the outcome. As in ADR-0010, the event excludes tool input, command text, output, and absolute paths.
- **`terminal.instructions.loaded`.** It arrives with S2 under a later event schema version. The required fields are `providerSessionDigest` and the repository-relative path. The content hash is present when Lervo can read the same bytes.
- **`terminal.session.ended`.** Lervo's `SessionEnd` handler records it, with a null `exitCode`. When the process ended without that hook, for example after a crash or SIGKILL, the session host's `session.exited` report records it with `process_exited` and the exit code ([core link](ade-core-link.md)). An end that the hook already recorded is not recorded twice. The required fields are `providerSessionDigest`, `endReason`, and `exitCode`.
  - `endReason` is `clear`, `logout`, `prompt_input_exit`, or `other` from `SessionEnd`, with any reason the provider adds later recorded as `other`, or `process_exited` from the session host.
  - `exitCode` is the process exit code from 0 to 255, or null after a signal or when unknown.
- **Failure meanings.**
  - `workspace_start_failed`: a stage of `lervo workspace start` failed. The `stage` field is `workspace`, `workstream`, or `launch`. Nothing from the earlier stages remains, and the ADE shows the instruction again so that the user can retry.
  - `session_host_unavailable`: the UI cannot reach the session host and restarts it. Sessions end only when the session host itself exits.
  - `provider_cli_unavailable`: the provider CLI is missing or not admitted under ADR-0536. This is notice-only, and shell sessions keep working.
  - `provider_login_unavailable`: the CLI reports no login. This is notice-only.
  - `workspace_in_use`, `workspace_has_changes`, `workspace_use_unverifiable`: retiring a workspace refused and changed nothing. The session host passes each on as `application_failed` with the parameter `coreCode`.
  - `launch_preparation_failed`: the launch stage failed, which `workspace_start_failed` reports with `stage: launch`.
  - `hosted_events_inactive`: the registered repository's writer selects a schema below 10, so Lervo recorded no hosted session event. The launch goes on, and `hostedEvents` reports `inactive`. `lervo upgrade` activates the current target, schema 14, once every configured reader reads it.
  - `provider_unknown`: no admitted hosted-session adapter has that provider name. The result lists the admitted ones.
  - `conversation_mode_unsupported`: the provider does not declare `nativeConversation`, so only the CLI conversation can start. Nothing changed.
  - `resume_unsupported` and `launch_intent_invalid`: the adapter refused the launch intent before any change.
  - `workspace_not_found`: `lervo workspace open` found no launch record for the workspace, or its worktree no longer exists.
