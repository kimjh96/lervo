# Responsibility, authority, and workforce decisions

## Responsibility and authority

| Responsibility | Required behavior | Boundary |
| --- | --- | --- |
| Product owner | Own the outcome, decompose work, inspect staff, allocate and hire, define responsibilities, resolve local blockers, review results, and report. | One bound repository team and its approved resources. Delegation retains accountability. |
| Central coordinator | Resolve project ownership, arrange cross-team support, handle shared infrastructure escalation, and resolve portfolio resource conflicts. | Observation grants neither repository writes nor transfer of workers' authority. |
| Assigned worker | Execute the current responsibility contract, preserve evidence, report blockers, and return artifacts to the reviewer. | Exact role, capability ancestry, assignment lease, workspace, and granted effects. |

Tarin and Vero are deployment identities, not core types. Product owners independently define and revise hired workers' responsibilities, expected artifacts, acceptance criteria, decision latitude, reporting conditions, and collaboration boundaries. Built-in roles are templates, not fixed job descriptions: researchers need not always be read-only, and product owners need not always save every artifact.

Role changes use versioned repository sources and validated agent bindings. Assignment changes bind exact role hashes and paths. Never silently mutate an active worker's contract: pause admission, resolve its lease through existing cancellation/reconciliation rules, publish the new binding, then admit the successor attempt. Unaffected workers retain their bindings.

Each goal has one accountable owner; each assignment has one current executor and one acceptance owner. The coordinator receives escalations without duplicating assignments. Ownership transfer requires recorded successor acceptance; until then, the original owner retains follow-up responsibility. Cross-repository requests bind separate workstreams through explicit handoffs, without cross-repository leases or merged histories.

## Context and workforce decisions

Before planning, read the verified workstream, canonical product decisions, instructions, current assignments, active staff, capability readiness, pending decisions, and resource observations. Use Lervo retrieval and read exact source bytes. Keep engine identity, candidates, selection, loading, injection, and references distinct. Search silence proves neither prior knowledge nor staff absent. Failed retrieval uses verified available sources with explicit coverage limits, or blocks only dependent decisions.

Compare existing staff by demonstrated capability, role, workload, path conflicts, and availability. Prefer a suitable existing worker; choose reassignment, owner execution, borrowing, or hiring when evidence supports it. Headcount must address a skill or capacity gap, not conceal a broken environment. Record the selected option and bounded rationale in an exact artifact. No minimum headcount or specialist chain is required.

Before dispatch, validate provider/tool availability, CLI access when needed, read/write scope, knowledge access, source policy, verification suites, budget, and workspace readiness. A visible speaker and successful greeting do not prove task readiness. If a worker can research but cannot save, the owner may separate research and persistence with explicit handoff and verification ownership. Formal research completion still requires its source policy and verification suite.
