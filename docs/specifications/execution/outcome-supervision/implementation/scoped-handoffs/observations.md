# Installed observations

Optional `outcomeSupervision.handoffPeers` launch configuration contains at most eight distinct foreign projects. Each route pins an absolute repository root, repository-instance ID, project ID, team ID, and supervision binding. Owner-installed paths locate observations; model output cannot install routes or grant authority. Observation is limited to repositories accessible to the same host, with no remote write endpoint or implicit Hub routing.

Peer storage opens existing SQLite and CAS stores read-only. It verifies the current storage schema, project manifest, event integrity, repository-instance marker, coordination layout, mandate, workstream, and active owner. It never initializes or migrates peers, creates assignment state, changes permissions, or writes artifacts. Missing, stale, conflicting, or revoked authority makes the observation unavailable. Local work remains available when independent of that peer.

The Node records a bounded peer view in its own event/CAS store under the local owner fence. Views omit repository paths and raw errors and include exact owner coordinates, current goal, and directed handoff receipts. Receipt observation checks the original admitted policy decision and immutable effect; a hash or matching event name alone is insufficient. Historical successor acceptance remains evidence after later peer unavailability but does not extend the recipient's current execution authority.

Persistent read-only handles cache unchanged committed heads. WAL change hints wake the same serialized owner loop. A 60-second authority audit covers changes without usable hints, including coordination-file changes. Unchanged semantic views append no event and invoke no model. Each view contains at most 32 incoming offers and 32 acceptances. The existing 4,096-event supervision-journal bound and 32-project retained-view bound require compaction before further admission. Evidence is never dropped to make room.
