# Reuse

## Semantic basis and spend

The semantic basis retains goal, mandate, role, assignment, and task evidence, excluding the reasoning run itself. A matching successful result can be reused after runtime reopen. Reuse checks the current trigger, task basis, and source bytes; it never creates another provider invocation.

The basis includes the explicit result-reference contract: schema version 1, JSON format, and standalone comments in decoded string values. This identifies the repaired structured-output projection, not a restart or another event.

Earlier failed calls and their exact diagnostics remain canonical on their historical basis. A new basis may admit its own bounded attempts only after prior effects settle and ordinary authority and resource checks pass. The independent owner-lineage spend allowance charges every historical reservation. Changing this contract neither refunds tokens, renews an epoch, nor widens a mandate.

## Failed result evidence

Historical confirmation proves only that the model invocation settled; it does not accept the proposed business effect. Malformed outer JSON can leave `run.failed/contract_validation_failed`.

Before propagating a projection failure, the managed result boundary preserves its actual validated raw adapter bytes in private CAS and `adapter.result.captured`. It emits no publication or context-reference success. `referenceTelemetry: supported` describes the managed evidence boundary, not successful parsing or semantic acceptance.

Only an exact captured result with a matching failed run, acknowledged stop, and observed native usage can enter malformed-result correction. Its private bytes must actually fail JSON parsing. Unknown stop, missing usage, conflicting captures, valid JSON with another reference failure, or telemetry failure retains uncertainty.

Retry context binds the original failed result hash and admitted reasoning plan. It neither fabricates a completed run nor refunds spend.

## Bounded proposal correction

A completed result whose outer JSON or bounded responsibility fields violate the canonical contract must not be endlessly rematerialized. The native owner verifies the exact stored reasoning result, classifies malformed reasoning, an invalid path, or an invalid task contract, and records its plan and result hashes in a version-two reasoning context for the next attempt on the unchanged semantic basis.

The previous model proposal remains evidence, not a business effect. Version-one contexts remain readable. Only the next owner reasoning turn may correct model-authored details; neither the host nor a retry may silently rewrite a glob or broaden a path.

After the mandate's bounded reasoning attempts (at most three), one `owner_proposal_invalid` local attention effect settles the need without a worker launch. Changed canonical facts start a separate basis. Uncertain or unconfirmed prior reasoning never authorizes a retry.

## Feedback and revalidation

The version-two `proposalFeedback` object contains exactly:

- `reasonCode`: `invalid_reasoning_result`, `invalid_expected_path`, or `invalid_task_contract`.
- `reasoningPlanHash`.
- `resultArtifactHash`.

It is stored only in the private context artifact. Revalidation requires the prior admitted decision and completed run with those exact hashes. No raw proposal, repository path, prompt, or provider error is added to an operational event.

Missing or conflicting evidence invalidates context reuse; it must not be treated as a completed correction.
