# Reuse

The semantic basis retains goal, mandate, role, assignment and task evidence, excluding the reasoning run itself. A matching successful result can be reused after runtime reopen. Reuse checks the current trigger, task basis and source bytes and never creates another provider invocation.

Historical confirmation proves only that the model invocation settled; it does not accept the proposed business effect.

A completed result whose outer JSON or bounded responsibility fields violate the canonical contract is not endlessly rematerialized. The native owner verifies the exact stored reasoning result, classifies malformed reasoning, an invalid path or task contract, and records its plan and result hashes in a version-two reasoning context for the next attempt on the unchanged semantic basis. The previous model proposal remains evidence, not a business effect. Version-one contexts remain readable. Only the next owner reasoning turn may correct the model-authored details; neither the host nor a retry silently rewrites a glob or broadens a path. After the mandate's bounded reasoning attempts (at most three), one `owner_proposal_invalid` local attention effect settles the need without a worker launch. Changed canonical facts start a separate basis; uncertain or unconfirmed prior reasoning never authorizes a retry.

The version-two `proposalFeedback` object contains exactly `reasonCode` (`invalid_reasoning_result`, `invalid_expected_path`, or `invalid_task_contract`), `reasoningPlanHash`, and `resultArtifactHash`. It is stored only in the private context artifact. Revalidation requires the prior admitted decision and completed run with those exact hashes. No raw proposal, repository path, prompt, or provider error is added to an operational event. Missing or conflicting evidence invalidates context reuse rather than being treated as a completed correction.
