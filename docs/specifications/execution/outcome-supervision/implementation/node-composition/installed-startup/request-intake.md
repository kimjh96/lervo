# Installed supervision request intake

An active installed owner can bind one request to its current workstream through local stdin or its configured Discord speaker. Both call the same Node intake under the exclusive owner lease. The writer checks the current mandate, workstream revision, assignment graph and latest event hash before appending `work.supervision.bound`. The event records supervision, owner, mandate, workstream revision, graph hash, snapshot cause, request artifact hash and acceptance artifact hash. It does not record request text, external message IDs or participant IDs.

The request artifact stores the bounded text, source kind, source and requester digests, content hash and, for Discord, an exact result origin. The writer and reader verify the text digest; the reader also verifies the Discord source digest against the bound source event. The acceptance artifact pins the workstream objective, snapshot and assignment IDs at admission. The reader reconstructs the assignment set from creation events before the binding sequence, independent of wall-clock timestamp ties. Both artifacts use local CAS. An exact replay of the same source and content returns its existing event; a changed source or second origin for that goal fails closed. A failed or unobserved commit does not authorize replaying a provider effect.

A refusal is typed with one bounded code and writes nothing: `request_invalid`, `identity_conflict`, `workstream_inactive`, `origin_conflict`, `authority_changed`, `evidence_changed`, or `owner_busy`. Any other failure is uncertain because the commit may have happened. The owner loop holds the owner fence for a whole cycle, so admission polls the fence until its deadline: 30 seconds for local stdin and 120 seconds for a Discord speaker, which covers about two idle owner cycles. Expiry refuses with `owner_busy` and records no event, artifact, or provider effect. An installed journey observed the earlier 30-second Discord bound expiring four seconds before the owner released its idle cycle, so the request was refused although the goal had no request.

The result origin's `actor` is the outbound product-owner speaker, not the incoming requester. Native owner reasoning reads the exact durable interaction inbox row for a Discord-bound source event without mutating the inbox. For ordinary `message.created` intake it also reads the immutable intent row and requires the same message hash, `continue_work`, `relevant`, medium or high confidence, and the exact no-argument `supervision_goal_request` effect. The inbound actor must be human and its content, target, policy, integration, and conversation must match the stored result origin; a mention is not required. Historical `goal.requested` provenance retains its original owner-mention checks. A missing inbox or natural-intent row supplies no human proof; a conflicting or invalid row fails closed. This adds a bounded reasoning fact, not a new event or request-artifact field.

An approved successor mandate retains the one original request and result origin. The writer replays the exact source, requester and content against that original binding without adding an event. The reader validates the installed mandate history before accepting a binding made under an earlier mandate for the same supervision, workstream, and owner. A binding from an unrelated mandate or a later installation cannot become the request origin.

Discord routing uses this path only when its durable responding agent ID equals the installed owner ID. The conversation intent and effect-request authority checks still precede intake, and the responder rechecks human or explicitly admitted agent authority. The accepted result is published to the bound source origin through the existing independently reviewed result-delivery path. The immediate response proves only that canonical binding succeeded. Local `--request-stdin` avoids request text in process arguments and runs the same owner loop after binding; local results remain canonical without external publication.

Discord goal intake uses the ordinary authenticated `message.created` path. The managed turn resolver is offered `supervision_goal_request` for a registered product owner or CEO; when supervision is installed, that durable agent ID must equal the installed owner. It selects the effect for a durable multi-step outcome and keeps one bounded task or inspection on `repository_work` ([ADR-0410](../../../../../../decisions/execution/orchestration/governed-work/0410-intent-routed-supervision-goal-intake.md)). The immutable intent record binds the message hash, provider/model evidence, confidence, participation, effect, digest, and time without copying raw text. A medium- or high-confidence installed-owner effect calls the same shared intake writer; a missing route, unavailable effect, low confidence, or unauthorized agent request does not. The Node registers no `/goal` command and accepts no `outcomeSupervision.goalCommand` configuration. Historical `goal.requested` events remain schema-valid and retain their original provenance meaning, but new goal admission does not bypass model classification based on event kind. A successful installed-owner reply proves only canonical binding. Typed refusals name the bounded reason and write nothing; any unclassified failure follows the normal visible uncertain-response contract.

A registered product owner or CEO without an installed supervision binding is also offered the effect, but its responder can only retain a `pending_authority` receipt. The owner-only SQLite row records event, project, intended owner agent, content and source-key hashes, conversation/thread, requester identity coordinates, status, and time. It contains no raw request and has an immutable 1,024-row bound. Exact replay is idempotent. Conflict, capacity, unsafe storage, or write failure produces no execution claim and follows the visible failure contract. Pending authority never counts as `work.supervision.bound`, goal creation, mandate installation, provider start, or delivery.

Binding an unrelated request to an existing objective is not a goal amendment. A new objective, revised acceptance criteria, or additional recipient needs a separate workstream and authority transition. Installed production acceptance must observe the real ingress, owner cycle, permission recovery, accepted result and delivery under settled authority.

Once the original workstream is settled and completed, a successor workstream may start with a new ID and exact predecessor hash. This preserves the prior local or Discord source binding while giving a later request a distinct goal identity. The successor still needs its own reviewed mandate and installed owner binding; workstream succession alone grants no execution or publication authority.

The natural intake response identifies admission to the current installed goal. It does not imply creation of an unrelated goal.

## Standing lineage

When configuration selects `outcomeSupervision.standing` ([ADR-0405](../../../../../../decisions/execution/orchestration/governed-work/0405-standing-supervision-lineage.md)), the named binding is the root of a lineage and intake first resolves the latest verified successor. The walk verifies the derivation on each successor's creating installation and then follows that successor's latest installed mandate, so a reviewed later version of a running goal's mandate is followed rather than rejected. A running service scans for such an installation after each owner cycle and rebinds to it without a restart, which is what lets an operator widen a stuck goal's ceilings while its owner keeps running. Binding under an active goal is unchanged. When the current goal is settled and the current mandate still carries `successorAuthority`, the same intake starts the next goal before binding: it records a successor workstream whose objective is the request text, installs the derived mandate `<parent>.s<n>` under the successor's own owner fence, then appends `work.supervision.bound` under the new binding and tells the running service to follow it. The transition itself is refused with `workstream_inactive` when the goal is not settled or the grant is exhausted; it uses the existing typed refusals and adds no event type. A request that arrives on an active goal with another origin is still refused with `origin_conflict`. A running standing service also scans new events after every owner cycle, including a failed cycle on the settled goal, for the next successor installation under its root grant; when another process such as the local command started that successor, the service rebinds to the verified lineage head without a restart.
