# Installed supervision request intake

An active installed owner can bind one request to its current workstream through local stdin or its configured Discord speaker. Both call the same Node intake under the exclusive owner lease. The writer checks the current mandate, workstream revision, assignment graph and latest event hash before appending `work.supervision.bound`. The event records supervision, owner, mandate, workstream revision, graph hash, snapshot cause, request artifact hash and acceptance artifact hash. It does not record request text, external message IDs or participant IDs.

The request artifact stores the bounded text, source kind, source and requester digests, content hash and, for Discord, an exact result origin. The writer and reader verify the text digest; the reader also verifies the Discord source digest against the bound source event. The acceptance artifact pins the workstream objective, snapshot and assignment IDs at admission. The reader reconstructs the assignment set from creation events before the binding sequence, independent of wall-clock timestamp ties. Both artifacts use local CAS. An exact replay of the same source and content returns its existing event; a changed source or second origin for that goal fails closed. A failed or unobserved commit does not authorize replaying a provider effect.

A refusal is typed with one bounded code and writes nothing: `request_invalid`, `identity_conflict`, `workstream_inactive`, `origin_conflict`, `authority_changed`, `evidence_changed`, or `owner_busy`. Any other failure is uncertain because the commit may have happened. The owner loop holds the owner fence for a whole cycle, so admission polls the fence until its deadline: 30 seconds for local stdin and 120 seconds for a Discord speaker, which covers about two idle owner cycles. Expiry refuses with `owner_busy` and records no event, artifact, or provider effect. An installed journey observed the earlier 30-second Discord bound expiring four seconds before the owner released its idle cycle, so the request was refused although the goal had no request.

The result origin's `actor` is the outbound product-owner speaker, not the incoming requester. Native owner reasoning reads the exact durable interaction inbox row for a Discord-bound source event without mutating the inbox. It reports verified human provenance only when the hashed inbound event is `goal.requested`, its actor is human, its content and target match the bound request, and its policy, integration, conversation and owner mention match the stored result origin. A missing inbox row supplies no human proof; a conflicting or invalid row fails closed. This adds a bounded reasoning fact, not a new event, request artifact field or claim that an outbound agent actor initiated the slash command.

An approved successor mandate retains the one original request and result origin. The writer replays the exact source, requester and content against that original binding without adding an event. The reader validates the installed mandate history before accepting a binding made under an earlier mandate for the same supervision, workstream, and owner. A binding from an unrelated mandate or a later installation cannot become the request origin.

Discord routing uses this path only when its durable responding agent ID equals the installed owner ID. The conversation intent and effect-request authority checks still precede intake, and the responder rechecks human or explicitly admitted agent authority. The accepted result is published to the bound source origin through the existing independently reviewed result-delivery path. The immediate response proves only that canonical binding succeeded. Local `--request-stdin` avoids request text in process arguments and runs the same owner loop after binding; local results remain canonical without external publication.

The installed owner registers a guild-scoped `/goal request:<text>` application command for its allowlisted Discord guilds only when supervised work routing is configured. An authenticated `INTERACTION_CREATE` bypasses ordinary message and READY history-reconciliation queues. Its acknowledgement starts before intake with a two-second network timeout to meet Discord's response window when the service and network are healthy. The Gateway retains the greatest observed sequence across that bypass for safe resume. The public acknowledgement message ID becomes the exact source message for a normalized `goal.requested` event and later result replies. Its command text remains in local CAS; the event carries a content reference, hashed source key, human actor, target, own-speaker mention, null reply and signal, automation depth zero and timestamp. The interaction token exists only in memory for the acknowledgement and status edit; it is never written to repository state, event payloads or artifacts. `goal.requested` is schema version 1 and always routes directly to work without model classification. A malformed or unauthenticated command is rejected before acknowledgement; an out-of-scope channel receives a scoped rejection. A failed intake is shown as failure; a later processing error is shown as uncertain because canonical binding or delivery may already have occurred. The final acknowledgement edit repeats only the intake outcome that the supervised work responder recorded in process memory for that exact inbound event: bound, duplicate, refused with its bounded code, or uncertain. A missing record is shown as uncertain, never as a connected request, because processing can complete through an unrelated route or after a caught failure. A refusal is also answered as a normal reply naming the bounded reason, so a second origin for a goal that already has one is reported as refused rather than as a generic response failure. An uncertain acknowledgement POST is reconciled by reading its original message and is never replayed. A status edit cannot by itself prove owner admission, result acceptance or publication; those remain separate canonical observations.

Binding an unrelated request to an existing objective is not a goal amendment. A new objective, revised acceptance criteria, or additional recipient needs a separate workstream and authority transition. Installed production acceptance must observe the real ingress, owner cycle, permission recovery, accepted result and delivery under settled authority.

Once the original workstream is settled and completed, a successor workstream may start with a new ID and exact predecessor hash. This preserves the prior local or Discord source binding while giving a later request a distinct goal identity. The successor still needs its own reviewed mandate and installed owner binding; workstream succession alone grants no execution or publication authority.

The `/goal` command description and acknowledgement identify the current installed goal. They do not imply creation of an unrelated goal.

## Standing lineage

When configuration selects `outcomeSupervision.standing` ([ADR-0405](../../../../../../decisions/execution/orchestration/governed-work/0405-standing-supervision-lineage.md)), the named binding is the root of a lineage and intake first resolves the latest verified successor. Binding under an active goal is unchanged. When the current goal is settled and the current mandate still carries `successorAuthority`, the same intake starts the next goal before binding: it records a successor workstream whose objective is the request text, installs the derived mandate `<parent>.s<n>` under the successor's own owner fence, then appends `work.supervision.bound` under the new binding and tells the running service to follow it. The transition itself is refused with `workstream_inactive` when the goal is not settled or the grant is exhausted; it uses the existing typed refusals and adds no event type. A request that arrives on an active goal with another origin is still refused with `origin_conflict`.
