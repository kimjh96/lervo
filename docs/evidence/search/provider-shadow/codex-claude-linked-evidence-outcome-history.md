# Outcome and remaining work

The work produced fresh same-input paired measurements, normalized provider-native carriers to one exact token-set contract, captured complete Codex and Claude usage and durable failure evidence, enforced privacy, replay, and no-effect requirements, and achieved mean precision above 65% for both providers in provider-shadow work.

V11 repaired the observed Codex recall failure without provider-specific routing, expected-path exposure, candidate changes, retries, or threshold relaxation, while preserving Claude recall. Increased terse-release selections reduced precision and byte savings but remained above the then-current gates.

V12 retained 100% valid-observation recall for implementation and terse release but did not complete hybrid search or fuzzy merge. One Codex result violated the exact-token grammar, and Claude's partial two-case precision was below the full-population mean threshold. V12 was rejected without retry.

V13 completed a fresh full population without carrier failure and did not erase V12. One Claude observation selected three unexpected implementation-release sources and reached 40% precision, exposing a new blocker.

V14's provider-neutral request-scoping correction kept Claude at or above the unchanged per-observation precision boundary and made all seven valid Codex selections exact. The final Codex result added prose outside the exact token-set carrier. Recovery made no additional call and retained the bounded violation code. V14 was rejected; a successor had to diagnose the carrier failure before another call. The two ambiguous cases remained excluded without reclassification, and activation remained blocked.

V15 confirmed that Codex's native response-schema path rejected `uniqueItems`; removing the redundant keyword preserved parser-side duplicate rejection. V16 then completed with valid common structured carriers. Claude passed, but one Codex fuzzy-merge result retained the later approval while omitting its distinct conflict-resolution prerequisite. The provider-neutral V17 rule treated each side of compare, reconcile, merge, and conflict-resolution relations as independently required until bodies explicitly proved equivalence or subsumption. V16 remains rejected; no activation is inferred.

V17 passed the two-case diagnostic. Both providers retained every relevant relation side; Codex was more selective and materially faster in this sample. This authorized only a fresh four-case confirmation: it neither erased earlier failures nor proved production readiness.

V18 passed the fresh four-case confirmation without retry. Both providers retained every relevant source in every observation. Codex selected nine fewer sources, loaded 44,575 fewer body bytes, used 73.83% less provider time, and reported 6.00% fewer tokens than Claude. This supports a separate managed-context canary and activation design review for the reviewed population. It does not authorize or prove a canary, direct-terminal behavior, operational search changes, or production activation.

[ADR-0277](../../../decisions/search/activation/provider-shadow-structured/0277-stage-managed-context-relational-canary.md) defines a default-off, managed-run-only, provider-neutral selector with strict E1-E4 evidence separation and a later isolated read-only ceiling of 16 runs and 32 calls. It authorizes implementation and provider-free verification only. Live execution and managed-context effects require an exact prepared checkpoint bound to an eligible registered corpus and rollback predecessor.

The first exact canary stopped before any task sample because Codex app-server could not prove the selection turn tool-free. The later Responses-based v2 checkpoint remained unexecuted because making a separate API credential the normal product prerequisite was rejected. [ADR-0282](../../../decisions/search/activation/provider-shadow-structured/0282-remove-api-key-requirement-from-managed-context-canary.md) prepared a key-free v3 task-only projection, but exact replay showed no added Codex source and only one added Claude source across the paired population. V3 was rejected before execution with zero calls.

[ADR-0283](../../../decisions/search/activation/provider-shadow-structured/0283-prepare-deterministic-linked-context-canary-v4.md) proved a population where every run selects exact bounded current linked candidates. [ADR-0284](../../../decisions/search/activation/provider-shadow-structured/0284-prepare-exact-deterministic-native-session-canary-v5.md) bound the schema-v2 runtime, and [ADR-0285](../../../decisions/search/activation/provider-shadow-structured/0285-authorize-exact-key-free-managed-canary-v6.md) bound exact authorization and fail-first execution. Managed v11 completed the first full measurement after correcting the context-forwarding boundary. It proved call reduction, full recall, provider timing, and usage observations, while Claude's precision failures kept activation blocked. Managed v12 completed a fresh full population with a stricter provider-neutral E4 instruction. It improved mean precision but introduced two Codex recall failures and retained two Claude per-run precision failures. The correction was rejected and rolled back; the next design had to add a typed task-evidence versus governance-context boundary before another live canary.

Managed v14 completed the same paired population after implementing that typed boundary. It restored full Codex recall and kept full Claude recall, but Claude still failed two per-run precision gates and the provider mean gate. [ADR-0296](../../../decisions/search/activation/provider-shadow-structured/typed-context/0296-reject-activation-after-typed-context-managed-canary-v14.md) rejects activation and requires a task-evidence eligibility diagnosis before any successor call.
