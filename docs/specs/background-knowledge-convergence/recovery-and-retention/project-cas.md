# Project CAS retention

The project content-addressed store (CAS) holds immutable artifact bytes. [ADR-0534](../../../decisions/operations/storage/0534-bound-installed-runtimes-and-convergence-artifacts.md) extends typed derived-state and checkout retention to obsolete convergence artifacts. Events remain immutable. General `.lervo/data` pruning remains unauthorized.

## Exact reachability

1. A candidate must already exist as a regular CAS object and be named by `inputArtifactHash`, `resultArtifactHash`, `dependencyHash` or `evidenceHash` in a convergence baseline or stage event. Other CAS objects are always retained, including objects not yet published by their writer.
2. For every open obligation, every hash or CAS URI anywhere in its event payloads is a root. For every settled obligation, the latest stage whose state is neither `queued` nor `running` roots its entire payload. Settlement includes current, superseded and attention outcomes.
3. Every successful `normalization_apply` stage roots its payload, including its result input and receipt graph. Every convergence terminal payload is a root, preserving historical lifecycle receipt digests. The latest `knowledge_sources_parked` stage also roots its payload for carry across obligations.
4. Every non-convergence event payload remains a root, regardless of age. All noncandidate CAS objects remain roots for their embedded references. This includes archived assignments and completed provider results.
5. Files under `.lervo` and the repository coordination home root their embedded hashes and CAS URIs. This covers normalization and canonicalization candidates, instruction capture, terminal evidence, materialization journals, provider review caches, workforce records, workspace records and recovery checkpoints. SQLite tables are read as logical cells, including long values spanning overflow pages. Event storage is read through the canonical event interface; SQLite report bodies are followed through the report reader.
6. References use `sha256:<64 hex>` or `lervo-cas://sha256/<64 hex>`. The collector follows candidate-to-candidate references to a fixed point. It scans retained object bodies conservatively, so incidental matching strings may retain extra objects.
7. Only unmarked candidates whose object modification time and latest direct convergence reference are both older than fourteen days may be unlinked. Unknown artifact ownership is protection, never deletion authority.

CAS temporary publication files, query indexes, convergence checkout contents, collector projections and worker lock files are outside reference-body scanning. Query indexes are rebuildable and do not own artifact lifetimes. Their canonical inputs remain roots. Links, unreadable reference files, changing references or exceeded inventory limits stop the pass. An invalid collector projection starts a fresh reference scan. No object from another subsystem is selected for deletion merely because it has no observed reference.

## Background bounds and failure

Every resident host runs collection through `withRepositoryKnowledgeWorkerLock`, before convergence ownership selection. It never nests the lock. A busy lock produces no status. Cancellation, developer work, scheduler yield or an active/recoverable materialization defers collection.

Each cycle scans at most sixty-four chunks of at most one MiB and at most eight MiB of file or SQLite-cell bodies in total, checking a 100 ms deadline between chunks. A logical SQLite chunk has at most 128 rows and one MiB of string or blob cells. Sweep unlinks at most thirty-two objects. Metadata inventory permits at most 100,000 files/directories; event and report reference inventories permit at most 200,000 records each. These are separate bounds, not a claim that complete metadata replay finishes in 100 ms. Immutable SQL report references have their own resumable digest cache. Each cycle makes at most sixty-four report lookups. Report bodies have a separate eight-MiB cycle budget and the existing one-MiB per-report limit. The current `context-quality-admission.ts` and `context-quality-commit.ts` writers append a publication event in the same transaction as each SQL report, so every stored report has a canonical event root. A completed pass waits twenty-four hours before a new scan. Further sweeps of the same pass reuse its completed scan.

The private scan envelope requires `scan` and a SHA-256 `checksum` of its exact JSON serialization. `scan` requires `schemaVersion: 1`, `nextScanAt` in epoch milliseconds, `eligible` hashes, `files`, and `reports`. Each file entry binds `identity`, `complete`, byte `offset`, bounded overlap `tail`, and candidate `references`; SQLite entries also bind table and row cursors. Each report entry binds `referenceSeq` and either immutable `references` or an observed absence. Absolute reference paths and hashes stay only in this private projection. Fixed `.next` files are replaced and excluded from roots, so an interrupted projection cannot pin its own candidates.

One checksummed scan projection is limited to 32 MiB. Each cached body scan binds the exact file identity, size and modification/change times. SQLite identities include the WAL identity. A changed body restarts its scan. The final inventory and event head must still agree before deletion. The collector does not change references or event history. An interrupted unlink leaves only unreachable objects for a later pass.

`cas-retention-observation.json` replaces one bounded local observation. Required fields are `schemaVersion: 1`, ISO `observedAt`, `status: yielded|collected|unavailable`, integer `removedObjects` and integer `reclaimedBytes`. Counts describe completed unlinks in that invocation. `unavailable` can follow partial reclamation; it means remaining work stopped without authorizing further deletion. A process crash can omit the observation. No paths, hashes, private text, provider output, credentials or unrestricted errors enter this status or a new event.

## Growth at the source

Baseline sources and stage source capture remain embedded to preserve current input identities and receipt proofs. A future version may store one immutable baseline per obligation and one capture per source snapshot, with a typed input envelope that binds their hashes. Readers must hydrate and verify every referenced object before reconstructing the exact current proof input. This change requires compatibility tests for old envelopes and crash recovery; it is outside this retention delivery.
