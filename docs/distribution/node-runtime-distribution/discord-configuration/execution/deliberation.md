# Discord deliberation

Optional `deliberation` binds exact human principals and permissions to the durable conversation queue. `cliExecutable` must be an executable Lervo CLI matching the installed Node release. Topics cross the process boundary on stdin, and the queue-assigned identity must match the managed result. Configured `remoteCommands.providerHost.executables`, `models`, and `reasoningEfforts` are passed through the worker boundary to each managed deliberation adapter; an installed service must not fall back to its inherited `PATH` or provider defaults when deployment configuration selected an exact provider runtime.

The Node runtime prepends its own executable directory to the child `PATH`, so an executable JavaScript CLI with an `/usr/bin/env node` shebang remains launchable under a restricted systemd environment. Configuration preflight still verifies the exact file and execute permission. A launch or child-process failure is operator evidence and must not be rendered to Discord as canonical-history repair guidance.

When `defaultPolicyId` is configured, an authorized human starts deliberation with an ordinary explicit request such as “independently challenge this design and decide whether it is ready.” The semantic resolver supplies the configured policy; the user does not need to know a policy ID or command syntax. Keep `/lervo deliberate start <policy-id> -- <topic>` for exact policy selection, diagnostics, and compatibility, and use `/lervo deliberate status <deliberation-id>` for inspection. Resume only an authoritatively reconciled interruption.

Natural multi-agent start first resolves the exact active participation routes and counts distinct real participant runtimes. Fewer than two verified participants returns a bounded reply before queue admission: no provider call, partial deliberation, policy-seat speaker, or automatic retry occurs. Direct CLI policy execution remains a separate diagnostic and repository decision surface; it does not prove a Discord multi-agent discussion.

The ordinary natural discussion path is separate from the formal policy queue. It selects two exact cross-Node bot peers from the shared conversation and carries both identities in the persisted assignment, but only one explicit active participant owns the first visible assignment. After that content-addressed contribution is recorded, the coordinator emits an idempotent assignment whose first visible bot address identifies the remaining participant; only that normalized exact participant may start the second `review` turn. The adapter resolves the ordered native address through its identity port before canonical mention sorting, so scheduling never depends on set order. Each receiver authenticates the source bot and current durable agent binding before using its own role, context, and repository knowledge. This preserves independent review while limiting the installed host to one discussion provider process at a time. The coordinator waits for both contributions and uses the `reasoning` profile once for the final synthesis after the second review releases its provider process. Discord message text is not the complete control contract: a versioned nonce authenticates the coordination kind and opaque discussion ID, the identity boundary normalizes the active participant, and each Node owns the full persisted envelope and validates source, active target, complete roster, reply, content hash, deadline, automation depth, and idempotency. Assignment rendering is bounded to Discord's 2,000-character limit before publication.

The coordinator persists a five-minute deadline. Restart preserves accepted turns and does not replay completed provider work. At expiry, one or more verified contributions produce a bounded non-converged synthesis that names the missing evidence as risk; zero contributions produce a fixed terminal reply without another model call. Either path releases the discussion instead of leaving the user with silence.

The default policy may define internal decision-coverage responsibilities, but those names are not Discord identities. Natural start replies contain no policy ID, deliberation ID, artifact count, or wait instruction. A verified terminal result returns the writing-gated decision body, or the final review when consensus was not reached, to the original conversation. Process stderr and recovery details remain in operator diagnostics.

Optional `deliberationParticipation.routes` lets this exact hired-agent deployment accept selected formal policy seats. Each route requires `policyId` and `policyRoleId` and may override provider, model, and reasoning effort. Configuration requires `agentId`, the exact `organization` binding, `policy.mode: proactive`, `system` in `respondTo`, and `deliberation.artifact.recorded` in `signalCodes`. It never matches by display name, workforce role name, provider, or conversation presence.

```json
{
  "deliberationParticipation": {
    "routes": [
      {
        "policyId": "deliberation_architecture-review",
        "policyRoleId": "product-owner",
        "provider": "codex",
        "model": "gpt-6-astra",
        "reasoningEffort": "high"
      }
    ]
  }
}
```

At start, the Node resolves the route to one current organization membership, external deployment, and channel membership, then records a deterministic assignment and route hash. The assigned worker recomputes those coordinates and resolves the exact versioned role contract before provider work. Resume requires the identical accepted route. The policy seat remains the deliberation responsibility; the verified workforce role supplies the participant's name, description, required inputs, context policy, and default skills. Contributions for a bound seat are delivered exactly once, without a synthetic policy-role heading, through that participant's already attached bot or authorized webhook runtime. No route creates a webhook, agent, or copied application identity. An unassigned seat remains internal review evidence and produces no Discord speaker turn.

Named formal participation currently requires the accepted agent deployment to be co-resident in the repository Node running the deliberation. Ordinary cross-Node agent discussion uses authenticated `peerAgents`; its evidence does not imply remote formal policy-seat execution. Consequently, the formal start remains unavailable when only one co-resident real participant is eligible even if several cross-Node discussion peers are visible in Discord.

The stored policy must also declare its managed execution budget. The installed architecture policy permits at most 32 provider calls, 500,000 exact observed total tokens, and 1,800,000 elapsed milliseconds, and blocks when token evidence is unavailable. With four reviewers, two rounds, one revision, one verification, and one decision, its no-repair baseline is 24 calls including independent semantic evaluation. The remaining eight calls admit four bounded writing repairs and their evaluations; configuration no longer sets the ceiling equal to the best-case baseline. Execution-plan construction rejects a policy whose call ceiling cannot complete the no-repair baseline. The worker derives a smaller managed ceiling from `processTimeoutMs`, so this policy requires `processTimeoutMs` of at least 1,860,000 milliseconds to preserve the worker's 60,000-millisecond terminalization reserve. The managed runner separately reserves the final portion of its elapsed ceiling for stream drain, provider stop, repository inspection, failure recording, storage close, and summary serialization. Reaching a limit records an exact terminal reason. Discord distinguishes budget exhaustion from participant-binding invalidity, says that partial work was not adopted, and does not repeat the same execution automatically.

Before the first provider call, the worker queries current repository knowledge from the complete human topic, verifies every selected publication against its exact content hash, and installs a bounded immutable evidence bundle in the deliberation workspace. Every decision stakeholder receives that same bundle. If no current publication is available or any selected byte changes, the deliberation records a terminal failure and spends no provider call. Provider tools are not a retrieval fallback.

The conversation policy must use `proactive`, allow the `system` actor, and subscribe to `deliberation.artifact.recorded`, `deliberation.completed`, and `deliberation.attention`. Lervo projects a writing-gated artifact only when a real participant binding exists, and it sends the verified body through that participant's runtime. Policy-only artifacts remain canonical internal evidence. These signals do not start another provider turn or expose prompts, private reasoning, or provider payloads.

An inconclusive reconciliation binds its attention event to the queue's durable uncertainty time. Restarting the service may resume bounded inspection, but it must not create another Discord message for the same unresolved job.

`deliberation-artifact-cursor.json` is an owner-only, atomic, rebuildable projection containing the schema version, exact cursor kind, project and integration IDs, last inspected repository-event sequence, and update time. First enablement starts at the current event head and does not replay old deliberations. The cursor advances only after an origin-less predecessor is intentionally skipped or exactly one interaction policy durably commits an outbound. A crash before advancement reuses deterministic event identity, while a delivery failure after advancement remains owned by the interaction outbox and adapter replay. Invalid artifact evidence, unavailable interaction ownership, or zero or multiple responding policies fails the deliberation worker without skipping the source event. A legacy artifact with no bound origin produces no Discord update and cannot satisfy installed acceptance.
